ROS 2, the Talos way

Talos's software is about twenty-five separate programs that never call each other directly. They only exchange messages through ROS 2. Learn its handful of ideas and you can watch, debug and change any part of the robot.

The short version
  • Each program is a node. Nodes talk through topics (streams), services (quick request and reply) and actions (long jobs with progress), and they are configured with parameters.
  • Almost all of Talos's names live under /talos/; shared ones like /tf and /clock don't. Messages are standard ROS types plus the team's own package, riptide_msgs2.
  • In Nereus one launch command starts the whole stack; on the robot the launcher starts it subsystem by subsystem. In Nereus the simulator stands in for the hardware, and the stack runs on the simulator's clock.
  • The middleware is Zenoh: a router on the Orin, and every laptop connects to it over TCP.
  • The ros2 command shows all of it from any laptop that can reach the router.

ROS 2 (Robot Operating System 2) isn't an operating system. It is a set of libraries and tools: one program publishes a message, another receives it, and neither needs to know where the other runs. Talos uses ROS 2 Humble on Ubuntu 22.04, on the Orin and on every team laptop. Every example on this page comes from Talos's own code or from a capture of the full stack running in Nereus.

The graph: nodes and what connects them

A node is one participant with a name, like /talos/mpc_controller. Usually it is one process, started from an executable in a package (riptide_mpc's mpc_controller). Nodes find each other by the names of what they exchange, not by address. The controller subscribes to /talos/odometry/filtered. It doesn't know or care which program publishes it, and in Nereus the same name is still served by the same EKF, fed by simulated sensors.

All the nodes together, with their connections, are the ROS graph. Here is Talos's, captured while the full stack ran the competition tree in Nereus.

Things to notice:

  • The simulator is just another node. physics_simulator publishes vectornav/imu, dvl_twist, gyro/twist, depth/pose and the camera images under the same names the real drivers and boards use, and subscribes to thruster_forces. The rest of the stack can't tell. On the robot those topics come from the sensor drivers and the boards' micro-ROS firmware (Firmware).
  • The viewer is four nodes on your laptop (nereus_viewer, viewer_panels, viewer_plots and a timing helper), in sim and on the real robot. It takes part in the graph like any other node: it subscribes to images and paths, publishes the software kill and starts trees.
  • One process can hold several nodes. The AprilTag detector is a component loaded into tag_container (both appear in the graph), and every tf2 listener adds a hidden helper node.
  • One node can hold many subscriptions to one topic. autonomy subscribes to odometry/filtered hundreds of times: each behaviour-tree node that reads odometry makes its own subscription (CenterDetection, for one).

On the robot you would see the same graph minus the two simulator nodes, plus the drivers: the IMU, FOG, DVL, cameras and the micro-ROS agent for the boards. Appendix A lists every topic, service and frame.

Topics and messages

A topic is a named stream. Any number of nodes publish on it and any number subscribe; the publisher never waits for anyone. Most of Talos is topics: sensor readings, the EKF's odometry, detections, thruster forces.

Every topic has exactly one message type, a fixed structure written in a small text file. Talos uses two kinds:

  • Standard types wherever one fits: sensor_msgs/msg/Imu from the VectorNav, nav_msgs/msg/Odometry from the EKF, vision_msgs/msg/Detection3DArray from the detector, plain std_msgs/msg/Bool for state/kill. Standard types mean standard tools (the EKF, the viewer, plotting) work without changes.
  • The team's own, in riptide_msgs2 (in riptide_core, folder riptide_msgs): 24 messages, 8 services and 10 actions for things no standard type covers, like kill-switch reports, controller commands, ESC telemetry and the tree stack.

At build time, rosidl turns each file into a Python class and a C++ struct, so code writes msg.kill_switch_id = 3, never bytes.

Three habits follow from how messages work:

  • Unset fields aren't empty, they're defaults. Numbers are 0 and strings are empty, but a geometry_msgs/Quaternion starts at w: 1, a real orientation ("face +x"). That's why goals that mean "keep the current attitude" must say w: 0.0 (Commanding Talos).
  • Stamped messages carry a header. header.stamp is when the data was measured and header.frame_id is the frame it is in. The EKF, mapping and the MPC all line data up by stamp, so a wrong clock shows up as a wrong position.
  • Changing a message changes everyone. Every node that uses it, the boards' firmware included, must be rebuilt, and old bags can no longer be read with the new definition. Add a field only when you have to.

A minimal Python subscriber, the shape of every rclpy node on Talos:

import rclpy
from rclpy.node import Node
from std_msgs.msg import Bool

class KillWatcher(Node):
    def __init__(self):
        super().__init__('kill_watcher')
        # relative name: becomes /talos/state/kill when run in the talos namespace
        self.create_subscription(Bool, 'state/kill', self.on_kill, 10)

    def on_kill(self, msg):
        self.get_logger().info('killed' if msg.data else 'enabled')

rclpy.init()
rclpy.spin(KillWatcher())      # run callbacks until Ctrl+C

Run it with python3 kill_watcher.py --ros-args -r __ns:=/talos. The node does nothing between messages: spin waits, and calls on_kill whenever one arrives. Timers work the same way (create_timer(0.05, self.tick) is the MPC's 50 ms loop, in C++).

Quality of service

Each publisher and subscription also states a QoS profile: what to do when the network is slow, and what a late joiner gets. Three settings matter on Talos:

SettingChoicesOn Talos
Reliabilityreliable: lost data is resent.
best effort: lost data stays lost.		Reliable is the default (a bare 10 in create_publisher(..., 10)). Subscriptions to fast sensors use best effort: the MPC reads the IMU, FOG, DVL and depth with SensorDataQoS().keep_last(50) (line 567), and the boards take the software kill best-effort (POAC ros.c).
Durabilityvolatile: only messages sent after you joined.
transient local: the publisher keeps its last messages for late joiners ("latched").		/tf_static, robot_description and the MPC's whole planned path (QoS(1).transient_local(), "latched for late viewers", line 453). A viewer opened mid-path still draws it.
History depthHow many messages wait in the queue if your callback is slow.10 for most topics; 50 for the MPC's 400 Hz IMU, so a slow tick doesn't drop samples before the estimator sorts them by stamp.

Why best effort for sensors: an IMU sample that arrives late is worse than none, because the next one, 2.5 ms later, is fresher. Resending would only delay it. Commands, like a controller setpoint (controller/linear) or an actuator command, are sent once, so they must arrive: reliable.

Zenoh is forgiving, DDS is not

With the default DDS middleware, a best-effort publisher and a reliable subscriber never connect, and nothing tells you: the topic exists, echo just shows nothing. Under rmw_zenoh, which Talos uses, "any publisher can match any subscription" (rmw_zenoh design), so a mismatch still delivers. Choose QoS as if it mattered anyway: Nereus can run on Fast DDS (rmw:=), and transient local still only works if the publisher asks for it. ros2 topic info -v prints both ends' QoS.

Services: ask and wait

A service is a request and one reply, for things that finish quickly and need an answer: "which trees are there?", "switch the detector to the down camera". The server runs a callback; the client waits for its return.

  • autonomy/list_trees (riptide_msgs2/srv/ListTrees): the viewer's tree picker fills from it.
  • set_camera_is_dfc (std_srvs/srv/SetBool): the detector swaps between the forward and down camera models.
  • mapping_target (riptide_msgs2/srv/MappingTarget): the tree tells mapping which object it is looking for.
  • command/actuator/torpedo (std_srvs/srv/Trigger): the trees fire through a service. ActuatorTranslator turns it into an std_msgs/Empty message on the topic of the same name, which the POAC board's firmware subscribes to (ros_torp.c).

Prefer standard std_srvs types (Trigger, SetBool) when they fit, as Talos mostly does. Never call a service from inside another callback of the same single-threaded node and block for the reply: the reply can't be processed until your callback returns, so it waits forever.

Actions: long jobs with progress

An action is for a job that takes seconds or minutes and can be stopped: run a mission tree, fly a path, tare the gyro. The client sends a goal; the server accepts or rejects it, streams feedback, and ends with a result. The client can cancel at any time. Under the hood an action is three services and two topics under <name>/_action/.

Talos's two most important actions are chained: the viewer asks autonomy to run a tree, and the tree asks the MPC to fly paths.

Two Talos details worth knowing:

  • "Succeeded" isn't success. doTask calls succeed() when the tree ends on its own, whether the tree's status was SUCCESS or FAILURE; the tree's status is in returncode (2 = SUCCESS, 3 = FAILURE). The viewer checks all three: "a SUCCEEDED action, no error flag and returncode 2" (uwrt_autonomy.cpp).
  • The stack comes on a topic. ExecuteTree declares a feedback field, but doTask publishes the running stack on autonomy/tree_stack instead (UWRTLogger.hpp). Any number of laptops can watch it, not only the one that started the tree.

Parameters and YAML files

A parameter is a named setting that belongs to one node: a number, string, bool or list. The node declares it with a default, the launch file can override it from a YAML file, and anyone can read or change it while the node runs. The MPC's are in riptide_mpc/config/mpc.yaml:

/**/mpc_controller:          # which node: any namespace (/**), node name mpc_controller
  ros__parameters:             # fixed key; everything below is a parameter
    control_period: 0.05       # s; also the MPC stage length
    horizon_steps: 30          # 1.5 s horizon (after the 0.1 s thruster delay)
    motion:
      linear_speed: 0.6        # nested keys become motion.linear_speed

And the node's side, in mpc_controller_node.cpp:

s.dt = declare_parameter("control_period", s.dt);   // the code's default unless YAML says otherwise
  • The node name must match. The YAML key is the node name, not the executable or the package. A typo there doesn't fail; the node silently keeps its code defaults. ros2 param dump shows what it really loaded (the capture's dump for the MPC is in this site's data).
  • Some parameters change live. The MPC registers a callback (line 178) that accepts new motion limits, weights or a whole new hydrodynamic model while flying. Others are read once at startup. Check the code before relying on ros2 param set.
  • A live change dies with the node. Put anything you want to keep in the YAML, in git.
  • Parameters are services underneath. Every node serves get_parameters, set_parameters and four more. The graph shows autonomy as a client of /talos/mpc_controller/set_parameters: trees change MPC settings mid-mission.

Launch files

Nobody starts twenty nodes by hand. A launch file is a Python script that describes which nodes to start, with which names, parameters and arguments. Talos's tree of them:

  • riptide_bringup2/bringup.launch.py includes one launch file per subsystem: hardware (or acoustics only, with hardware:=none), control, navigation, the detector, mapping and autonomy. It passes each robot:=talos.
  • On the robot, the Orin's launcher starts those subsystem files one by one from a list (Computers and networks).
  • In Nereus, ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim starts the simulator, then the same bringup with hardware:=none, then the viewer. In the capture that one command started 18 processes (launch log). Leave out active_control_model:=mpc and bringup falls back to its default, hybrid, which starts the legacy complete_controller instead of the MPC (control_system.launch.py). mpc_model:=sim gives the MPC a model of the simulated vehicle.

One node, from autonomy.launch.py:

DeclareLaunchArgument('robot', default_value="tempest"),  # an argument: robot:=talos on the command line
GroupAction(actions=[
    PushRosNamespace(LC("robot")),         # everything below lives in /talos
    Node(
        package='riptide_autonomy2',      # the package (from its package.xml)
        executable='doTask',             # the program it installs
        name='autonomy',                 # the node name, replacing the code's "autonomy_dotask"
        parameters=[{'enable_zmq': False}],
    ),
], scoped=True)

Each subsystem's launch file defaults robot to tempest, Talos's predecessor. Launch one on its own without robot:=talos and its nodes appear under /tempest/, talking to nobody. Launching the stack covers the launch files in full.

Names and namespaces

Code mostly uses relative names like "thruster_forces". ROS prefixes the node's namespace, so the same code becomes /talos/thruster_forces on Talos and could run a second vehicle under another name. A name that starts with / is absolute and ignores the namespace. One with ~/ is private: it goes under the node's own name.

Written in codeNodeResolves to
"thruster_forces"/talos/mpc_controller/talos/thruster_forces
"autonomy/run_tree"/talos/autonomy/talos/autonomy/run_tree (a sub-name, not the node's name)
"/tf"any/tf: one transform tree for everyone
"/" + hostname + "/autonomy/bag_trigger"/talos/autonomy/<hostname>/autonomy/bag_trigger, named after the computer doTask runs on (DoTask.cpp)
"~/rgb/..."/talos/ffc/zed_node/talos/ffc/zed_node/rgb/... (the ZED driver's private topics)

Log lines name the node with dots instead of slashes: [talos.mpc_controller]: MPC ready: 8 thrusters, 0.050 s x 30 stages. A launch file can also remap a name (remappings=[('odom', 'odometry/filtered')]) to connect code you can't edit; Talos's own launch files mostly pass topic names as parameters instead (odom_topic, imu_topic in mpc.yaml).

TF: where everything is

Positions only mean something in a frame: "1 m ahead" of the camera isn't 1 m ahead of the DVL. ROS keeps all the frames in one tree, TF, published on two topics:

  • /tf for transforms that can move: the EKF's odom → talos/base_link (about 20 Hz in the capture) and mapping's object frames (7.5 Hz). Also the sensor mounts the robot description declares as movable joints (DVL, FOG, pressure sensor, acoustics, thrusters), which robot_state_publisher sends at about 7 Hz even though they never move.
  • /tf_static, latched, for the fixed joints: the IMU, the cameras, the torpedo, claw and other actuator mounts, plus world → odom and world → map.

So ros2 topic echo /tf_static won't show talos/dvl_link; a tool that replays sensor frames needs /tf too.

Any node asks a tf2 buffer "where is torpedo_frame in talos/base_link, at this stamp?" and gets an answer chained through the tree. The capture's tree had 89 edges, 27 of them static, from two roots: world and the AprilTag's tag36h11:0. In sim there is also a separate truth branch, world → simulator/talos/base_link, so the viewer can draw truth and estimate side by side.

Time: wall clock or sim clock

Every node has a clock. On the robot it is the computer's clock (the Orin syncs it to the opbox, Computers and networks). In Nereus it isn't:

  • The simulator publishes /clock, the simulated time, at every 2 ms physics step.
  • use_sim_time: true makes a node read /clock instead. Nereus sets it for the whole stack with one SetParameter (mission_stack.launch.py).
  • Then timers follow sim time. The MPC's 50 ms tick is 50 ms of simulated time, so a sim that runs at 0.95x, or pauses, takes the controller with it. Timers made with create_wall_timer stay on real time (the MPC's 2 s mount check, doTask's 1 s bag trigger).
  • One exception: the detector's launch file passes its own use_sim_time, default false, which beats the global setting (tensorrt.launch.py). It still works because it stamps each detection with its image's stamp (use_incoming_timestamp), not with its own clock.
Sim time is also a safety check

The MPC only sends RPM to the ESCs over CAN if its model describes the real hardware, can0 exists, and it is not on simulation time: "a simulator on the vehicle computer never drives the real thrusters" (configureHardwareOutput). That check only applies in the default hardware_output: auto; setting it to on skips it. Don't work around it.

The middleware: Zenoh, and domains

ROS 2 doesn't move bytes itself. It hands them to a middleware, the RMW, chosen per shell with RMW_IMPLEMENTATION. The default is DDS, which finds other nodes by multicast: every node announces itself to every machine on the network, and every node connects to every other. On one computer that's fine. Across a tether and Wi-Fi it means lots of discovery traffic, multicast that routers often drop, and many connections per laptop.

Talos uses rmw_zenoh_cpp instead:

  • One router, on the Orin. The Orin's launcher service starts rmw_zenohd at boot (ros_launcher.service, --start-discovery-server). The default command is in launcher.py, but a script that lives only on the Orin (uwrt_config/source/zenoh_server.bash, not in git) can override it, so the Orin router's exact settings aren't in any repo. Laptops reach it on TCP port 7447, and it does discovery for everyone.
  • Everyone else connects to it. The team's session config makes every node a client of tcp/orin2:7447 (zenoh_session.json5). A laptop opens one outgoing TCP connection; the robot never connects back.
  • It holds up under load. Nereus's launch file records why the team runs it on Zenoh: Fast DDS "showed 0.4-0.9 s reliable-delivery stalls of the simulator's /tf under full-stack load with camera traffic; Zenoh delivered the same run without stalls" (sim.launch.py).
  • Both ends must use the same RMW. A laptop on Fast DDS sees none of Talos's topics. Computers and networks shows how to set your laptop up, including over Tailscale.
  • No router, no graph. A Zenoh node finds others only through a router. With no session config it looks for one on its own computer (tcp/localhost:7447), and if none is there it prints Unable to connect to a Zenoh router. Have you started a router with `ros2 run rmw_zenoh_cpp rmw_zenohd`? and then sees nobody. For sim on your laptop, start that router in its own terminal first.
  • A client sends everything through its router. The team's source_rmw.bash makes every node a client of the Orin. Run the sim in a shell with it sourced and all its camera and IMU traffic crosses the tether to the Orin's router and back, even in another domain. And with it sourced, a local router reads zenoh_router.json5 and dials the Orin too.

Domains keep separate ROS systems apart on the same network. ROS_DOMAIN_ID, a number that is 0 when unset, is the first part of every Zenoh key, so two domains never see each other's data, even through one router. None of the team's scripts set it, so the robot and laptops use domain 0. For a sim that must not touch the robot, use another domain and your own router, in a shell without the robot's Zenoh config:

# only needed if your .bashrc sources source_rmw.bash
unset ZENOH_SESSION_CONFIG_URI ZENOH_ROUTER_CONFIG_URI
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 run rmw_zenoh_cpp rmw_zenohd    # a local router; leave it running
unset ZENOH_SESSION_CONFIG_URI ZENOH_ROUTER_CONFIG_URI
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
export ROS_DOMAIN_ID=61    # the capture ran in domain 61
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim

Nereus's own acceptance scripts refuse to run in domain 0 (hold.py). A sim in domain 0 on a laptop connected to the robot would publish fake sensor data, and a fake state/kill, next to the real ones.

Packages and colcon

Code is organised in packages: a folder with a package.xml (name, version, dependencies, build type). A workspace is a src/ folder full of them; colcon builds them all in dependency order into install/. The release repo's submodules in src/ hold 29 packages of two kinds (the ZED camera wrapper is cloned next to them and isn't counted here):

(The 29th, riptide_teleop2, has a COLCON_IGNORE file, so colcon skips it. Three of the built ones are legacy: the old simulator's c_simulator and camera_faker, replaced by Nereus, and riptide_rviz, from before the team dropped RViz.) Two naming traps: the package name comes from package.xml, not the folder, so the folder riptide_msgs builds riptide_msgs2 and riptide_hardware builds riptide_hardware2; and the node name is set in the launch file, so package riptide_autonomy2, executable doTask, runs as node autonomy. Setting up your machine has the build commands and A map of the code every package.

Sourcing is the step new members trip on most. A built workspace does nothing until a shell sources it:

  • Source the underlay first (/opt/ros/humble/setup.bash), then your workspace, the overlay (install/setup.bash). The one sourced last wins.
  • After colcon build, a new package or executable isn't found until you re-source install/setup.bash or open a new terminal.
  • Your .bashrc does it for every new terminal; Setting up your machine explains the layers.

Leave the kill topic to the viewer

Don't publish on /talos/command/software_kill from the command line unless you know the kill-slot rules: a "not killed" report can latch, and leave Talos enabled with nobody driving. Commanding Talos explains the slots and the safe way to hold a kill.
