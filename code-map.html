A map of the code

Talos's software is spread over about a dozen repositories, with firmware, board designs and tools in a dozen more. This is the map: what each one does, which branch the robot runs, and which chapter explains it.

The short version
  • The robot runs ROS 2 packages from five team repos (riptide_core, _control, _perception, _autonomy, _launch) plus a few outside drivers.
  • riptide_release ties them together: each repo is a git submodule pinned to one commit, and you deploy from that workspace.
  • Most of them run a feature branch, not master. Check the branch before you clone.
  • Below ROS sits titan_firmware on the boards; beside it is Nereus, the simulator and operator GUI for both sim and robot.
  • Mercury is a different robot's stack (Triton). riptide_simulator and the RViz panels in riptide_gui are legacy, but the Nereus viewer still draws the props from riptide_gui's meshes.

The stack in layers

Before the list of repos, here is the robot's software as one picture: data flows up from the boards through the drivers, the state estimate and perception to the mission tree, then back down as thruster commands. Each box is one program, labelled with the package that provides it (the sensor box groups three drivers); the dashed boxes are what the operator runs.

  • Firmware runs on the RP2040 boards (Firmware on the boards). Each board is a micro-ROS node, bridged onto ROS 2 over CAN by an agent on the Orin. Thruster RPMs skip ROS: the MPC writes them to the ESC boards as raw CAN frames.
  • Drivers turn devices into ROS topics: IMU, fiber-optic gyro, DVL, the two ZED cameras (Navigation sensors, The cameras).
  • Estimation is the robot_localization EKF, launched and configured by riptide_hardware (State estimation).
  • Perception and mapping find the props and keep one estimate of each (How Talos sees).
  • Autonomy runs a behaviour tree that decides what to do next (Behaviour trees); control turns that into thrust (How Talos flies).

Each package talks to the others only through ROS topics, services, actions and TF frames (ROS 2, the Talos way). That's why the code can live in separate repos: a package mostly needs another repo for its message types, not its code.

Every repo and package

The explorer below is generated from the repositories themselves: package.xml for names, versions and dependencies, CMakeLists.txt and setup.py for the nodes each package installs, and a line count of every tracked source file. Vendored libraries (the VectorNav SDK, Dear ImGui, the Pico SDK and the like) are left out.

"Depends on" lists only the team's packages. Talos also leans on outside packages that come from ROS 2 or the system, not a team repo: robot_localization (the EKF), behaviortree_cpp_v3 (the mission trees), Eigen and yaml-cpp (the MPC), rmw_zenoh_cpp (the middleware: Zenoh; the launcher starts its router) and the detector's OpenCV and Ultralytics. Each package's "Upstream packages" line lists its own.

A few things stand out:

  • Nereus and the firmware are the biggest pieces. The simulator and viewer are about 78,000 lines of C++ and Python, the board firmware about 58,000 of C and C++. The robot's own ROS packages are smaller: riptide_control (mostly riptide_mpc) is about 18,000.
  • The mission is mostly XML. riptide_autonomy has about 10,000 lines of code (mostly the C++ tree nodes) and about 86,000 lines of XML, nearly all of it the trees in trees/. The competition tree alone is over 4,000.
  • Package names don't always match folder names. The folder riptide_hardware builds the package riptide_hardware2; likewise riptide_msgs2, riptide_descriptions2, riptide_controllers2, riptide_mapping2, riptide_autonomy2, riptide_bringup2. ros2 run and ros2 launch want the package name, not the folder.
  • Two marker files change how a package is built. COLCON_IGNORE makes colcon skip it everywhere (riptide_teleop, and Nereus, which has its own CMake build). DEPLOY_IGNORE keeps it off the robot (riptide_rviz, riptide_meshes, camera_faker).

Where it lives on your machine

Everything goes under ~/osu-uwrt. Setting up your machine walks through it; this is the layout you end up with:

There are two workspaces because they do different jobs:

  • development/ is created by riptide.repos with vcs import (a tool that clones every repo a list names). It clones the team repos on master (ros2 for autonomy) and the dependencies on their own branches (ros2_dev for the DVL driver), and builds them as two chained colcon workspaces.
  • release/ is riptide_release, cloned with --recursive. It is the one you deploy from and the one GUI tools should run from, so your laptop and the robot run the same code.

Talos's current code is on feature branches, so a fresh development/ on master isn't what the robot runs. Check out the branch from the table below, or work in release/src directly.

The release repo pins everything

A git submodule records one exact commit of another repo. The release workspace is built on that. So one commit of riptide_release names exactly which commit of every package was meant to be on the robot. That's the whole idea (the README spells out the routine):

  1. Before a pool test, move each submodule to the commit you want to test and commit the release repo ("Pre RPAC test 10-12-26").
  2. At the pool, deploy from ~/osu-uwrt/release with colcon deploy: it copies the package sources to ~/colcon_deploy/src on the Orin and builds them there. Packages with DEPLOY_IGNORE stay behind.
  3. After the test, commit any fixes made at the pool in their own repos, bump the submodules, and tag the release with the date. If a later change breaks something, you can roll back to a tag.

The release repo's CI, ros2-ci.yml ("ROS 2 Full Stack CI"), builds every package in src/ except tensor_detector with colcon on every push and pull request to master. That is the automatic check that a set of pins builds, with one catch: if a pinned commit can't be fetched, it falls back to that submodule's branch tip, so a green build doesn't prove that exact pin builds.

In practice the last dated tag is from June 2024 (6-29-24_talos) and robosub2026 is the newest tag. Recent tests are found by their "Pre … test" release commits instead (the history below).

A pin only matches the robot if your checkout matches the pin. colcon deploy rsyncs each package folder from your working tree (deploy.py), not the pinned commit, and the robot's copy has no git history. Local edits, untracked files and branch commits past the pin all go to the Orin. Run git submodule update in ~/osu-uwrt/release and check git status is clean before you deploy. Packages generated from Simulink by riptide_simulink (staged in src/simulink_models/) aren't in any repo, so no release commit pins them.

Legacy code and other robots

The repos carry a lot of history, and GitHub search will happily send you to it. What's no longer used on Talos:

  • riptide_simulator (c_simulator, camera_faker): the previous simulator. Nereus replaced it (Nereus, the simulator).
  • The RViz panels in riptide_rviz (in riptide_gui): the old operator GUI. The team no longer uses RViz; the Nereus viewer drives both sim and robot. Old READMEs still say "start RViz". One file in it is still live: the viewer reads riptide_rviz/config/markers.yaml, the list of course markers.
  • complete_controller: the Simulink sliding-mode/PID controller in riptide_controllers/models, built with riptide_simulink. riptide_mpc replaced it; control_system.launch.py still starts it unless you pass active_control_model:=mpc.
  • The vectornav driver in the dependencies workspace: riptide_imu replaced it.
  • The monitor nodes in diagnostics.launch.py: out of date and not run. The diagnostics entry is still in talos_launch_mpc.yaml and the bench list, but nobody starts it (Launching the stack). The leak sensor: no longer used.
  • Archived repos on GitHub (riptide_kill_switch, riptide_controllers, riptide_mapping as separate repos, riptide_yolo, uuv_simulator, …) are from before the current repo layout.
  • riptide_slam and riptide_isaacSim are experiments that Talos doesn't use; Nereus now makes the synthetic training data (Training the detector).

riptide_gui and riptide_simulator are still submodules, which is why they show up in the pins table and the history above. riptide_gui is still pinned because the Nereus viewer draws the mapped props with its riptide_meshes models, placed by the marker list in riptide_rviz/config/markers.yaml; its recent commits (September and October 2026) are prop mesh fixes, and a wrong-looking prop in the viewer is fixed there. Its RViz panels were last used at RoboSub 2026 (the "Semis2" and "Finals config" commits, July 2026). The old simulator was worked on until September 2026, when Nereus was started; Nereus joined the release repo on 27 October 2026. Don't start new work in riptide_simulator or the RViz panels.

The mercury_* repos (mercury_release, mercury_dev, mercury_controller, …) are a separate ROS 2 stack for Triton, the team's second vehicle: the 2025-26 rebuild of the earlier secondary AUV, competing at RoboSub 2026 (RoboSub and the course). The firmware's DeviceList.jsonc lists the "Triton boards" with mercury/… board types. Its mercury_release pins submodules the same way riptide_release does. The uwrt_docs Sphinx docs cover Mercury packages, not Talos's. Inside the Talos repos you'll also meet configs for older vehicles (Puddles, Tempest, LilTank in riptide_descriptions/config); Talos's are always the talos* files.

Open problems

Looking for something to work on? These are the known gaps the other chapters describe, one line each. They reflect the code at the branches in the pins table; check the code before you start, since someone may have fixed one since.

  • The pinger order looks inverted. buffer_0_closer true means the torpedo stop was louder, but the mission stores it as is_table (Acoustics).
  • The pinger comparison can go stale. In max mode, peaks 1000 or more apart set nothing, and the node keeps publishing the old answer (Acoustics).
  • The IMU's angular-velocity covariance is about 10,000× too big, so the EKF trusts its model far more than the gyros (Sensors).
  • The battery housings have no agent. The can1 micro-ROS agent was turned off "until poac/batteries happy", so state/battery doesn't reach ROS (Firmware).
  • The viewer has no PVT button. The old RViz button's node, pressure_monitor.py, is installed but nothing starts it (Pool test day).
  • The diagnostics monitors are out of date and not run, so the viewer's CPU chip stays grey (Launching the stack).
  • The prebuilt downward-camera engine is an untested risk. dfc_rs_26.engine only loads on the GPU and TensorRT it was built for, with no fallback (Setting up your machine).
  • Nereus has no pinger, so the random-pinger step can't be tested in sim (Nereus).
  • riptide_navigation, still in the pool list, has no source in any team repo. It is a Simulink-built navigation; the team runs riptide_hardware2's instead, never both (Launching the stack).
