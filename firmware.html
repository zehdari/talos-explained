Firmware on the boards

Every circuit board in Talos has a small computer of its own, running C that the team wrote. This chapter is that code: how it talks, how it keeps Talos safe, and how to build, flash and debug it.

The short version
  • Each board has a Raspberry Pi RP2040 microcontroller. Its firmware lives in titan_firmware: one project per board, sharing one set of libraries and one main loop.
  • Boards talk over CAN with CANmore, the team's protocol, and each one is a micro-ROS node: copro_agent on the Orin carries its topics into ROS. Thruster RPMs skip ROS: the MPC writes raw CAN frames to the ESC boards.
  • The POAC board decides kill. Every other board follows its state/kill, and kills itself if that goes quiet for 500 ms.
  • Boards are reflashed over CAN with upload_tool, and inspected with canmore_cli.

Read from titan_firmware master at 058df2a (10 Oct 2026). What a board actually runs is in its state/firmware topic.

Building an image

The firmware is C on the Pico SDK, built with CMake and the gcc-arm-none-eabi cross compiler on Linux (WSL works). One-time setup: docs/01_Setup.md. Then, for each board:

cd ~/osu-uwrt/development/titan_firmware
cd talos/ESCBoard
mkdir build && cd build
cmake ..
make -j8

That leaves three files: esc_board_ota.uf2, the application, for flashing over CAN; esc_board_with_bl.uf2, plus the bootloader, for USB or a debug probe; and esc_board.elf, with debug symbols. Keep the ELF: GDB needs the exact one that is on the board.

  • Build type. Only RelWithDebInfo (the default) goes on the vehicle. The type is cached, so delete build/ to switch.
  • Messages are compiled in, from riptide_core's master on GitHub. Change a message a board uses, and it must reach master before you rebuild libmicroros and reflash that board.

How a board knows who it is

A board's CAN client ID is fixed at compile time in its board header (poac_board.h), with two exceptions. The ESC boards read a solder jumper on GPIO 29 at boot: open is client 2 (thrusters 0–3), bridged is client 3 (thrusters 4–7), so one image fits both (main.c). Each battery housing reads a serial number written once into its flash at 0x101FF000; a blank one stops the firmware.

On ROS each board is a node in /talos (poac_board, esc_board_0 and _1, camera_cage_bb, led_board, ivc_board), and every second each publishes state/firmware: name, client ID, version, uptime, fault bits and kill-switch bits.

One loop, every board

There is no operating system. Each board runs one loop on core 0, written the same way in every project (main.c): background tasks, then the ROS tasks if the agent is connected, then safety_tick(), which checks the kill switches and feeds the watchdog. Nothing in it may block: slow work goes to interrupts, DMA (hardware that moves data without the CPU), the PIO blocks (the RP2040's small programmable I/O engines) or core 1.

CAN and CANmore

CAN is a two-wire bus where every node hears every frame. A frame has an ID (11 bits, or 29 in an "extended" frame) and up to 8 data bytes. When two nodes start at once the lower ID wins, and another node must acknowledge every frame. Talos has two buses, both classic CAN (no CAN FD):

  • Internal, can0 on the Orin, 1 Mbit/s: every board but the batteries.
  • External, can1, 250 kbit/s: the smart battery housings.

Why a protocol of their own

ROS messages are far longer than 8 bytes. CANmore (titan_canmore) splits them across frames and keeps what is needed to reassemble them in the frame ID, so all 8 data bytes carry payload. Every frame is one of two kinds. A message frame is part of a ROS message (up to 1024 bytes): the first frame holds the length, the last a CRC-18 checksum, and losing any frame drops the message. A utility frame stands alone on one of 16 channels: 0 thruster commands, 13 remote terminal, 14 control interface (debugging and the bootloader), 15 heartbeat. The ID starts with the client ID, so the POAC board (1) wins arbitration over the ESC boards (2, 3).

From topic to frames: micro-ROS

A board doesn't run DDS, ROS 2's usual middleware, itself. It runs micro-ROS: a small XRCE-DDS client ("eXtremely Resource Constrained Environments") that asks an agent on the Orin to create its publishers and subscribers and carry its messages.

  • The agent is copro_agent, started with the hardware launch and restarted if it dies (copro_agent.launch.py). It reassembles each board's frames and hands the messages to ROS 2 (over Zenoh today).
  • The battery housings are cut off for now. The second agent, on can1, was commented out on 27 Oct 2026 "until poac/batteries happy" (720bdd9). Their state/battery doesn't reach ROS, and nothing on ROS reaches them, state/kill included.
For maintainers: the agent's code
  • osu-uwrt/micro-ros-agent builds the agent from four pinned submodules (build_agent.bash): the team's fork of eProsima's Micro-XRCE-DDS-Agent (branch Happyxrce), micro-ROS-Agent-impl, titan_canmore and micro_ros_msgs.
  • The can transport isn't in upstream micro-ROS (CanAgentLinux.cpp). -m rmw is a middleware the team added in 2025 (RmwMiddleware.cpp), so the agent publishes through the Orin's RMW instead of speaking DDS.
  • A board has one node with up to 15 publishers and 15 subscribers. The transport is transport_can.c, and the limits are in colcon.meta. The boards use only topics, no services, since June 2025 (783b8e0, for Zenoh).
  • osu-uwrt/nano_ros (August 2026) is an experiment to replace micro-ROS with something lighter. No Talos board uses it.

Watchdogs, faults and crashes

titan_safety (safety.h), the first thing every board starts, assumes the firmware will hang or crash sometime. Its watchdog resets the board if a loop pass takes over 3 s while starting, or 250 ms once connected (safety_internal.h). Core 1, which runs the timing-critical work (the thruster loop, the battery gauge), must check in every 250 ms too. Each crash goes into a 24-entry crash log that survives the reset, and the board comes back with WATCHDOG_RESET raised.

Faults are a 32-bit word, one bit per fault. Any fault flashes the LED red and sets the error bit in the CAN heartbeat (decode one below).

Kill switches in firmware

The POAC board alone decides kill, from four slots: the kill switch and three software senders. Every other board follows its state/kill, relayed by copro_agent, and kills itself if that goes quiet for 500 ms. The slots, the rule and the sender lock: Commanding Talos.

An agent restart doesn't hold Talos killed. Slots keep their last report until the POAC board reboots (safety.c), so a latched enable, like the Nereus viewer's, is back as soon as the agent is. To keep Talos killed, pull the switch.

Thrusters: from RPM to DShot

Each ESC board drives four ESCs (hardware: Thrusters and ESCs). The MPC sends each board one CAN frame of four RPM targets every 50 ms, with no ROS involved (Commanding Talos). A target expires after 500 ms.

Core 1 runs the RPM loop (core1.c):

  • Talk. Each ESC gets its throttle over DShot600, a digital signal made by the PIO, and answers on the same wire with its RPM.
  • Control. Per thruster, the throttle is a fitted guess for the target RPM (feed-forward), plus a correction proportional to the RPM error (on a 100-sample average), plus a slowly growing correction once within 300 RPM of the target. It is capped at ±725 of the ±999 range.
  • Guard. If any disabled_flags bit is set, all four ESCs get zero (all six bits). After a kill you will see ESC_BOARD_OFF while thruster power is cut, then ESC_POWERON_DELAY for 5 s while the ESCs start (dshot.h): the pause between Enable and the first thrust.
  • Reversed motors. Slots 0 and 3 on each board (mask 0b1001), so thrusters 0, 3, 4 and 7, spin the other way for the same target.

The depth sensor

The camera cage board reads the Bar02 pressure sensor (driver_depth) and publishes state/depth/raw at 20 Hz, negative below the surface. The sensor itself: Navigation sensors.

  • It zeroes itself at power-up, averaging 20 readings into a surface pressure: wherever Talos is when the board starts reads as 0 m.
  • The zero survives a watchdog reset, but not a power cycle. To re-zero at the surface, send CLEAR_DEPTH on command/electrical.

Flashing and upgrading

Every board keeps the titan bootloader in its first 16 kB of flash (main.c; Boot delay and Bootloader mode in the life cycle). upload_tool sends a running board there over CAN, so an upgrade needs no buttons, and the bootloader checks a CRC-32 of the application's first page before starting it, so a half-written image never runs.

WayNeedsCommand
CANThe board on a bus with your computer: the Orin, or a USB-CAN adaptermake upload_ota
USBBoard power (most Mark 2 boards don't take it from USB), BOOT held during resetmake upload, or copy the UF2 to the RPI-RP2 drive
SWDA Picoprobe (a Pico flashed as a debug probe), a Tag-Connect cable (it clips onto pads; the board has no connector), and OpenOCD 0.12 (the program that drives the probe)make upload

For a pool test, tools/archive.sh tags the commit, builds every project and packs the OTA images into full_ota.tar for ~/firmware_deploy on the Orin (deployment docs). Flash every board, both ESC boards and every battery housing included (no ~/firmware_deploy/bin yet? Run tools/tools_build.sh firmware_deploy on the Orin first):

cd ~/firmware_deploy/ota
tar -xvf full_ota.tar
# asks which matching board, then flashes
../bin/upload_tool poac_board_ota.uf2
# a board that crashes at once:
# wait for it, then power-cycle it
../bin/upload_tool -w esc_board_ota.uf2
# what is in this file?
../bin/upload_tool -i esc_board_ota.uf2
Before you flash
  • Kill the robot and keep clear of the propellers. A flashed POAC board reboots and cuts thruster power, and every board comes back killed.
  • Send the _ota image over CAN, never _with_bl. An interrupted bootloader upload needs USB or SWD to recover, which is hard on a sealed battery housing.
  • On a battery housing, mind USB power. Its board takes USB power unprotected: unplug everything else first (testing docs).

Your first firmware change

  1. Branch titan_firmware and read docs/02.
  2. Build a Debug image in a fresh build/: cmake -DCMAKE_BUILD_TYPE=Debug ..
  3. Flash a board on the bench, not in Talos, by any way in the table above.
  4. Watch the serial console and state/firmware; check the fault word with the decoder.
  5. Rebuild as RelWithDebInfo, test again, push, and deploy with tools/archive.sh.

Work from the outside in: the LED, then state/firmware, then the CAN bus, then the board itself.
