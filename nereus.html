Running Talos · Chapter 2

Nereus, the simulator

A pool, a course and a Talos that exist only in software, close enough to the real ones that the robot's own code can't tell the difference. Where you test a tree, a controller change or a new detector before anyone gets wet.

The short version
  • Nereus pretends to be the hardware: it publishes Talos's sensor and camera topics, takes the controller's thruster forces and moves a simulated Talos. The robot stack runs unchanged.
  • Nothing about Talos is in the code. The robot, pool, course and ROS wiring are YAML packs, merged into one resolved.json per run.
  • The physics is the same Fossen model, with the same numbers, that the MPC uses. Sensor noise comes from real pool bags. Cameras are rendered on the GPU with depth and point clouds.
  • One command starts it all: ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim.
  • It also renders labelled training images for YOLO. It doesn't simulate acoustics, sensor failures or a real pool's mess, so the pool still has the last word.

What Nereus is

Nereus is the team's simulator and operator interface. It has three parts:

  • nereus-sim, the simulator. C++: physics, sensors, cameras, mechanisms, props, scoring, and a ROS 2 bridge.
  • nereus-viewer, the pool viewer. The 3D pool and the operator panels. The same program drives the real robot at the pool, so it has its own chapter: The Nereus viewer.
  • Packs: YAML files in content/packs/ that describe the robot, pool, course and ROS topics.

The simulator, the robot stack and the viewer share no code. They only talk over ROS 2 topics. That is the whole design: if the stack sees the same topics, with the same names, types, frames and timing as on Talos, it behaves the same way. Nothing in the stack has an "if simulation" branch except the clock.

Everything is a pack

A pack is a folder with one YAML file and its meshes. Every number about Talos, the pool or the course lives in a pack, so changing the robot or laying out a new course is an edit, not a rebuild.

PackSays
robots/talosMass, drag, thrusters, sensors, cameras, mechanisms, frames
pools/…Size, floor shape, lane lines, water colour, lighting
tasks/robosub_2026The props, what counts as an event, how points are scored
bridges/uwrt_talosWhich ROS topics and services, with which types and fields
equipment/uwrtTeam gear at the pool: the AprilTag board
scenarios/…Picks one of each and places everything

Before a run, python -m nereus.packs resolve checks every pack against a JSON schema and cross-checks them (does the bridge name real sensors? does the robot have a claw for the table task?), then writes one resolved.json. The simulator and the viewer only ever read that file. Errors name the file and the key.

Check a pack after editing, from the nereus folder:

uv run nereus-packs validate content/packs/scenarios/talos_uwrt
Gotcha: pack paths are relative

A scenario names its robot, pool, course and bridge as folders relative to the scenario file (robot: ../../robots/talos). The schema rejects absolute paths. If you copy a scenario somewhere else to try a variant, fix those paths so they still point at content/packs/ from the new place.

The course and scenarios

The scenario is the file you edit most. It places the pool, the AprilTag board and each task in the world, sets the robot's start, the random seed and the 2 ms physics step. Its world is the robot's map frame: the task poses in talos_uwrt are copied from riptide_mapping's prior map, so before any detection the simulated course and the robot's map agree (how the map works).

  • talos_uwrt (the default, pool:=robosub): the RoboSub 2026 pool, 50 × 22.86 m and 2.13 m deep.
  • talos_uwrt_rpac (pool:=rpac): Ohio State's RPAC dive well, 25.23 × 17.07 m, 5.18 m deep with a sloped floor. Here the scenario hangs the board on the deep-end wall and places the world from the tag, the way the stack does it (world_placement). Move the board and the map and course move with it.

Moving the course. Real props are never exactly where the prior map says. To test that, move the tasks in the simulator but not in the map: edit task_placements in a copy of the scenario, or use the viewer's Edit map → Sim course, which saves through nereus.packs set-course (comments kept) and restarts the simulator. One mission in Nereus runs the tree on a course moved 72 cm, the torpedo 1.27 m more, to see whether mapping finds the props.

Physics: the model the MPC flies

The simulator advances in fixed 2 ms ticks. Each tick runs in the same order (session.cpp):

  1. Take any new commands from ROS (thrust, kill, actuators).
  2. Plant: thrusters, then one RK4 step of the 6-DOF body, then contacts with the pool and course.
  3. Mechanisms, payloads in flight, prop physics (the table objects).
  4. Tasks watch the robot and the payloads and report events.
  5. Sensors that are due take a sample; the bridge publishes them, /clock and the TF.

The body is a Fossen model (The Fossen model): rigid-body and added mass, Coriolis, linear and quadratic drag, and buoyancy from an ellipsoid, so it changes as Talos breaks the surface. Its class, MarineDynamics, is the same code riptide_mpc carries a copy of (marine_dynamics.hpp; apart from comments the equations are identical). Both came from the old simulator.

Which model the MPC gets

The MPC needs its own model of the vehicle. In simulation you choose how good that model is with mpc_model:

mpc_modelThe MPC's modelUse it to
empty (default)riptide_mpc's models/talos.yaml, the estimate of the real TalosFly with model error, as on the robot. The real model has been re-fitted since 2026-10-03, so it no longer matches the plant.
simWritten for this run from the plant by mpc_sim_model.pyRemove model error: test trees, perception and paths without fighting the controller

With mpc_model:=sim the launch writes vehicle.yaml, hydrodynamics.yaml and mpc.yaml into <run>.mpc/. It also sets the MPC's DVL latency to 0, because the simulator stamps each reading when it is taken.

Mechanisms and props

  • Torpedoes: two finned projectiles that turn under drag and buoyancy. A 0.047 J spring launches them at about 2.5 m/s plus Talos's own speed. A miss is removed after 30 s.
  • Droppers: two markers released nose-down, same spring. Torpedoes and droppers share a 0.5 s cooldown.
  • Claw: two jaws, 0 to 14 cm gap, 3.3 cm/s each, 12 N hold. Grasps are real contacts: the table's objects are rigid bodies in a Bullet physics world (prop_world.cpp), so a bad grip slips.
  • Magnet: passive. The course judges whether its tip dwells near a magnet light.
  • Safety: Talos starts killed. While killed, thruster commands become zero and the mechanisms disarm; arming is refused.

Sensors and their noise

Each sensor in robot.yaml is sampled from the true motion at its mount point, then noise is added. The noise levels were measured in the 2026-10-03 pool bags. The Navigation sensors chapter covers the real ones.

SensorRateNoise (1σ, per sample)
IMU (VN-100)400 Hzaccel 0.035 m/s², gyro 0.0009 rad/s, attitude 0.0002 rad
FOG500 Hzyaw rate 0.0011 rad/s
DVL8 Hz6 mm/s (x, y), 3 mm/s (z)
Depth20 Hz0.7 mm

These are idealised on purpose. The models are white noise only, with no bias or drift, although the sensor library can add both. The DVL never loses bottom lock and has no range output, and depth is the robot's height, not a pressure. Every reading is reproducible from the scenario's seed.

Cameras, depth and point clouds

Both ZED X Minis are simulated as stereo cameras at the real calibration: 1920 × 1200, 15 Hz, the rectified intrinsics and baselines (49.8 and 50.3 mm). Each frame is rendered offscreen with OpenGL through EGL, so no window is needed. The water colour, absorption and scattering come from the pool pack.

  • Colour is published as JPEG (quality 93) on the same topics as the ZED wrapper, so the detector reads it unchanged.
  • Depth is the true distance from the render, then degraded on the CPU with a stereo-style noise model (below).
  • Point clouds come from the noisy depth and colour, every 8th pixel, on every 3rd frame (5 Hz).
  • Only when wanted. The bridge checks for subscribers every 500 ms and renders a camera output only while someone listens (always_cameras:=true renders everything).

Tasks and scoring

The course pack turns the RoboSub rules into geometry. Each task file has props (what you can hit or grab), regions (judged volumes) and events:

  • a gate or slalom row is a portal: crossing it from one side to the other is a pass;
  • the torpedo board is a perforated panel: each torpedo is a hit on a hole, or a miss;
  • bins are open crates that catch markers; baskets catch the table's objects;
  • magnet lights fire when the magnet tip dwells close enough; the octagon reports surfacing and facing.

The ROS bridge

The bridge is the ROS node /talos/physics_simulator. Its pack, bridge.yaml, lists every topic as a stream: direction, ROS type, the simulator value it carries and how each message field is filled. Any message type in your sourced workspace works, so adding a topic needs no C++.

A few entries matter more than the rest:

  • Thrust in. thruster_forces (8 floats, newtons) is mapped onto the thrusters in the order VUS VUP HUS HUP HLS HLP VLS VLP. A message of the wrong length or with a NaN is dropped whole.
  • Kill. Only command/software_kill messages with kill_switch_id 1 count (the viewer's slot). The simulator then publishes state/kill, as the firmware would. There is no heartbeat timeout in the simulator, unlike the real firmware (Commanding Talos).
  • Firmware stand-ins. Thruster telemetry is published at 2 Hz with every ESC "ready", only so controller_overseer doesn't time out. Actuator status and command replies copy the firmware's messages.
  • Truth beside the estimate. The simulator publishes its true pose as its own TF branch, world → simulator/talos/base_link (100 Hz), plus simulator/ground_truth. It never publishes talos/base_link, odom or map; those belong to the EKF and mapping, as on the robot. So the viewer can draw both, and you can compare them (frames).
  • Moving the robot by hand. set_sim_pose, sync_sim_to_estimate and three resets (reset_sim_to_start, simulator/reset_tasks, simulator/reset_scenario). After a reset or placement the bridge calls the EKF's set_pose so the estimate jumps with the truth. It never does this during a run.

Sim time

The simulator owns time. It publishes /clock on every 2 ms tick, starting at the wall-clock time (so ROS time is never 0) and never going backwards, even across resets. Every stack node runs with use_sim_time: true. In the media run the detector was the exception (use_sim_time false); its annotated images carry a zero timestamp.

Real-time factor. The node parameter real_time_factor (default 1) sets the speed. The loop owes the simulator wall time × factor and pays it back in ticks. If it falls behind, it catches up at most 20 ticks at a time, then drops the backlog and logs falling behind wall time. The viewer's Simulation window sets it from 0 (pause) to 10×.

  • On a loaded desktop in the media run, an average tick took 1.73 ms of its 2 ms budget, and the run went at about 0.95× real time.
  • Faster than real time only helps if the stack keeps up. The MPC must still solve in its 50 ms of sim time; when the machine is busy it logs MPC solve … exceeds the control period.
  • Pausing (factor 0) stops ticks and /clock. The stack freezes with it.

Running it

Build Nereus once (README: ./setup.sh, then ./build.sh with ROS and the workspace sourced; Setting up your machine). Then, with a Zenoh router running:

ros2 run rmw_zenoh_cpp rmw_zenohd
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim

That one launch (sim.launch.py) resolves the scenario, starts the simulator under sim_supervisor.py, brings up the UWRT stack exactly as on the robot but with hardware:=none (plus the AprilTag detector), and opens the viewer. Talos starts killed: press Enable in the viewer, then drive it or run a tree (The Nereus viewer).

ArgumentDoes
active_control_model:=mpcRun riptide_mpc (anything else: the legacy controller)
mpc_model:=simGive the MPC this run's exact plant (above); empty = the real-vehicle model
pool:=rpacThe RPAC dive well instead of the RoboSub pool
scenario:=<folder>Any scenario pack, such as a moved course (not with pool:=)
mpc_odom_topic:=simulator/ground_truthFeed the MPC the truth instead of its estimator: rules out estimation
stack:=false · viewer:=falseLeave out the robot stack or the viewer
cameras:=falseNo rendering: much lighter, but no detections
close_with_viewer:=falseKeep the sim and stack running if the viewer closes
rmw:=rmw_zenoh_cppSet the RMW for every process (default: your shell's)

Why Zenoh. UWRT runs rmw_zenoh_cpp on the robot too. With FastDDS the simulator's /tf stalled for 0.4 to 0.9 s under full load with camera traffic; Zenoh delivered the same run without stalls (comment in sim.launch.py).

Run records. Each run writes to /tmp/nereus_sim/<timestamp>/: resolved.json (exactly what ran), execution.json, summary.json (messages published per stream, camera frames dropped, tick timing) and tasks.json (every task event and the score). Switching pools in the viewer (File → Switch pool) restarts only the simulator, into <run>-2, -3…; the stack keeps running.

Gotchas
  • Two simulations on one computer. Give each its own ROS_DOMAIN_ID. Even then, two doTasks clash: each opens the Groot monitor ports 1666/1667, even with enable_zmq false, and the second fails every tree with "Address already in use". Restart your doTask once the other is gone.
  • Nothing moves. Talos is killed until you press Enable, and a tree waits for the kill switch.
  • Slow machine. Watch for falling behind wall time. Try cameras:=false if you don't need detections, or close other GPU jobs.

Synthetic training data

Nereus can also render labelled images straight from the course, with no simulation running, for training the detector (Training the detector). Images come through Talos's own camera models, and every pixel is labelled exactly because the renderer knows which part of which prop it drew.

  • The course pack names the pieces of the artwork (parts.yaml: the fire icon, a ring, a red pole).
  • The team's label pack maps parts to classes, in the same class order as the deployed models: 11 forward classes, 8 down.
  • A dataset spec says how many images of each task, where the camera may be, and how to vary the water and light. nereus-dataset generate plans, renders and exports YOLO segmentation labels.

On 2026-10-19 this made 10,250 forward-camera and 7,350 down-camera images, at about 30 images a second with 4 workers on an RTX 3090. A third were drawn in a "RPAC look" pool (RoboSub geometry with RPAC water and indoor light). Magnet lights were always red, because green lights, even unlabelled, would teach the model the wrong thing.

Hardware in the loop

In hardware-in-the-loop (HIL) testing, the simulator runs on a desk computer while the robot's own computer runs the stack, so you test the real Orin, its build and its load. The team's HIL launch file, simulation_hil.launch.py, was written for the old simulator. It shrinks the camera images to half size by default, because full-size raw depth (about 9 MB a frame) saturates gigabit Ethernet. Nereus has no HIL launch file yet. The pieces exist (stack:=false on the desk computer, the stack on the Orin, one Zenoh network), but this setup has not been tried with Nereus.

Tests

Nereus has about 400 C++ tests and over 200 Python tests. The C++ ones run with ctest --test-dir build/ros-viewer -j2, the Python ones with uv run pytest tests/python -q. Tests never read the live robot configs; they use frozen copies, so a pack edit can't silently change what they check.

What the simulator can't tell you

  • No acoustics. There is no pinger, so the random-pinger step can't run.
  • Clean sensors. No biases, drift, dropouts or DVL lock loss. The DVL reading is stamped when taken; the real one arrives about 125 ms old (Navigation sensors).
  • Clean depth. Detections scatter far less than on the robot (One mission in Nereus).
  • A model of Talos, not Talos. Controller gains tuned here don't carry over to the pool. Tune them in the water (System identification).
  • No failures. Leaks, brownouts, CAN errors, a stuck ESC: none of it is simulated (Debugging).

Use the simulator for logic: trees, mapping, paths, launch files, the operator's workflow. Use the pool for anything physical.

Before Nereus

From 2021 the team simulated Talos with riptide_simulator: c_simulator for physics and tasks, camera_faker for images, with RViz as the GUI. In September 2026 a plan to make it reusable became a fresh project instead. Nereus started on 2026-09-24 and replaced it within weeks: packs instead of hard-coded robots, a viewer that also drives the real robot, and datasets. The old simulator's dynamics live on twice: as the MPC's copy of MarineDynamics (its parity test compares the two) and as the recordings Nereus's reference tests check against.
