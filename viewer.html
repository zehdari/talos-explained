Running Talos · Chapter 3

The Nereus viewer

One program on the operator's laptop shows Talos in 3D, enables and kills it, drives it, starts its trees and shows what its cameras see. It works the same against the simulator and against the real robot in the pool.

The short version
  • nereus-viewer is the team's operator interface for sim and pool alike. It replaced RViz.
  • Its Enable / KILL button owns software-kill slot 1. It starts killed, and Enable latches, so a run survives the tether coming off. KILL before you close it.
  • Panels around a 3D pool view drive Talos, run trees, control mapping and show the cameras.
  • It talks to Talos only through ROS 2, over Zenoh from the laptop.
  • Ctrl+P finds every control and takes typed moves like turn left 45 forward 2. Enable and KILL are never on the keyboard.

What it is

Nereus (osu-uwrt/nereus) is nereus-sim, the simulator (Chapter 2), and nereus-viewer, this chapter. The two share no code and only talk ROS 2, so the viewer can't tell a simulated Talos from the real one, apart from a few sim-only tools.

Runs on
The operator laptop (op-top at the pool) or any team laptop with the workspace built. Never on the Orin.
Built with
C++, OpenGL and Dear ImGui; ./build.sh in the Nereus repo (README).
Configured in
talos_uwrt_panels.yaml (panels, topics) and talos_uwrt_host.yaml (window, overlays).
Manual

Why not RViz?

  • The viewer took over the old riptide_rviz jobs: the kill switch on slot 1, the electrical panel, bag presets, and the mapping meshes from riptide_rviz/config/markers.yaml.
  • It adds what RViz couldn't do: one window for sim and robot, simulator truth beside the estimate, run scoring, and the prior map editor.
  • Don't run the old RViz control panel next to it: two senders on slot 1 count as competing operators.

A tour of the window

Every window can be moved, docked or closed, but everyone starts from the Standard layout below. Step through it, or tap a number.

Enable and KILL

The POAC board's firmware decides whether Talos may run, from four kill-switch slots (full rules): it is killed if any slot asserts a kill, or if a slot that promised heartbeats goes quiet for 500 ms (kill_switch.c). Slot 0 is the physical switch. Slot 1 is the viewer's.

  • It starts killed. From its first tick it sends a KillSwitchReport on command/software_kill every 50 ms: slot 1, asserting kill unless enabled (report()). Opening a viewer kills a running robot.
  • Enable latches. The report has switch_needs_update = false, so slot 1 stays clear if the viewer closes or the tether comes off. Untethered, the physical switch is the only kill.
  • One operator per slot. Each viewer signs its reports viewer_<host>_<pid>_<n>. If anyone else reports on slot 1, it drops its enable ("Another operator owns the enable switch") and refuses Enable until that sender has been quiet for 1 s. The board itself only lets whoever last killed a slot re-enable it, so the newest viewer to assert wins the slot (ros.c).
  • KILL asserts slot 1, sends the controller a DISABLED command at the last commanded pose, and stops a running tree (composition.cpp).
  • It never kills on its own. A window frozen for 0.75 s, a pose stale for 1 s or a mode request hung for 3 s only releases manual control: Talos holds its last command (releaseLocked).
  • Never from the keyboard. Enable and KILL are only buttons: not in Ctrl+P, no shortcut.
At the pool
  • Enabled with the switch in means the thrusters can spin. Whoever holds the physical switch watches the robot, not the screen (kill switch rules).
  • KILL only works while its messages reach the robot. Untethered or with the link down, pull the switch.
  • One viewer at a time: a second one fights the first for slot 1.
  • Press KILL before you close the viewer or hand the laptop over. A closed viewer leaves slot 1 enabled, so only the physical switch can stop Talos, and opening a viewer again kills it at once.

Driving with the Motion panel

Every Motion command is a pair of ControllerCommand messages on controller/linear and controller/angular: the same topics a tree uses.

Frames. Targets are typed and shown in the map frame, the prior map's frame, so prop coordinates work as typed. The panel converts them and sends them in world (command_frame in talos_uwrt_panels.yaml), which is the same as odom, the frame the MPC flies in (ControllerCommand). After a Calibrate moves map, a held target stays put in world and its map numbers change (ros_runtime.cpp).

  1. Enable, from the panel or the command bar.
  2. Pick Position (it calls controller_overseer's setTeleop first). Leave Feedforward alone: with both halves in FEEDFORWARD the MPC skips optimisation and splits the fixed controller/FF_body_force wrench straight onto the thrusters (mpc.cpp).
  3. Give a target, in one of four ways:
    • Type a Target and press Command (Current copies the actual pose in first).
    • Drag the pose gizmo: arrows move, rings turn, Esc mid-drag puts it back.
    • Dive in place: hold x, y and heading, level, at dive_z = −0.75 m. Zero roll & pitch levels Talos where it is.
    • Drive with keys: W/S, A/D, Space/Shift, Q/E, one step per press: 25 cm or 15° to start, 5 cm / 2° to 1 m / 45° with [ ].

The table reads Actual (from TF), Commanded, Error and Target. During a tree, Commanded follows the tree's setpoints, so the gizmo shows where autonomy is taking Talos.

Typed moves

The fastest way to move Talos is Ctrl+P and a sentence: forward 2, turn right 45, go 15.5 2.8 -1.4 0, or several in a row. Moves start from the pose last commanded, not from where Talos is, so they add up while it's still travelling. They only send when Command would: enabled, Position control, a fresh pose, no tree or other operator driving.

Running a tree

The Autonomy panel is a client of doTask, riptide_autonomy's tree runner (Running a tree):

  • The picker lists the XML trees from autonomy/list_trees. Refresh after you add one.
  • Start sends an ExecuteTree goal on autonomy/run_tree, only once Motion is enabled with a fresh pose and no competing operator (mayStart).
  • While it runs, Motion locks and the execution stack (autonomy/tree_stack) lists the running nodes, outermost first. Trees started from a terminal show up too.
  • Stop or KILL cancels it. Manual control comes back only when you send a command.
  • Untethered, a tree's result never arrives; the panel settles the goal from the action's status once the link is back.

The competition tree first polls state/kill until Talos is enabled, then waits 6 s more (Commanding Talos). In sim, Enable plays the switch going in.

Seeing what Talos sees

Camera cards

One card each for the forward (ffc) and downward (dfc) ZED X Mini, showing the rate actually arriving.

  • RGB / Depth: the compressed rectified image, <cam>/zed_node/rgb/image_rect_color/compressed, or depth. These are the heaviest thing on the tether: close a card if the link struggles.
  • Truth / ROS (sim only): Truth is the viewer's own noiseless render; ROS is what the stack receives. Judge the detector on ROS.
  • Main view looks through that camera in the pool view, overlays and all.

Overlays in the pool view

TF
Axes for every frame; its arrow opens the frame tree to show or hide each one.
MPC path
controller/mpc/predicted_path, 30 stages × 50 ms = 1.5 s ahead, plus any follow_path plan (Control, Chapter 4).
Covariance
Each prop's estimate as a 1–3 σ ellipsoid from mapping/<object> (Perception, Chapter 6). Often too small to see.
Thrust
Each thruster's commanded force (thruster_forces) as a red arrow, 0.05 m per newton.
Vision panel
Detection markers, and ticks for the YOLO and ZED point clouds. A cloud is only subscribed while ticked: they're heavy over the tether.

Mapping and the prior map

The Mapping panel controls riptide_mapping2 (The course map):

  • Tag calibration: hold Talos still facing the AprilTag board and press Calibrate. chameleon_tf's world_to_map takes one sample a second of the tag's pose, 10 in all; if their spread is under stddev_threshold 0.5 it moves map to their average, otherwise it refuses (mapping.launch.py).
  • Mapping target: which prop mapping fuses now. Empty means automatic: in each batch of detections it fuses whichever prop was seen nearest the camera (beyond 1 m). Setting a target makes mapping re-check that prop: it keeps its position, but needs a few fresh detections that agree before it counts as confirmed again (mapping.py).
  • Lock map ignores every detection, freezing all estimates. Target and lock go to the mapping_target service (What gets fused).
  • Reset mapping throws the estimates away and starts again from the prior.

Edit map (Ctrl+M) opens the prior map editor on riptide_mapping's config.yaml:

  • Move props in 2D or 3D, type poses, re-parent. A running simulator pauses while you edit.
  • Save writes only the changed values; comments and order stay. It edits this laptop's copy: the robot sees it only after you deploy and restart mapping, and the team only once you commit it.
  • The Sim course layer moves the simulator's props instead, to test a tree against a course that doesn't match the prior.

Recording, Bagging, Electrical, Actuators

The tabs under the camera cards are for the real robot. In sim most of their services are missing, and the panels say so.

Recording
SVO recording on the robot, one file per camera (the ZED driver's start_svo_rec / stop_svo_rec), and Capture image. A red REC chip shows while it records.
Bagging
ros2 bag record on the robot over SSH (prefilled ros@orin2, ~/bags) or on this laptop; a robot bag keeps going if the link drops. Pick All topics and, usually, a Leave out regex such as image|point_cloud (the field starts empty, so camera images are recorded unless you add it), or tick topics and save a preset (Recording bags).
Electrical
Power cycling (asks first), LEDs, IMU magnetometer calibration, Tare gyro, the pinger and IVC.
Actuators
Arm first; the POAC board refuses while Talos is killed. Open claw and Close claw publish command/actuator/claw, which no POAC build takes, so they only act in sim. Stop claw sends claw_move_s = 0: on the poac-multiple-servos firmware that is an integer divide by zero, so don't press it on the robot (Testing on the bench; panel config).

Tools that only exist in sim

Simulation
Speed up to 10× (real_time_factor), Pause. Sync sim moves the simulated Talos to where the EKF thinks it is; Reset sim puts it back at the start.
Run tracking
The RoboSub 2026 scorecard: Start run (resets the props), a sim-time clock, task status and events. Pinger points can't score: Nereus has no pinger.
Display, Scene
What this view draws (water, walls, the mapping estimate as a ghost course, the EKF estimate as a ghost robot) and how. None of it changes what the cameras see.
View › Pool
Restarts the simulator in another pool (RoboSub 2026 or the RPAC dive well); the stack keeps running.

Layouts, search and shortcuts

  • Layouts: Standard, Wide view and Camera wall on Ctrl+Shift+1/2/3. Save current as keeps your own; Lock layout stops accidental drags during a run.
  • Pin to toolbar: right-click any button or checkbox in any window. The pinned copy works with its window closed.
  • Plots and Topics (Windows menu): live plots of any topic field, and a topic browser (Plotting live).
  • Themes: Heat sheet (default, light, for a sunny deck), its night twin Timing board, and ten more.
  • Follow: Ctrl+F. The run video also turns the camera with Talos's heading (View › Turn with the vehicle), a local change not yet on Nereus's main branch.

At the pool and in sim

Same binary, different launch file. sim.launch.py starts the simulator, the whole stack and the viewer. robot.launch.py starts only the viewer, which loads the scenario pack itself. In sim, start a Zenoh router first (Running Nereus).

ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim
source ~/osu-uwrt/release/scripts/dds_scripts/config_rmw.bash
ros2 launch nereus robot.launch.py pool:=rpac

How it connects

The viewer is four ROS nodes on the laptop: /nereus_viewer (scene, cameras, overlays), /nereus_viewer_timing (receives TF on its own thread, ros_side.cpp), /talos/viewer_panels (every panel) and /talos/viewer_plots. Only Bagging logs into the robot (SSH); everything else is ordinary ROS traffic.

  • Over Zenoh. The Orin runs the router; a laptop that has sourced config_rmw.bash joins as a client at tcp/orin2:7447 (zenoh_session.json5), with the robot workspace sourced for riptide_msgs2 (ROS 2 over Zenoh).
  • Names are relative to /talos: command/software_kill is /talos/command/software_kill.
  • Nothing hidden. Anything the viewer does, a terminal can do with the same topic or service. That's how the pre-test tool holds a bench kill on slot 3.
