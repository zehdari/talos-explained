Behaviour trees

Every Talos mission is a behaviour tree: an XML file of small nodes that a C++ library walks through every 30 ms. Learn how one walk goes and you can read any of the team's trees.

The short version
  • A tree is XML. doTask, the autonomy program that runs trees, ticks the tree's root about every 30 ms until it returns SUCCESS or FAILURE.
  • Each tick, every node it reaches answers SUCCESS, FAILURE or RUNNING. Leaves act or check; Sequence, Fallback and decorators decide what runs next.
  • Nodes share data on a blackboard. A subtree gets its own, and values reach it only through named keys.
  • Anything slow (a path, a service call) is an async action. It starts on one tick, returns RUNNING, and checks its ROS reply on later ticks. Halting it tells the node to stop: FollowPath cancels its MPC goal.
  • The team wrote missions as state machines (SMACH in 2017, then FlexBE: planned in 2019, adopted in 2021) until 2022, then switched to BehaviorTree.CPP v3.

Missions live in riptide_autonomy and run on BehaviorTree.CPP version 3 (read the 3.8 docs; version 4 differs). Trees are edited in the team's Groot fork (Chapter 4).

A whole real subtree, WaitForKillSwitch, the first thing the competition mission runs (messages shortened):

<BehaviorTree ID="WaitForKillSwitch">
  <Sequence>
    <!-- LEDs solid red -->
    <Action ID="SetStatus" status="waiting"/>
    <Action ID="Info" message="Waiting..."/>
    <Action ID="Wait" seconds="5"/>
    <!-- try forever -->
    <RetryUntilSuccessful num_attempts="-1">
      <Sequence>
        <!-- read state/kill once -->
        <Action ID="GetBoolTopic" topic="state/kill"
                value="{kill_switch_inserted}"/>
        <!-- go on only if it is false -->
        <Inverter name="IsFalse">
          <Condition ID="IsTrue" value="{kill_switch_inserted}"/>
        </Inverter>
        <Action ID="Wait" seconds="1"/>
        <Action ID="Info" message="INSERTED..."/>
      </Sequence>
    </RetryUntilSuccessful>
    <!-- LEDs blink blue -->
    <Action ID="SetStatus" status="starting"/>
    <Action ID="Wait" seconds="5"/>
  </Sequence>
</BehaviorTree>

Read it top to bottom: show red, wait 5 s, keep reading state/kill until it says false, then blink blue and wait 5 s more. state/kill is true while the robot is killed (despite the key's name), so the Inverter waits for false.

Ticks and statuses

A tick is one function call on the root, which ticks a child, which ticks one of its children, and so on down. Every node it reaches returns one of three statuses:

  • SUCCESS: done, it worked.
  • FAILURE: done, it didn't (or the answer to a check is no).
  • RUNNING: not finished, tick me again.

A fourth state, IDLE, means "not started". A parent that no longer needs a RUNNING child halts it, back to IDLE. A tick must be quick: a node that waits returns RUNNING and checks again next tick.

The figure below ticks WaitForKillSwitch. Three rules are enough to follow it: a Sequence ticks its children in order and stops at the first that fails or is still RUNNING; RetryUntilSuccessful ticks its child again when it fails; an Inverter swaps SUCCESS and FAILURE.

Statuses travel up: a leaf answers, and each parent turns its children's answers into its own. The thing that calls tick on the root again and again is doTask:

  • Who starts a tree: the Nereus viewer's autonomy panel, through autonomy/run_tree. It also shows the node stack from autonomy/tree_stack.
  • Logs: every run writes ~/btlogs/BTLog_<date>.fbl for Groot to replay. Live streaming to Groot (ZMQ) is off.
  • Stopping: apart from a node throwing an error (abort, LEDs flash red), only a cancel (the viewer's Stop) ends a tree early. Pulling the kill switch does not (Chapter 2).

Sequence, Fallback and friends

Control nodes have children and decide which to tick. Three cover most of every tree:

  • Sequence ("do all of these"): ticks children in order, and stops at the first one that fails or is RUNNING, returning the same. SUCCESS when all succeed.
  • Fallback ("try until one works"): ticks children in order until one succeeds. FAILURE only when all fail.
  • IfThenElse ("if, then, else"): ticks the first child; if it succeeds, the second, otherwise the third. Talos uses it 55 times, mostly to pick numbers (SearchMpc picks its sweep size with one).

A real example, AssertTree: pass the check, or else print why and fail.

<Fallback>
  <Condition ID="CompareNums" a="{a}" b="{b}" test="{test}"/>
  <ForceFailure>
    <Action ID="Info" message="Assertion {aname} ({a} {test} {b}) failed"/>
  </ForceFailure>
</Fallback>

The detail that matters most:

  • A plain Sequence remembers its RUNNING child and goes straight back to it next tick, without re-checking the children before it.
  • A ReactiveSequence starts from the first child on every tick, and halts the running child if an earlier one now fails. Conditions first, long action last: the action stops the moment a condition changes.

Decorators

A decorator has exactly one child and changes how it runs or what it returns.

  • ForceSuccess is everywhere: "try this, but failing is fine". CompMissionTreeMpc wraps each task in one, so a failed task moves the run on to the next (Chapter 3).
  • RetryUntilSuccessful and Repeat loop inside one tick while the child finishes at once; a RUNNING child makes them carry on next tick.
  • The team's RetryUntilSuccessfulOrTimeout re-ticks its child once per tick until it succeeds or num_seconds have passed.
Worth knowing

When its time runs out, RetryUntilSuccessfulOrTimeout returns FAILURE without halting a child that is still RUNNING (the library's Timeout would). If SearchMpc's 100 s run out mid-sweep, nobody cancels the FollowPath goal: the MPC flies on until the path ends, stalls or is preempted. The simulator marks such a node "left running".

The blackboard and ports

The blackboard is a key-value store shared by the nodes of one tree. Nodes reach it through ports, the named inputs and outputs each node type declares in C++:

  • seconds="5" is a literal; seconds="{hold_secs}" reads the key hold_secs.
  • An output port names the key to write: out="stage" and out="{stage}" both write stage.
  • SetBlackboard writes a value to a key (561 of them in the competition file).

Three Talos conventions sit on top of the library:

  • Every port is a string, converted only when read (autonomy_lib.hpp): "abc" throws and aborts the tree, while "1.5m" quietly reads as 1.5.
  • Empty means default: Groot saves unset ports as "", and the nodes read that as "use my default".
  • {key} inside text (message="error {cov}, target: {target_cov}") is filled in by Talos's formatStringWithBlackboard in Info, Error, Format and FollowPath, not by the library.

Subtrees and remapping

Any <BehaviorTree ID="..."> can be called from another as <SubTree ID="..."/>; Move is called 33 times. Each tree file carries its own copy of the shared subtrees (87 in RepairCompMpcTree.xml) and runs the one named by main_tree_to_execute.

  • Own blackboard. Every call either sets __shared_blackboard="false" or leaves it out (the same thing: isolated is v3's default), so the subtree gets a fresh blackboard.
  • Remapping. Each other attribute maps one key: port="key" means "when the subtree uses port, use my key key".
  • Always a key, never a value. In v3 the right-hand side is always a key name, so to pass a number the caller first writes it to a key named after the number.

The main tree passes repair_mission = 1 like this:

<BehaviorTree ID="BehaviorTree">
  <Sequence name="MISSION">
    <!-- key "1" now holds "1" -->
    <SetBlackboard output_key="1" value="1"/>
    <Action ID="Info" message="MISSION: REPAIR"/>
    <!-- repair_mission reads my key "1" -->
    <SubTree ID="CompMissionTreeMpc"
             __shared_blackboard="false"
             repair_mission="1"/>
  </Sequence>
</BehaviorTree>

Forget the SetBlackboard and the port is silently empty inside the subtree. It happens for real: FireTorpedo calls WaitForActuators with timeout_secs="10" but never writes a key "10", so the wait's timeout reads as 0. The wait fails at once with a false "Actuators busy!" error, and "Torpedo fired!" never prints; a ForceSuccess named REMOVE ME hides the failure (Chapter 3; pick it in the explorer below). Likewise the port defaults in the file's TreeNodesModel only document the subtree for Groot; v3 never applies them.

Actions that take time: talking to ROS

Talos has two kinds of action node:

  • Quick ones (Info, Math, Format, AddWaypoint...) are UWRTSimpleActionNode, a SyncActionNode that runs one function and returns SUCCESS or FAILURE in the same tick (simple_nodes.hpp, SimpleActions.simple.cpp).
  • Slow ones (FollowPath, Wait, the service and topic nodes) derive from UWRTActionNode, the library's StatefulActionNode plus a ROS node handle (UwrtBtNode.hpp). They have three callbacks:
onStart()
The first tick. Read the ports, send the request, return RUNNING (or finish at once).
onRunning()
Every later tick. Check the reply without waiting; return RUNNING, SUCCESS or FAILURE.
onHalted()
Called if a parent halts it while RUNNING. FollowPath cancels its goal here. Most service and topic nodes leave it empty, so their request just goes unanswered.

Two ROS words first. An action server takes a long job (a goal), reports progress, returns a result, and can be told to cancel. A future is a handle to a reply that hasn't arrived yet: you check it later.

FollowPath sends a path to the MPC's follow_path action server. Cut down to the parts that matter here:

BT::NodeStatus onStart() override {
    startTime = now();  timeout = input("timeout", 60);
    // parse the waypoint string
    return RUNNING;
}
BT::NodeStatus onRunning() override {
    if (now() - startTime > timeout) { cancel(); return FAILURE; }
    // send the goal (once the TF frames resolve)
    if (!goalFuture.valid()) {
        goalFuture = client->async_send_goal(goal);
        return RUNNING;
    }
    if (!goalHandle) {
        // poll, never block
        if (goalFuture.wait_for(0s) != ready) return RUNNING;
        goalHandle = goalFuture.get();
        // rejected
        if (!goalHandle) return FAILURE;
        resultFuture = client->async_get_result(goalHandle);
    }
    if (resultFuture.wait_for(0s) != ready) return RUNNING;
    return resultFuture.get().code == SUCCEEDED ? SUCCESS : FAILURE;
}
// a parent halted it: async_cancel_goal
void onHalted() override { cancel(); }

Every step checks a future with wait_for(0s), which returns at once whether or not the reply is there. Service nodes such as CallTriggerService work the same way. The replies are received on another thread (the tree ticks on its own thread while main handles ROS callbacks, DoTask.cpp). A tick that blocked waiting for one would freeze the whole tree: a ReactiveSequence above could not re-check its conditions or halt the action.

Conditions answer at once from data a subscription already cached: SeenRecently only compares the time a class was last seen with the clock, so it is safe to re-check every tick. Chapter 2 goes through the nodes one by one.

Tick it yourself

Now all of it at once. This runs the real SearchMpc subtree with BehaviorTree.CPP v3's rules. The torpedo task uses it to fly arcs round where the map thinks the board is until the camera sees it, chase the detection, then hold still until the map is sure.

You play the ROS side: the switches are the detector and the map, the buttons are the MPC. The inputs are remapped in from TorpedoTreeMpc: max_dist 2 m, min_dist 1 m, timeout_secs 100 s, and target_cov 0.0025, the map's covariance error in m² (about (5 cm)²: it knows the board's position to a few centimetres).

Things to try:

  1. Step a few times. The first tick runs the bookkeeping nodes straight through, then stops at SetMappingTarget, which waits for a service reply. A few ticks later FollowPath is flying.
  2. Turn Torpedo in view on and step once. The ReactiveSequence re-checks SeenRecently, its Inverter fails, and FollowPath is halted (its goal is cancelled). The chase starts on the same tick.
  3. Reset, switch to plain Sequence and do the same: nothing happens until the path ends, because a Sequence goes straight back to its RUNNING child.
  4. In the chase, press Centred, then turn Map converged on and use Skip: the hold ends, getCovariance reads the map, and SearchMpc succeeds.

Why trees, not state machines

The team has written mission code in three systems, as its technical design reports (TDRs) show:

In the tree, the same logic comes from the structure:

  • Reacting: "stop sweeping when it's seen" is a condition in front of the action in a ReactiveSequence.
  • Limits: the time limit is one decorator round the whole thing.
  • Reuse: a subtree doesn't know who called it or what comes next, so Move can be called from 33 places.
  • Failure stays local: ForceSuccess and Fallback decide what a failure means where it happens.

The cost: arrows become decorators and blackboard flags. "Sweep wider" is a retry decorator plus the stage key, and you need the tick rules to see the loop.
