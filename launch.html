Running Talos · Chapter 1

Launching the stack

27 processes make Talos work, and nobody starts them by hand. On the robot a web page on the Orin starts them from a list; in the simulator one command starts everything. This chapter shows what starts, in what order, and why.

The short version
  • On the Orin, the ros_launcher service serves a page at http://orin2:8080. You load a list (a YAML file) and press Start on each entry. Each entry is one ROS 2 launch file.
  • The pool list, talos_launch_mpc.yaml, has seven entries in use, 27 processes: board link and sensor drivers, the EKF, both cameras, the detector, mapping, the behaviour trees and the MPC.
  • In Nereus, ros2 launch nereus sim.launch.py starts the simulator, the same launch files with the simulator standing in for hardware, and the viewer.
  • Nothing enforces the order. Follow the start order: control_system last, with Talos killed. Never press Start on control_system at the bench: an enabled robot would spin its thrusters.
  • Node output appears on the launcher page; journalctl -u ros_launcher only holds the launcher's own messages.

Four ways to start Talos

The same launch files run in every setup. What changes is which list is loaded and who stands in for the hardware.

Why a web page and not ros2 launch over SSH? The README gives the reasons: it starts the vehicle "without the need for an active SSH connection", and it lets GUIs control each subsystem.

  • No laptop has to stay connected. The nodes are children of a system service, not of anyone's terminal.
  • Each piece is separate. Any browser or script can start, stop and watch one entry without touching the others.
  • Nothing gets lost. The service keeps track of every process it started (below).

Every process, from the real files

The explorer below was made by running each list and launch file through the ROS 2 launch library itself, the same code ros2 launch uses, without starting anything (tools/launch/build_tree.py). Includes, conditions, namespaces and arguments resolve exactly as they would on the Orin. A launch file is a Python script that lists nodes and includes other launch files; ROS 2, the Talos way explains one. A container is one process that loads several nodes, called components, so they share memory: both ZED cameras run in one, and it counts as one process.

The pool list: two things the explorer doesn't show

Every entry passes robot:=talos. Most launch files default it to tempest, an older robot, and nodes started without it land under /tempest/ and talk to nobody.

The list order is not the start order. talos_launch_mpc.yaml has nine entries, and control_system is fourth in the file; the start order puts it last. The page shows the entries in file order, so read the explorer's numbers, not the page's rows.

The pool and bench lists also keep a commented-out copro_agent entry: the micro-ROS agent now comes with hardware, which includes copro_agent.launch.py itself.

Why the order matters

Most ROS nodes simply wait for their inputs, so a wrong order rarely crashes anything. It matters for three reasons:

  • The page waits for topics. An entry shows Running only after every topic in its list has published once. Start navigation before hardware and it sits at 2/4 completed: no sensors, so no odometry/filtered and no depth/pose (screenshot below; what to check).
  • The boards need the agent. Until the micro-ROS agent in hardware runs, the boards can't reach ROS at all: no kill state, no depth, no thruster telemetry (Firmware on the boards).
  • The controller acts. Started last with Talos killed, it has its inputs and does nothing until someone enables. Killed, or without fresh odometry, the MPC publishes zero thrust (mpc_controller_node.cpp).

The order follows the data. A script assigned every node in the Nereus graph capture to the entry that starts it on the robot and collected what crosses between entries:

The start order

  1. hardware (hardware_fake_dvl on the bench)
  2. navigation, riptide_hardware2's
  3. zed
  4. tensorrt
  5. mapping
  6. autonomy
  7. control_system: last, at the pool only, with Talos killed and the viewer up

The pool test uses this order, and pretest_checks starts the bench entries (1 to 6) in it.

The controller rule
  • Never press Start on control_system at the bench. With the controller up, the thrusters spin as soon as the robot is enabled: the MPC writes RPM to the ESCs over CAN itself. pretest_checks warns if it is running on the bench; its controller check (B8) starts it only while holding a software kill, then stops it.
  • At the pool, start it last, with Talos killed (physical kill switch out), and only after the viewer is up: the viewer keeps a kill asserted until someone presses Enable (The kill system).
  • Stopping navigation while the controller runs cuts its odometry: the MPC logs No fresh odometry; thrusters off and stops thrusting, wherever Talos is.

The remote launcher, inside

remote_launch is one Python file, launcher.py, run as a systemd service by ros_launcher.service as user ros. The service sources ~/colcon_deploy/install/setup.bash and the Zenoh settings, then runs launcher --systemd --start-discovery-server. Step through what happens when you press Start:

Port
8080 (env SERVER_PORT): http://orin2:8080, or http://192.168.1.24:8080 on the robot LAN if your laptop can't resolve orin2 (Computers and networks). Page at /, websocket at /ws. No login: anyone who can reach the port can start and stop launches.
Zenoh router
Started first, after killing any old router. launcher.py's default is rmw_zenohd with zenoh_router_test.json5 (L29), but the service first sources zenoh_server.bash, which can override it through DISCOVERY_SERVER_CMD: the committed version runs plain rmw_zenohd, no config file. Which one runs depends on the Orin's copy of that script. If it dies, the launcher stops everything and exits.
Restarts
Restart=always after 500 ms; systemd gives up after 5 restarts in 15 s.
Stopping
SIGINT to each launch's process group; systemd allows 15 s, then SIGKILL.
Status
Broadcast to every page at least every 1.5 s, and on every change.
Lists
Read from share/remote_launch/launches/ of the deployed install. Edit them in riptide_launch and deploy (colcon deploy).
  • After a boot no list is loaded. The first page to connect sends the list its browser used last, and the launcher loads it.
  • Loading a different list marks every entry of the old one abandoned and stops the ones running.

An entry's states

Running means "each topic was seen once", not "healthy now". A node that crashes later and is respawned by launch (the micro-ROS agent, DVL, IMU, acoustics, both mapping nodes and the actuator translator have respawn=True) never changes the state; a node that crashes without respawn only shows in its log.

The other buttons

  • Log (per entry) and Log by Default choose which entries' output this browser receives.
  • Shut Down Launcher stops every launch cleanly and exits. As a service it comes straight back, so the button reads Restart Launcher there.
  • Force Reset (service only) exits at once without cleanup; systemd then kills every leftover process in the service and restarts it. Its confirm box warns that it kills all running nodes without cleanup: the last resort.

Adding your node to a list

A list is a YAML file with one key, launches, holding the entries. This is the hardware entry of the pool list (talos_launch_mpc.yaml L1-18):

launches: [
  {
    package: "riptide_hardware2",
    file: "hardware.launch.py",
    args: [
      "robot:=talos",
      "imu_port:=/dev/ttyTHS1",
      "imu_frame_id:=talos/imu_link",
      "gyro_port:=/dev/ttyTHS2"
    ],
    topics: [
      "/talos/dvl/status", "nortek_dvl_msgs/msg/DvlStatus", "0",
      "/talos/vectornav/imu", "sensor_msgs/msg/Imu", "0",
      ...
    ]
  },
package, file
The launch file, looked up in share/<package>/launch/ of the deployed install. The page names the entry after the file, minus .launch.py.
args
Launch arguments, as on the ros2 launch command line (launcher.py L409-411). Always include robot:=talos.
topics
What the page waits for before showing Running, three items per topic: full name, type, and a QoS flag, "0" for the default or "1" for sensor data. Use "1" for a best-effort publisher, or the entry never reaches Running. An empty list means Running at once.
The exact rules

The name is the full name from / (letters, digits, underscores); the type is package/msg/Name (launcher.py L286-304). Flag "1" subscribes with sensor-data QoS (L1179); a reliable subscriber never receives a best-effort topic. A bad name, type or flag, or a count that isn't a multiple of three, stops the list loading at that entry.

To get a new launch file started on the robot:

  1. Add the launch file to your package and install it to share/<package>/launch/ (in its CMakeLists.txt or setup.py). Check it with ros2 launch <package> <file> robot:=talos on your laptop.
  2. Add an entry to the pool list, talos_launch_mpc.yaml, and the bench list, talos_launch_bench_mpc.yaml (and the HIL list if it should run there), with robot:=talos and one or two of its output topics to watch. Put it where it belongs in the start order.
  3. Deploy both your package and riptide_launch (colcon deploy). The lists are read from the installed remote_launch package, not from your checkout (launcher.py L689-691).
  4. Reload the list on the page. Choosing the list that's already loaded does nothing (L726-727): load another list and then yours, or use Restart Launcher. Either stops everything running. A brand-new list file only shows in the menu after a restart, because the folder is read once at start-up.

The simulator doesn't read the lists. sim.launch.py starts the stack through riptide_bringup2's bringup.launch.py, which includes the same launch files from its own list of add_launch_file calls. A node added to an existing launch file (say mapping.launch.py) runs in both; a new launch file needs an add_launch_file there too to run in Nereus.

Driving the launcher from a script

The page is one client of a small JSON protocol over the websocket at /ws. pretest_checks and any script can drive the launcher the same way.

  • pretest_checks (Pool test day) has its own client. Its bench stage fails unless talos_launch_bench_mpc.yaml is loaded, starts any stopped bench entries in order, and warns if control_system is running.
  • The Nereus viewer doesn't talk to the launcher. It is an ordinary ROS client: it sees whatever the launched nodes publish. Its Bagging panel does borrow the launcher's setup: it runs ros2 bag record on the Orin over SSH after sourcing the same files as the service, so the recorder joins the running stack.
Protocol reference, and a Python client

Each command is a JSON object with a cmd field plus the fields listed:

connect
First message, always. Fields logging_enable_default and, optionally, last_launchfile. Answer: first_connect with the list files, systemd_mode, the status and this client's log_enrollment.
load_launch
file: load a list (stops everything running).
start_launch, stop_launch
id: start or stop one entry.
set_logenable, set_logdefault
enable (and id for one entry): receive one entry's output, or every entry's. Answer: log_enrollment.
stop_server, kill_server_now
The two shutdown buttons.

The server pushes status (the list, every entry's id, state, monitored topics and process tree), log lines and error, and sends log_enrollment in answer to the two log commands. Every message has a type field. Entry ids are fresh random UUIDs every time a list loads, so look them up by package and file each time. A complete client (tested against launcher.py):

import asyncio, json, websockets   # websockets is what the launcher itself uses

async def main():
    async with websockets.connect("ws://orin2:8080/ws") as ws:
        await ws.send(json.dumps({"cmd": "connect", "logging_enable_default": False}))
        status = json.loads(await ws.recv())["status"]   # the first_connect message
        print(status["current_launchfile"], status["discovery_status"])
        for l in status["launches"]:
            print(f'{l["package"]}/{l["file"]}: {l["state"]}')
        # to start one: {"cmd": "start_launch", "id": l["id"]}

asyncio.run(main())

In the simulator: sim.launch.py

On a laptop there is no launcher. With a Zenoh router running (Nereus: running it):

ros2 launch nereus sim.launch.py \
  active_control_model:=mpc \
  mpc_model:=sim
  • Always pass active_control_model:=mpc. Without it, bringup uses its default, hybrid (bringup.launch.py), and control_system starts the legacy complete_controller, not the MPC. A plain ros2 launch nereus sim.launch.py does that.
  • mpc_model:=sim gives the MPC this run's exact plant: a perfect-model baseline (mpc_controller.launch.py). Leave it out to use config/models/talos.yaml, the same estimate of the vehicle as on the robot; the simulator keeps its own plant, so the two differ, as they do in the pool.

sim.launch.py starts three things, all under one ros2 launch:

  1. The simulator, as sim_supervisor.py running nereus-sim, so the viewer can switch pools without restarting the stack.
  2. The stack, through mission_stack.launch.py: riptide_bringup2's bringup.launch.py with hardware:=none, plus the AprilTag detector. Every node runs on sim time except the YOLO detector, which stays on wall time (tensorrt.launch.py).
  3. The viewer. Closing it ends the whole launch, unless close_with_viewer:=false.

bringup.launch.py includes the same files as the pool list (control_system, navigation, tensorrt, mapping, autonomy) but, with hardware:=none, swaps hardware for acoustics alone and has no zed: the simulator publishes the sensor topics and camera images. (hardware:=real or fake would start the whole robot stack as one launch, but on the robot the team uses the launcher's separate entries.) The launch's first lines say which branches it took (full log):

MPC model: this run's plant (/tmp/nmedia/run/sim.mpc)
Launching with NO hardware                       # bringup.launch.py
I'm running on a development laptop              # control_system.launch.py
zed_wrapper not found. Launching without zed TF  # navigation.launch.py
...
[mpc_controller-5] ... Hardware output disabled (the model has no hardware section); publishing thruster_forces only

Each line comes from the launch file named beside it. Compared with the robot:

  • 18 processes in that run. The explorer's Simulation tab marks two more, navigation's camera-frame publishers, which only start when zed_wrapper is installed.
  • Acoustics runs as /riptide_acoustics, without the robot namespace that hardware.launch.py pushes.
  • control_system checks for /home/ros/colcon_deploy to decide it's on the Orin.

Hardware in the loop

In hardware-in-the-loop (HIL) testing the Orin runs the stack while a desk computer simulates the world, so you test the real computer, its build and its load. talos_launch_sim_hil_mpc.yaml (added in October 2026, "nereus provides the sim and viewer") is the pool list without hardware, zed and diagnostics. On the desk computer, sim.launch.py stack:=false starts just the simulator and the viewer. Both sides must share one Zenoh network.

  • Camera traffic crosses the network. The detector on the Orin subscribes to the simulator's images, including the depth image. The old simulator's HIL launch halved camera resolution because full-size raw depth, about 9 MB a frame, saturates gigabit Ethernet (simulation_hil.launch.py). sim.launch.py has no such option.
  • No AprilTag detector, acoustics or board link. All three live in hardware.launch.py, which the HIL list drops, and stack:=false also skips mission_stack, which adds the detector in pure simulation. Tag calibration and pinger tasks don't work in HIL, and with no micro-ROS agent the boards get no ROS messages at all.
  • The older talos_launch_sim_hil.yaml ran the old simulator (c_simulator) and RViz on the Orin with the legacy controller. Both are replaced.
HIL and the thrusters

The MPC sends RPM to the ESCs over CAN whenever it runs on wall time, can0 exists and its model has a hardware section (configureHardwareOutput). The HIL list doesn't change any of that, so on Talos's Orin the MPC logs Hardware output ENABLED and sends the simulated run's RPM commands to the real ESCs over CAN. If the ESC boards are powered and not killed, the thrusters can spin. Keep the physical kill switch out for the whole session. HIL with Nereus hasn't been confirmed end to end yet.

Logs: the page, the journal and the disk

A launched node has no terminal. Its output goes to the launcher, which forwards each line to the pages that asked for it and then drops it (launcher.py). It is never written to the journal.

  • Watching a start-up: the launcher page's Launch Log.
  • "Why did everything stop?": the journal, which holds the launcher's own lines and the Zenoh router's crash output.
  • After the fact: each node's ROS log file under ~/.ros/log/ on the Orin, and /rosout live (Debugging: where the logs are).
# follow
journalctl -u ros_launcher -f -o cat
journalctl -u ros_launcher \
  --since "10 min ago"
# list loaded, launches active
systemctl status ros_launcher

What the journal holds, from the desk run above:

[remote_launch] Loading launch definition 'talos_launch_mpc.yaml'
[remote_launch.navigation] Launch Starting
[remote_launch.mapping] Launch Starting
[remote_launch.navigation] Launch Stopping...
[Launch Monitor-1444434] Interrupted before all topics seen
Traceback (most recent call last):
  ...
rclpy._rclpy_pybind11.RCLError: failed to shutdown: rcl_shutdown already called on the given context
[remote_launch.navigation] Launch Cleaned Up

The traceback is harmless: it appears whenever an entry is stopped before all its topics were seen, because the monitor shuts ROS down twice. Launch died is the line to look for: an entry's launch exited by itself.

Running one piece by hand

Any entry is an ordinary launch file, so you can run it on your laptop (sourced release workspace, Setting up your machine) against the simulator or a bag:

ros2 launch riptide_mapping2 \
  mapping.launch.py robot:=talos
ros2 launch riptide_controllers2 \
  control_system.launch.py \
  robot:=talos active_control_model:=mpc
# the viewer against the real robot
ros2 launch nereus robot.launch.py \
  pool:=rpac
  • Don't run a second copy of a node that's already running on the robot or in the sim: two MPCs or two EKFs publish on the same topics. Stop it in the launcher (or give your sim its own ROS_DOMAIN_ID) first.
  • Launch arguments are listed with ros2 launch <package> <file> --show-args.
  • To change what the robot starts, edit the list or the launch file in its repo, merge it, and deploy. Don't edit files on the Orin.
