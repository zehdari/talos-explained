Running Talos · Chapter 2

Nereus, the simulator

A pool, a course and a Talos that exist only in software, close enough that the robot's own code runs on it unchanged. Where you test a tree, a controller change or a new detector before anyone gets wet.

The short version
  • Nereus plays the hardware: it publishes Talos's sensor and camera topics, takes the controller's thruster forces and moves a simulated Talos. The robot stack runs unchanged.
  • Nothing about Talos is in the code: the robot, pool, course and ROS wiring are YAML packs, merged into one resolved.json per run.
  • The physics is the MPC's own Fossen model with the numbers from the 2026-10-03 pool fit, and the sensor noise comes from real pool bags. Cameras are rendered on the GPU, with depth and point clouds.
  • Start the Zenoh router, then one launch file starts the simulator, Talos's stack and the viewer (Running it).
  • It also renders labelled training images for YOLO. It doesn't simulate acoustics, sensor failures or a real pool's mess, so the pool still has the last word.

What Nereus is

Nereus is the team's simulator and operator interface, in three parts:

  • nereus-sim: C++ physics, sensors, cameras, mechanisms, props, scoring and a ROS 2 bridge.
  • nereus-viewer: the 3D pool and operator panels. It also drives the real robot, so it has its own chapter (The Nereus viewer).
  • Packs: YAML in content/packs/ describing the robot, pool, course and ROS topics.

The simulator and the viewer are separate programs that talk to the robot stack only through ROS 2 topics; both read the same resolved.json. That is the whole design: if the stack sees the same topics, types, frames and timing as on Talos, it behaves the same way. The robot stack runs as on Talos, minus the hardware drivers (hardware:=none), on the simulator's clock.

Running it

Build once (README: ./setup.sh, then ./build.sh with ROS and the workspace sourced; Setting up your machine). That registers a nereus ROS package (source build/ros-viewer/ros/setup.bash, or let ./setup.sh add it to ~/.bashrc). Then start the Zenoh router and the launch file:

ros2 run rmw_zenoh_cpp rmw_zenohd
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
ros2 launch nereus sim.launch.py \
    active_control_model:=mpc mpc_model:=sim

sim.launch.py resolves the scenario, starts the simulator, brings up the UWRT stack as on the robot with hardware:=none (plus the AprilTag detector), and opens the viewer. Talos starts killed: press Enable, then drive it or run a tree (The Nereus viewer).

active_control_model:=mpc
Run riptide_mpc. Leave it out and you get the legacy controller (the default is hybrid, control_system.launch.py).
mpc_model:=sim
Give the MPC the exact plant (below).
pool:=rpac
The RPAC dive well instead of the RoboSub pool.
scenario:=<folder>
Any scenario pack, such as a moved course (not with pool:=).
mpc_odom_topic:=simulator/ground_truth
Feed the MPC the true pose: rules out estimation.
stack:=false · viewer:=false
Leave out the robot stack or the viewer.
cameras:=false
No rendering: much lighter, but no detections.
rmw:=rmw_zenoh_cpp
Set the RMW for every process (default: your shell's).
  • Why Zenoh. The robot runs rmw_zenoh_cpp too, and with FastDDS the simulator's /tf stalled for 0.4 to 0.9 s under full camera load (sim.launch.py).
  • Run records go to /tmp/nereus_sim/<timestamp>/: resolved.json (exactly what ran), summary.json (messages per stream, dropped frames, tick timing) and tasks.json (events and score).
Gotchas
  • Nothing moves. Talos is killed until you press Enable, and a tree waits for the kill switch.
  • Slow machine. Watch for falling behind wall time; try cameras:=false or close other GPU jobs.
  • Two simulations on one computer. Give each its own ROS_DOMAIN_ID. Even then both doTasks open the Groot ports 1666/1667, and the second fails every tree with "Address already in use".

Everything is a pack

A pack is a folder of YAML (usually one file; the course has one per task) plus its meshes. Every number about Talos, the pool or the course lives in one, so a new course is an edit, not a rebuild.

PackSays
robots/talosMass, drag, thrusters, sensors, cameras, mechanisms, frames
pools/…Size, floor shape, lane lines, water colour, lighting
tasks/robosub_2026The props, what counts as an event, how points are scored
bridges/uwrt_talosWhich ROS topics and services, with which types and fields
equipment/uwrtTeam gear at the pool: the AprilTag board
scenarios/…Picks one of each and places everything

Before a run, nereus-packs resolve checks every pack against a JSON schema, cross-checks them (does the bridge name real sensors? does the robot have a claw for the table?) and writes resolved.json. Errors name the file and the key. sim.launch.py runs the same tool (as python -m nereus.packs), so you rarely call it yourself.

Check a pack after editing, with the same tool, from the nereus folder:

uv run nereus-packs validate content/packs/scenarios/talos_uwrt
Gotcha: pack paths are relative

A scenario names its packs by paths relative to the scenario file (robot: ../../robots/talos); the schema rejects absolute ones. Copy a scenario elsewhere and you must fix them.

The course and scenarios

The scenario is the file you edit most. It places the pool, the AprilTag board and each task, and sets the robot's start, the random seed and the 2 ms physics step. Its world is the robot's map frame: the task poses in talos_uwrt are copied from riptide_mapping's prior map, so the simulated course and the robot's map start out agreeing (the map).

  • talos_uwrt (the default, pool:=robosub): the RoboSub 2026 pool, 50 × 22.86 m and 2.13 m deep.
  • talos_uwrt_rpac (pool:=rpac): Ohio State's RPAC dive well, 25.23 × 17.07 m, 5.18 m deep with a sloped floor. The board hangs on the deep-end wall and the world is placed from the tag, as the stack does it: move the board and the map and course follow.
  • A moved course. Real props are never exactly where the prior map says. Move tasks in the simulator but not the map: edit task_placements in a copy of a scenario, or use the viewer's Edit map → Sim course. One mission in Nereus moves the course 72 cm, the torpedo 1.27 m more.

Physics: the MPC's own model

The simulator advances in fixed 2 ms ticks, each in the same order (session.cpp):

  1. Take new commands from ROS (thrust, kill, actuators).
  2. Plant: thrusters, one RK4 step of the 6-DOF body, contacts. Every sensor that is due takes a sample.
  3. Mechanisms, payloads in flight, prop physics (the table objects).
  4. Tasks watch the robot and payloads and report events.
  5. The bridge publishes what is due: sensors, /clock, TF, simulator state.

The body is a Fossen model: rigid-body and added mass, Coriolis, linear and quadratic drag, and buoyancy from an ellipsoid, so it changes as Talos breaks the surface. Its class, MarineDynamics, has the same equations as riptide_mpc's copy (marine_dynamics.hpp).

Which model the MPC gets

The MPC predicts with its own model of the vehicle. In simulation, mpc_model picks how good it is:

mpc_model empty (the default)

riptide_mpc's talos.yaml, the estimate of the real Talos. It was re-fitted after 2026-10-03 (surge drag 224 against the plant's 124, for one), so the MPC flies with model error, as on the robot.

mpc_model:=sim

The plant itself, written into <run>.mpc/ by mpc_sim_model.py. No model error: test trees, perception and paths without fighting the controller.

Mechanisms and props

  • Torpedoes and droppers: two finned torpedoes flying under drag and buoyancy, launched by a 0.047 J spring at about 2.5 m/s plus Talos's speed, and two markers, pushed out nose-down by the same 0.047 J spring. All four share one 0.5 s cooldown.
  • Claw: two jaws, 1 mm to 14 cm gap, 3.3 cm/s each, 12 N hold. The table's objects are rigid bodies in a Bullet world (prop_world.cpp), so a bad grip slips.
  • Magnet: passive; the course judges whether its tip dwells near a magnet light.
  • Safety: Talos starts killed. While killed, thrust is zero, the mechanisms disarm and arming is refused.

Sensors and their noise

Each sensor in robot.yaml samples the true motion at its mount, plus noise measured in the 2026-10-03 pool bags (the real sensors: Navigation sensors).

SensorRateNoise (1σ, per sample)
IMU (VN-100)400 Hzaccel 0.035 m/s², gyro 0.0009 rad/s, attitude 0.0002 rad
FOG500 Hzyaw rate 0.0011 rad/s
DVL8 Hz6 mm/s (x, y), 3 mm/s (z)
Depth20 Hz0.7 mm

Idealised on purpose: white noise only, no bias or drift (the sensor library can add both). The DVL never loses bottom lock and has no range output. Depth is base_link's true z in the world, not a pressure reading. Every reading is reproducible from the scenario's seed.

Cameras, depth and point clouds

Both ZED X Minis are simulated as stereo cameras at the real calibration: 1920 × 1200, 15 Hz, the rectified intrinsics and baselines (49.8 and 50.3 mm). Frames are rendered offscreen (OpenGL through EGL, no window), with the pool pack's water colour, absorption and scattering.

  • Colour: JPEG (quality 93) on the ZED wrapper's topics, so the detector reads it unchanged.
  • Depth: the true depth from the render, degraded on the CPU like stereo depth (depth_noise.cpp): the error grows with range squared, half of it is shared across 8-pixel patches so surfaces look wavy rather than speckled, some pixels have no depth, and 0.2 % are outliers, off by up to 25 %.
  • Point clouds: from the noisy depth and colour, every 8th pixel, every 3rd frame (5 Hz).
  • Only when wanted: the bridge checks for subscribers every 500 ms and renders an output only while someone listens (always_cameras:=true renders all).

Tasks and scoring

The course pack turns the RoboSub rules into geometry. Each task file has props (things to hit or grab), regions (judged volumes) and events:

  • a gate or slalom row is a portal: crossing it is a pass;
  • the torpedo board is a perforated panel: a hit on a hole, or a miss;
  • bins and baskets are open crates that catch markers and objects;
  • magnet lights fire when the magnet tip dwells close; the octagon reports surfacing.

Points come from a C++ rules class (robosub_2026) with every value in tasks.yaml. Scoring waits for Start run in the viewer's scorecard.

The ROS bridge

The bridge is the ROS node /talos/physics_simulator. Its pack, bridge.yaml, lists each topic as a stream: direction, ROS type, the simulator value it carries and how each field is filled. Any message type in your sourced workspace works, so a new topic needs no C++.

  • Thrust in. thruster_forces: 8 floats in newtons, in the order VUS VUP HUS HUP HLS HLP VLS VLP. A wrong length or a NaN drops the whole message.
  • Kill. Only kill_switch_id 1 (the viewer's slot) counts, and unlike the firmware there is no heartbeat timeout (Commanding Talos).
  • Truth beside the estimate. The true pose is its own TF branch, world → simulator/talos/base_link. The simulator never publishes talos/base_link, odom or map; those belong to the EKF and mapping, as on the robot (frames). At startup, after set_sim_pose or Sync sim, and after a robot or full reset, the bridge calls /talos/set_pose so the estimate jumps to the truth.

Sim time

The simulator owns time. It publishes /clock every 2 ms tick, starting at the wall-clock time (so ROS time is never 0) and never going backwards, even across resets. Every stack node runs on /clock except the YOLO detector: tensorrt.launch.py leaves its use_sim_time false, so its annotated image stream carries a zero timestamp.

Real-time factor. real_time_factor (default 1; the viewer's Simulation window sets 0 to 10×) is how much sim time the loop owes per second of wall time, paid back in ticks. Falling behind, it catches up at most 20 ticks at a time, then drops the backlog and logs falling behind wall time. Faster only helps if the stack keeps up: the MPC must still solve within 50 ms of sim time, or it logs MPC solve … exceeds the control period. Factor 0 stops ticks and /clock, and the stack freezes with it.

Synthetic training data

Nereus also renders labelled images straight from the course, with no simulation running, to train the detector (Training the detector). They come through Talos's camera models, and every pixel is labelled exactly: the renderer knows which part of which prop it drew.

  • The course pack names the pieces of the artwork (parts.yaml: the fire icon, a ring, a red pole).
  • The label pack maps parts to classes in the deployed models' order: 11 forward, 8 down.
  • A dataset spec sets images per task, camera placement, water and light. nereus-dataset generate plans, renders and exports YOLO segmentation labels.

On 2026-10-19 this made 10,250 forward and 7,350 down-camera images, about 30 a second with 4 workers on an RTX 3090; a third in an "RPAC look" pool (RoboSub geometry, RPAC water and light). Magnet lights were always red: green ones, even unlabelled, would teach the model the wrong thing. The larger specs and the RPAC-look pool aren't in the repository yet; the pack explorer shows the smaller committed specs.

The code and its tests

About 400 C++ tests (ctest --test-dir build/ros-viewer -LE live -j2) and over 200 Python tests (uv run pytest tests/python -q). They check values against frozen copies of the resolved scenarios and only check that the live packs are valid (CONTRIBUTING.md), so retuning Talos or moving the course never breaks a test. The key one, TalosReference, steps the Talos plant through scripted thrust and compares 27 state values per tick with the old simulator's recordings.

What the simulator can't tell you

  • No acoustics. There is no pinger, so the random-pinger step can't run.
  • Clean sensors. No biases, drift, dropouts or DVL lock loss. The DVL reading is stamped when taken; the real one arrives about 125 ms old (Navigation sensors).
  • Clean depth. Detections scatter far less than on the robot (One mission in Nereus).
  • A model of Talos, not Talos. Controller gains tuned here don't carry over to the pool. Tune them in the water (System identification).
  • No failures. Leaks, brownouts, CAN errors, a stuck ESC: none of it is simulated (Debugging).
  • Not the Orin's load. Hardware in the loop runs the stack on the Orin against Nereus on a desk computer (sim.launch.py stack:=false). It isn't confirmed end to end yet and the MPC still writes RPM to the real ESCs, so keep the kill switch out (Launching the stack).

Use the simulator for logic: trees, mapping, paths, launch files, the operator's workflow. Use the pool for anything physical.

Before Nereus

The team used to simulate Talos with riptide_simulator (c_simulator and camera_faker). On 2026-09-24 a plan chose "a complete refactor in a new folder"; Nereus started that day and replaced it within weeks. Its dynamics live on in the MPC's MarineDynamics (parity test) and in the recordings behind Nereus's reference tests.
