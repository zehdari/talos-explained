Talos's tree nodes

Talos's trees are built from 44 custom nodes written in C++, on top of the built-in ones. This chapter lists them all: what each does, its ports, and which part of the robot it talks to.

The short version
  • Apart from SetBlackboard and AlwaysSuccess/AlwaysFailure, every leaf in a Talos tree is one of 44 nodes from riptide_autonomy: 35 C++ classes, one header each, and 9 one-function "simple" actions.
  • Ports are plain strings. An unset or empty port uses the node's default (required ports log a warning).
  • Nodes open their ROS topics and services when the tree is loaded. The competition tree builds 5,822 custom node instances, which open 646 subscriptions before the first tick.
  • Talos moves through the MPC: FollowPath for paths, PublishToController for single setpoints.
  • doTask runs one tree file per ExecuteTree goal and ticks it every 30 ms. When the tree ends, it disables the controller and sets the LEDs.

Chapter 1 covered behaviour trees in general. BehaviorTree.CPP (BT.CPP, version 3, the one ROS 2 Humble ships) provides the control nodes: Sequence, Fallback, ForceSuccess, SetBlackboard, and ReactiveSequence, a sequence that re-checks its earlier children on every tick. Everything that touches the robot is a custom node in riptide_autonomy (branch autonomy-mapping). The numbers on this page come from that source and from the competition tree, RepairCompMpcTree.xml (walked through in Chapter 3), read by this site's script.

Four kinds of node

Each custom node inherits from a BT.CPP base class and from UwrtBtNode, which gives it the ROS node and a TF helper.

KindHow it runsCount
Stateful action · 28UWRTActionNodeonStart on the first tick, then onRunning every tick while RUNNING, onHalted if a parent stops it.28
Simple action · 9UWRTSimpleActionNodeOne function, finished in one tick. All nine live in SimpleActions.simple.cpp.9
Condition · 6UWRTConditionNodetick answers SUCCESS or FAILURE at once.6
Decorator · 1UWRTDecoratorNodeWraps one child and decides what its result means.1

Why stateful actions? doTask ticks the whole tree from one thread. A node that blocked (waiting for a service reply, say) would freeze every other node, including the conditions guarding it. So a slow node starts its work in onStart, returns RUNNING, and checks for the result on each later tick.

The service nodes break this rule a little: each waits up to 1 s in onStart for its service to appear (wait_for_service(1s)), and the whole tree waits with it. With mapping or the detector down, or a mistyped srv_name, every such call costs a frozen second and then fails.

Ports and the blackboard

The port rules (every port is a string, {key} reads the blackboard, empty means default, subtree ports name a key) are in Chapter 4. Two more matter for reading the catalogue:

  • Defaults live in the code, not the XML. Each is the last argument of tryGetRequiredInput or tryGetOptionalInput, and the catalogue lists them. Only the required form logs a warning when the port is empty ("does not have a value for required port"); both carry on with the default.
  • Some nodes fill {key} inside a longer string. Info, Error, Format and FollowPath replace each {key} in their text with the blackboard value, so "at {x}, {y}" works there and nowhere else.

Talking to ROS

  • rosInit runs when the tree is loaded. doTask calls initRosForTree, which hands every node the ROS node and calls its rosInit. Publishers and subscriptions made there last the whole run. A node whose topic comes from a port makes them in onStart instead.
  • One ROS node for all of them. Every tree node uses doTask's node, /talos/autonomy. Relative names resolve under /talos: controller/linear is /talos/controller/linear. Log lines from Info appear under talos.autonomy.
  • One TF buffer (the store of recent transforms every lookup reads). UwrtBtNode::lookupTransform returns the latest transform and warns at most once a second while it can't.

Loading is not free. BT.CPP builds every subtree again wherever it is used, so the competition tree becomes 11,993 nodes, 5,822 of them custom, before it starts. Each one runs its rosInit:

Most of these sit idle: 486 GetOdometry subscriptions all receive every odometry message for the whole run. The README notes that this load makes a real bug worse: Humble's multi-threaded executor can starve service replies under steady subscription traffic, so doTask now spins a single-threaded executor and ticks the tree on its own thread.

How a node gets registered

BT.CPP's factory turns an XML ID such as FollowPath into a C++ object. Its list is generated, not written by hand: when CMake configures, generateRegistrators.py registers every header in bt_actions, bt_conditions and bt_decorators under its file name (the pipeline is in Chapter 4). So a new header needs CMake to configure again (btassistant.py create does it for you), and Groot, the tree editor, only shows a node's ports once a TreeNodesModel declares it (the catalogue notes the nodes its workspace still lacks).

Moving: paths and setpoints

The MPC takes two kinds of command (Control, Chapter 4):

  • A path: FollowPath sends one follow_path goal. Talos flies through every waypoint without stopping and settles on the last. The newer subtrees (names ending in Mpc) mostly move this way.
  • A setpoint, one target pose (or velocity) for the MPC to reach and hold, sent as a ControllerCommand on controller/linear or controller/angular. PublishToController, CenterDetection and ContinuousSpin send these. The MPC holds a setpoint until the next one.

Any setpoint ends a running path, so a PublishToController in parallel with a FollowPath stops the path. The older move subtree, PrimitiveMovePosition, shows the setpoint style. It loops until it arrives or times out: publish the setpoint, Wait 0.25 s, GetOdometry, CalculateDistance, done if under 0.25 m. That loop is why Wait and GetOdometry are among the most-built nodes.

Waypoint strings

FollowPath reads its whole path from one string, waypoints separated by ;. Each is x,y,z,yaw in metres and radians, optionally after a frame name, followed by options after |. The second waypoint of the torpedo search, piece by piece:

torpedo_frame:
The frame the numbers are in: the board's, from mapping.
1.94,0.49,0,0
x, y, z, yaw: 2 m out from the board, 0.25 rad round from its front.
arc=0,0,0.25
Get there along an arc round (0, 0), turning 0.25 rad.
heading=look_at
Face a point instead of the yaw above…
look_at=0,0,0
…the board's centre…
look_frame=torpedo_frame
…given in the board's frame.
yaw_offset=0.5
Then turn 0.5 rad to one side of it: the camera pans.

Before it comes the first waypoint, torpedo_frame: 2,0,0,0: 2 m straight in front of the board, facing it. The figure below shows every line of the string.

Trees rarely write these by hand. AddWaypoint and AddArc append one piece each, so a path is a readable chain of nodes, each passing its out to the next one's path. A waypoint in an object's frame moves with mapping's estimate of that object, even while Talos is on the way.

Perception: search until the map has it

Searches combine three nodes from the catalogue. SeenRecently and MapConverged are conditions that answer at once, so in a ReactiveSequence they are re-checked on every tick and stop the move beneath them the moment either passes. From SearchMpc (empty ports left out):

<ReactiveSequence name="Sweep, panning, until it is seen (or the map has it)">
    <Inverter>
        <Condition ID="SeenRecently" max_age_secs="0.5" min_score="0.2" object_name="{object_name}"/>
    </Inverter>
    <Inverter>
        <Condition ID="MapConverged" object="{object_name}" target_cov="{target_cov}"/>
    </Inverter>
    <Action ID="FollowPath" max_depth="-2.5" min_depth="-0.75" timeout="90" waypoints="{sweep_path}"/>
</ReactiveSequence>

When a condition flips, the ReactiveSequence halts FollowPath, whose onHalted cancels the goal. The search then calls CenterDetection to bring the target into the middle of the image, and holds there (at most 8 s) until MapConverged passes or the target has been out of sight for 2 s. What the covariance thresholds mean is in Perception, Chapter 9; the whole search, stage by stage, is in Chapter 3.

Lining up a tool

To shoot, drop or grab, the tree needs a camera or tool, not the centre of Talos, at a pose relative to a prop. The controller only moves talos/base_link. ComputeFrameAlignment works out where the base must go. With T^{a}_{b} the pose of frame b in frame a:

T^{\text{world}}_{\text{base}} = T^{\text{world}}_{\text{ref}}\; T^{\text{ref}}_{\text{link}}\; T^{\text{link}}_{\text{base}}
  • T^{\text{world}}_{\text{ref}}: the prop's frame in world, from TF (mapping publishes it).
  • T^{\text{ref}}_{\text{link}}: where you want the tool, the node's x, y, z and or, op, oy (roll, pitch, yaw) ports.
  • T^{\text{link}}_{\text{base}}: the base seen from the tool, looked up in TF (the node waits up to 5 s for it). The robot description publishes these frames from talos.yaml (the torpedoes entry, for example).

The competition tree lines up these frames this way: the down camera, the claw, the forward camera, both torpedo tubes, the magnet and the dropper.

Status lights: SetStatus

The LED strips tell swimmers and the surface crew what the tree is doing. SetStatus sends one of ten named patterns on command/led; doTask sets the last one itself when the tree ends.

Where a mission's time goes

doTask publishes the names of the running nodes on autonomy/tree_stack whenever one starts or stops. Mapping each name back to its node type shows which nodes a real run spends its time in.

More than three quarters of the run is FollowPath (39 %) and Wait (39 %): flying, and pausing between polls. SetControllerSafeMode's 10 s is the old flip at the gate, waiting on a parameter the MPC doesn't have (Chapter 3).

doTask: the tree runner

DoTask.cpp is one ROS node, /talos/autonomy, started by autonomy.launch.py. It offers:

autonomy/run_tree
Action, riptide_msgs2/ExecuteTree. Goal: tree, the full path of an XML file. Result: uint32 returncode, BT.CPP's status (2 SUCCESS, 3 FAILURE; 1 when the goal was cancelled), or −1 after an exception, which reads as 4294967295 in a uint32; and bool error, true only for a cancelled goal. Its feedback field (TreeStack stack) is never sent; watch autonomy/tree_stack.
The rest of what doTask offers
autonomy/list_trees
Service: every .xml in the source trees/ folder, the installed copy and any ext_tree_dirs.
autonomy/tree_stack
Topic: the names of the running nodes, root first.
/<host>/autonomy/bag_trigger
Topic, once a second: true while a tree runs. Nothing current reads it.
~/btlogs/
One BTLog_<date>.fbl per run: every status change, for replay in Groot.
Parameters
enable_zmq (live view in Groot over ZeroMQ, a messaging library; false in autonomy.launch.py), log_file_dir (default ~/btlogs), ext_tree_dirs (more folders for list_trees) and ext_plugin_list (more node plugins).

The tree file is read when the goal arrives, so an edited tree in src/riptide_autonomy/trees runs without a rebuild. A new node does need one. You will usually start trees from the Autonomy panel of the Nereus viewer, which lists them, sends the goal and shows the stack. From a terminal (more in Chapter 4):

ros2 service call /talos/autonomy/list_trees riptide_msgs2/srv/ListTrees
# then send one of the paths it printed:
ros2 action send_goal /talos/autonomy/run_tree riptide_msgs2/action/ExecuteTree \
  "{tree: /path/it/printed/RepairCompMpcTree.xml}"

Things to watch

  • The kill switch does not stop the tree. doTask listens to state/kill, but the check that would end the tree is commented out (// || robotKilled). The tree keeps ticking with the thrusters off. To stop a run, cancel the goal (Stop in the viewer).
  • Start one tree at a time. The "already running" check never refuses. A second goal crashes while starting its loggers, and on the way out sends DISABLED to the controller and flashes the LEDs red, while the first tree keeps running. The viewer only offers Start when nothing runs.
  • A failed tree still "succeeds". A tree that ends in FAILURE finishes the action as succeeded: read returncode (2 is SUCCESS). The viewer does, and reports anything else as Tree failed.
  • Error succeeds. Logging an error does not fail anything.
  • The topic readers wait for the next message. GetBoolTopic, GetFloat64Topic, GetTwistTopic and GetImuOrientation subscribe when they start and wait up to 3 s, so a topic that is published rarely, or only on change, makes them fail.
Known bugs
  • A timed-out retry leaves its child running. When RetryUntilSuccessfulOrTimeout runs out of time it returns FAILURE without halting a child that is still RUNNING (read from the code; not yet tested in Nereus). In SearchMpc it wraps the sweep, so a timeout mid-sweep skips FollowPath's onHalted: the MPC keeps flying the sweep until the next setpoint or path.
  • The stack shows that decorator in the wrong place. RetryUntilSuccessfulOrTimeout turns RUNNING only after ticking its child, so on autonomy/tree_stack, and in the viewer's stack readout, its name sits above the child it waits on.
  • ApproxEqualToAngle wraps one way only. A difference below −π isn't wrapped. With a 0.25 rad range, a = 3.1, b = −3.1 passes (the angles are 0.08 rad apart), but a = −3.1, b = 3.1 fails.
  • Names that mislead. PublishInt8 publishes a UInt16. getCovariance's output is a single score built from the covariance diagonal (position variances, plus the angular ones divided by 2π), not a covariance.
  • The old flip still runs at the gate, and leaves the controller disabled for 10 s (Chapter 3).
  • The generic service nodes make a new client on every start (CallTriggerService, CallSetBoolService, CallSetStringService, CallStartBinaryClassifierService).
