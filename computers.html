The vehicle · Chapter 10

Computers and networks

One computer in the hull runs the whole robot. A few machines on the surface watch it, record it and keep its clock right. Which box does what, how they connect, and how your laptop joins in.

The short version
  • Every ROS node of the real robot runs on one Jetson AGX Orin (orin2). A systemd service, ros_launcher, starts the nodes. They run the code that colcon deploy copied to ~/colcon_deploy.
  • The circuit boards hang off a CAN bus, can0. A micro-ROS agent turns their messages into ROS topics, and the MPC writes thruster RPMs straight onto the bus.
  • ROS 2 runs over Zenoh. A router on the Orin listens on TCP port 7447, and laptops connect to it as clients, on the LAN or through Tailscale. Both paths run over the tether.
  • The opbox, a Raspberry Pi in the operator box, gets the robot network onto the internet through campus Wi-Fi. It also serves the time that every clock follows.
  • op-top, the team laptop, is the operator station. It runs the Nereus viewer, deploys code and runs the pre-test checks.

Each machine has one job. The Orin does all the real-time work: sensors, estimation, control, vision, mapping and the mission tree. Everything outside the hull is optional while Talos runs. You can pull the tether and the robot keeps going, which is how competition runs work. This chapter covers each machine, then the links between them, then the commands you'll use to reach them.

The network at a glance

One box holds what is inside the hull, the other the surface. Pick a kind of traffic to see where it flows. Tap any machine for what it runs and where it lives.

The Orin: Talos's only computer

The Orin is an NVIDIA Jetson AGX Orin, bought in 2022 (2026 design report, component table). It's an ARM (aarch64) computer with an NVIDIA GPU, which the YOLO detector and the ZED depth processing use.

The Orin's environment: the service sources ~/uwrt_config/source/zenoh_server.bash. In the repo, that script sources client.bash from uwrt-config (hyphen, not underscore), so what runs depends on what is installed on the Orin. client.bash sets up ROS, the source-built rmw_zenoh_cpp, the ZED wrapper workspace, config_rmw.bash, ~/colcon_deploy and the micro-ROS agent workspace. Interface setup: configure_jetpack.bash. Serial ports: talos_launch_mpc.yaml. Hardware list: the 2026 design report.

Why one computer

  • The loop never leaves the hull. Sensors, the EKF, the 50 ms MPC and the thruster commands all run on one machine with one clock. A dropped tether can't stall control.
  • Competition runs are untethered. Autonomy has to run without any help from the surface, so the surface machines only observe and command.
  • Cameras stay local. Two raw camera streams are far too big for the tether (see below), so the detector runs next to the cameras.

ros_launcher: starting the stack without SSH

Nobody types ros2 launch on the robot. The Orin runs the remote launcher (remote_launch in riptide_launch) as a systemd service, ros_launcher.service. It starts at boot and does four jobs:

  • It starts the Zenoh router. With --start-discovery-server it runs rmw_zenohd, the ROS 2 router that every node and laptop connects to. If the router dies, the launcher shuts itself down and systemd restarts the whole service.
  • It serves a web page and a websocket on port 8080. You can open http://orin2:8080 in a browser. Scripts such as the pre-test checks use the websocket.
  • It loads a launch-file list (a YAML file in remote_launch/launches/) and starts or stops each entry on request. It never starts an entry by itself.
  • It watches. An entry only counts as running once every topic in its list has published. Every child process stays in the service's cgroup, so the page can list orphans: processes that belong to no entry, for example ones that escaped a shutdown. Loading a different list stops the old list's entries; any that haven't exited yet are listed as abandoned.

Each robot mode has its own launch-file list. Three are current for the MPC. Pick one to see its entries in list order, the order you start them in. Tap an entry to see its arguments and the topics the launcher waits for.

Thrusters
  • Starting control_system on an enabled robot spins the thrusters. On the bench, keep the robot killed before you start it, and keep hands clear.
  • Force Reset kills every node without cleanup. Use the normal Stop buttons unless the launcher is stuck.

Inside the launcher (restarts, states, logs, scripting): Launching the stack, The remote launcher, inside. The full launch sequence, with each entry and what it starts, is on the same page.

Getting code onto the Orin: ~/colcon_deploy

~/colcon_deploy isn't a git checkout. Code goes on with colcon deploy, a verb the team added to colcon (colcon_riptide in riptide_setup). colcon deploy orin2 rsyncs package sources to ~/colcon_deploy/src and builds them there (Setting up your machine, colcon deploy).

Why build on the Orin? It's ARM and op-top is x86, so binaries built on op-top won't run on the Orin. Building in place keeps the robot's install matched to its own libraries.

  • Don't edit files on the Orin. No git tracks ~/colcon_deploy, and the next deploy overwrites the change.

CAN: the link to the boards

The circuit boards talk to the Orin only over CAN. Each board has an RP2040 microcontroller, and the boards exchange ROS 2 messages over the team's own CAN protocol (2026 TDR). Every board has its own CAN client ID. The Orin reaches the internal bus as can0 and the external bus as can1.

The firmware runs the internal bus as CAN FD: 1 Mbit/s nominal, 5 Mbit/s for the data phase (talos.h). The Orin setup script only sets the 1 Mbit/s nominal rate (configure_jetpack.bash). Check the live setting with ip -details link show can0.

Two different programs talk on can0:

  • The micro-ROS agent, copro_agent (copro_agent.launch.py). It runs micro_ros_agent can -D can0 -m rmw and is started by hardware.launch.py. Each board runs a micro-ROS client, and the agent bridges its publishers and subscribers into the ROS graph. state/firmware and state/depth/raw, for example, both come in this way. The team wrote the -m rmw middleware so the agent hands messages to whatever RMW the Orin runs, which today is Zenoh.
  • The MPC itself. When hardware output is on, mpc_controller opens a raw CAN socket and sends each ESC board one 8-byte frame every control tick: four signed 16-bit RPMs, big-endian (send_thruster_cmd_canbus.c). Thrusters 0–3 go to client 2 and thrusters 4–7 to client 3. The same numbers are published on command/requested_rpm so you can see them.

The MPC only enables CAN output when all four checks pass (configureHardwareOutput):

  • hardware_output isn't off.
  • The model file has a hardware section (Talos's talos.yaml does).
  • The node isn't running on simulation time (checked in the default auto mode). In the code's words, "a simulator on the vehicle computer never drives the real thrusters".
  • /sys/class/net/can0 exists.

The interface name is fixed: send_thruster_cmd_canbus.c always opens can0 (line 15); the model's can_interface key isn't read.

On your laptop there's no can0, so the same node runs in Nereus and only publishes thruster_forces.

The boards themselves, their firmware and how to talk to one with a USB-CAN adapter are in The circuit boards and Firmware on the boards.

The robot LAN and the tether

Everything with an IP address sits on one wired network, 192.168.1.0/24, behind the team router (192.168.1.1). Inside Talos, the Orin, the DVL and the tether meet at a small network switch in the camera cage (2024 TDR). For pool tests, Talos joins the LAN through an Ethernet tether. For competition runs and some test runs, the tether comes off and Talos is on its own.

router192.168.1.1Gateway for the robot LAN
orin2192.168.1.24Talos's Orin
uwrt-dvl192.168.1.212The DVL (web settings page, TCP data)
opbox192.168.5.69The opbox, on the router's other side (192.168.5.0/24)
  • Names come from /etc/hosts. The launch configs and tools use orin2, so add 192.168.1.24 orin2 to /etc/hosts on your laptop. riptide_setup's setup_hosts.bash still adds an older entry, orin at 192.168.1.23. Talos is orin2.
  • A tether pulls on the robot. Fine for testing, but don't trust physics measured with it on. A tethered identification run fitted the tether's pull as buoyancy (System identification).
  • Losing the tether doesn't stop Talos. The viewer's enable latches, and its watchdogs release manual control but never kill (ros_runtime.cpp). That's what lets untethered runs work.
Kill

With the tether off, or the link down, the only way to stop Talos is the physical kill switch. Software KILL only works while your messages reach the robot. Kill switch slots are explained in Commanding Talos.

ROS 2 over Zenoh

ROS 2 sends messages through a pluggable middleware layer (the RMW). Talos uses rmw_zenoh_cpp. Why (2025 TDR):

  • Fast DDS, the default, was unreliable. The team traced a year of problems to it. Its old discovery-server scripts are still in the release repo as history.
  • Zenoh copes with heavy traffic, discovers peers efficiently and gives more reliable communication between processes.
  • One router, on the Orin. The launcher starts rmw_zenohd, which listens on TCP port 7447. Nodes on the Orin find each other through it.
  • Laptops are clients. A client session opens one TCP connection to the router. Every message to or from your laptop goes over it. The robot never opens a connection to a client; the router only dials the addresses in its own config's connect list.
  • Both ends need the same RMW. A laptop on Fast DDS won't see a single topic. If topics are missing, check echo $RMW_IMPLEMENTATION first.
  • The ros2 daemon caches the old RMW. The team's Zenoh source script runs ros2 daemon stop. Otherwise, add --no-daemon to ros2 topic list.

The release repo picks the RMW per machine. config_rmw.bash reads ~/.uwrt/default_rmw (set it with changermw). For Zenoh it sources zenoh/source_rmw.bash, whose session config is a client of tcp/orin2:7447 (zenoh_session.json5). The same can be done in one environment variable, which is handy over Tailscale (below).

Follow a camera frame to your laptop

Camera images are the biggest thing on the network, and they show every stage of the system. Step through one forward-camera frame, from the sensor to the Nereus viewer on op-top.

The arithmetic is why vision runs on the robot. A raw 1920×1200 BGRA frame is 9.2 MB, or about 1.1 Gbit/s at 15 fps for one camera, more than a gigabit Ethernet link carries. The JPEG is 17 times smaller, about 64 Mbit/s at 15 fps. Two habits follow:

  • Subscribe to /compressed topics from a laptop, never raw images or point clouds. Each client gets its own copy over the tether.
  • Measure topic rates one at a time. Subscribing to several camera streams at once loads the link and skews every rate. The pre-test checks expect at least 8 Hz on each compressed camera topic and 3 Hz on the detector's annotated image.

The opbox

The opbox is the operator box, and inside it is a Raspberry Pi (a Compute Module 4 running Debian 12) with hostname opbox. Its first two jobs are networking:

  • Internet passthrough. The Pi's wlan0 joins campus Wi-Fi. Its eth0 (192.168.5.69) is a NetworkManager shared connection that NATs the router's traffic out over the Wi-Fi. That gives the robot LAN internet access for apt, pip and GitHub without moving any cables.
  • Time server. It runs chrony as the team clock (next section). It has a battery-backed real-time clock, so it keeps time across reboots even with no internet.
Hands off its network settings

Every machine on the LAN reaches the internet through the opbox. Don't change its routing, DNS or Wi-Fi setup without asking whoever looks after it.

Its third job was an operator panel. opbox_software drives a kill button with red, yellow and green LEDs, a buzzer and pop-up alerts. It talks to opbox_ros_client on the robot over UDP port 10510 and opens a diagnostics page in a browser. Read the current code before you rely on any of it:

  • The robot-side code that would publish the button as a kill report is commented out (main.cpp). The opbox button does not kill Talos.
  • Its alerts come from /diagnostics, and the team no longer runs the diagnostics node.
  • opbox_ros_client isn't in any of the launcher's Talos lists.

Time: why every clock has to agree

Every ROS message carries a timestamp from the clock of the machine that made it. Most of Talos's own timing is safe, because the sensors, EKF, MPC and mapping all stamp and compare on the Orin's single clock. The trouble starts when a second machine is involved:

  • Bags. A bag recorded on op-top stores op-top's receive times next to the Orin's header stamps. Merge it with a bag from the robot and it lines up only if the clocks agree.
  • The viewer. Its live plots compare each header stamp with the arrival time, averaged over many messages. If that gap is over 0.5 s they show clock offset, which is really clock offset plus delay (averaging in plots_hub.cpp, the 0.5 s warning in plots_ui.cpp).
  • Jumps. A clock that steps backwards by more than about 10 s during a run makes the Nereus viewer drop TF.
  • No internet at the pool. Without a reachable time server, a machine's clock can drift and nothing corrects it.

Drag the offset below to see what a laptop makes of a message from the robot.

The fix is chrony, with the opbox as the one source everyone follows. The settings live in /etc/chrony/conf.d/opbox-server.conf on the opbox and /etc/chrony/conf.d/opbox.conf on each client. The script that writes the client file isn't in a team repo yet, so check what a machine really follows with chronyc sources on it. The intended setup:

MachineFollowsSteps the clock
opboxInternet pool when online, else its RTC (local stratum 10 orphan)n/a, it's the server
Talos (Orin)The opbox only (server 192.168.5.69 iburst prefer), internet pools commented outmakestep 1 3: only in its first three updates after boot. After that chrony slews (speeds up or slows down) and never jumps under a running stack. Untethered, it free-runs, which is harmless: all of Talos's own timing uses its one clock.
op-topThe opbox, preferred, with the internet pool as fallbackmakestep 1 -1: any time it's more than 1 s off, for example after booting offline

Before chrony, the team set the robot's clock by hand from a laptop. colcon timesync orin2 (timesync.py) SSHes in and runs sudo date --set and hwclock --systohc. It still works as a fallback. The pre-test checks measure the op-top to Orin offset over SSH and warn above 50 ms.

chronyc sources -v     # which servers, which one is selected (*), last offset
chronyc tracking       # how far off this clock is right now

op-top, the operator laptop

op-top is the team laptop (user uwrt, with an RTX 4070 laptop GPU). Anything an operator does goes through it:

  • The Nereus viewer, the operator UI for both the simulator and the real robot. It enables and kills Talos, drives it, starts trees, sets mapping targets, fires actuators and records bags. RViz used to fill this role and isn't used any more. See The Nereus viewer.
  • The Nereus simulator, which needs the GPU to render cameras for the real YOLO detector (Nereus).
  • The release workspace, ~/osu-uwrt/release, built for x86. You deploy from here.
  • The pre-test checks (pretest), which read the robot over SSH, the launcher websocket and ROS (Pool test day).
  • Its keyboard (optop_software). The backlight shows the link at a glance. It pings orin2 every 2 s. Two answered pings in a row turn it bright white, and two missed pings turn it dim white. Once something publishes on command/led, it shows Talos's own LED colour.

Joining from your own laptop

Any Ubuntu 22.04 machine with ROS 2 Humble can join the robot's ROS graph (Setting up your machine). There are two ways to reach the Orin:

  • On the robot LAN, plugged into the team router: use orin2 with the hosts entry above.
  • From anywhere, with Tailscale, the team's private network of encrypted tunnels. It only reaches Talos while the tether is in and the opbox has internet. Ask a team lead to add your machine and for the Orin's tailnet name (not published) to use in place of orin2.
sudo apt install ros-humble-rmw-zenoh-cpp
source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash        # riptide_msgs2 and friends
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
export ZENOH_CONFIG_OVERRIDE='mode="client";connect/endpoints=["tcp/orin2:7447"];scouting/multicast/enabled=false'
ros2 daemon stop
ros2 topic list --no-daemon | head
ros2 topic hz /talos/odometry/filtered
  • Client mode works one way. Your laptop dials the Orin, and nothing on the robot ever has to reach you. Keep it that way: never set anything up that makes the robot open connections to a personal machine. The team's router config also dials 192.168.1.25 (purpose unconfirmed), so don't give a laptop that address.
  • Multicast scouting off. Without it, your laptop won't go hunting for other Zenoh nodes on whatever network you're on.
  • Sim at your desk? Keep it off the robot's graph, or on the robot LAN the sim joins the robot's router and its camera images cross the tether:
    1. No ZENOH_CONFIG_OVERRIDE, and not the team's zenoh_session.json5: both connect to orin2.
    2. unset ZENOH_ROUTER_CONFIG_URI. The team's source_rmw.bash points it at zenoh_router.json5, which connects to 192.168.1.24, the Orin.
    3. Run your own router: ros2 run rmw_zenoh_cpp rmw_zenohd.
    A different ROS_DOMAIN_ID (the planned pre-test sim stage uses 77) is a second guard. ROS_LOCALHOST_ONLY is a DDS setting and does nothing under Zenoh.
  • One operator at a time. Anyone connected can publish. Two viewers enabling on the same kill-switch slot fight each other, and the viewer drops its enable when it sees another publisher there.

SSH, logs and the usual commands

SSH is for looking, not for running the stack. Use key login (the release repo's relationship.bash makes and installs a key). Tools like colcon deploy and the viewer's bag recorder expect it.

ssh ros@orin2
journalctl -u ros_launcher -f -o cat             # the launcher's own messages
journalctl -u ros_launcher --since "10 min ago"  # what just happened
systemctl status ros_launcher                    # is it up, what is it running
sudo systemctl restart ros_launcher              # last resort: stops every node
ip -br link show can0                            # CAN up?
candump can0                                     # raw CAN traffic, needs can-utils (Ctrl-C to stop)
df -h ~                                          # room left for bags
  • Node output is on the launcher page only. It appears there while the page is open; afterwards read ~/.ros/log/ on the Orin (Debugging, where the logs are, and Launching the stack, Logs). The journal holds the launcher's own lines and the Zenoh router's output if it dies. The old README's ros2_launch_service name is out of date: the unit is ros_launcher.
  • Record bags on the robot. The viewer's Bagging panel runs ros2 bag record over SSH as ros@orin2. The bag keeps recording if the link drops or the viewer closes, and it's saved under /home/ros/bags/. Copy it off with rsync or scp -r. See Debugging, bags and data.
  • Looking is fine, changing isn't. Don't edit code, run apt upgrade or rebuild on the Orin by hand. Deploy from the release workspace so the robot always runs code you can name.
