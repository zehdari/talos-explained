Setting up your machine

From a blank laptop to Talos's code built and running in the simulator. What each script installs, where the code lives, what "sourcing" does, and how your changes get onto the robot.

The short version
  • Install Ubuntu 22.04, then run riptide_setup/setup.bash. It installs ROS 2 Humble, clones the code and edits your ~/.bashrc.
  • The code Talos runs is one repo, riptide_release, in ~/osu-uwrt/release. Every package repo inside it is a git submodule pinned to one exact commit. Build it with colcon build, and Nereus inside it with ./build.sh.
  • source install/setup.bash puts a workspace's packages on top of the ones already sourced. The last one sourced wins, and a new terminal starts with nothing except what ~/.bashrc sources.
  • A GPU helps but isn't required: the ZED SDK is only needed on the robot (Nereus renders the sim's camera images), and the detector falls back to the CPU.
  • Code reaches Talos as commits: push your branch, bump its submodule in release, then colcon deploy copies the sources to the Orin, the robot's main computer, and builds them there. The checklist at the end tracks your progress.

Before you start

Operating system
Ubuntu 22.04, installed on the laptop itself (dual boot is fine). ROS 2 Humble's packages are built for 22.04, and the setup script stops on any other version (update_system.bash).
GPU
Optional. If you have an NVIDIA one, install its driver first: the script checks for nvidia-smi. See Do you need a GPU?
Disk
About 17 GB, so leave at least 25 GB free. Measured on a team member's machine: release 4.2 GB (Nereus included), the development workspace and board firmware 5.3 GB, PyTorch for the detector 5.4 GB. ROS is 0.5 GB in /opt/ros, plus roughly 1.5 GB of system libraries apt installs with it (VTK, PCL and others).
Memory
Nereus's build runs one compile job per 3 GB of free memory, after keeping 4 GB for the desktop: 8 GB free gives 1 job, 16 GB gives 4.
GitHub
The repos are public, so cloning needs no account. Pushing needs write access to osu-uwrt (ask a lead): see Git.
Time
The script says the ROS install alone "will take about 20 min".

riptide_setup: one script, ten steps

riptide_setup is the team's installer. Clone it to exactly this path; every script inside uses ~/osu-uwrt/... paths.

sudo apt install git
mkdir -p ~/osu-uwrt && cd ~/osu-uwrt
git clone https://github.com/osu-uwrt/riptide_setup.git
# without sudo; it asks when needed
~/osu-uwrt/riptide_setup/setup.bash
Answer the prompts like this
  • Enter your install (Default is desktop): press Enter.
  • Install release setup? (default is no): type y. The rest of this site assumes ~/osu-uwrt/release exists.
  • After the reboot, the first terminal asks Setup bashrc for Release (R) or Development (D)?: type R and press Enter. It asks once per boot.
  • Until you build release (below), every terminal prints release/install/setup.bash: No such file or directory. That's expected: the script clones release but doesn't build it.

What the script does not do, so you do it next (Building, Building Nereus): build release, install GLFW, the Zenoh middleware and the detector's Python packages, and build Nereus.

Two quirks of setup.bash
  • The development workspace clones the branches in riptide.repos, which are old (master, ros2, ros2_dev, galactic): riptide_control's master has no riptide_mpc at all. One more reason to work in release.
  • Running setup.bash again appends a second Release/Development block to ~/.bashrc (nothing checks for one). Delete the duplicate.

Two workspaces: development and release

A workspace is a folder with a src/ of ROS packages that colcon builds into build/ and install/. The team has two:

  • development (~/osu-uwrt/development): one clone per repo, each on a branch, in two chained workspaces. The original day-to-day layout.
  • release (~/osu-uwrt/release): one repo, riptide_release, with every package repo inside it at a pinned commit. What the robot runs.

Work in release. Its README says to deploy from it and to run GUI tools from it so configs match the robot, and Nereus is built against it.

A submodule is a repo inside a repo. The outer repo stores only a commit hash for it, the pin. Cloning or git submodule update checks out exactly that commit, so one release commit names the whole robot's code at once. That's why the team commits "Pre RPAC test" to release before a pool test (RPAC is the campus pool).

# the first time (setup.bash does this if you answered y)
git clone --recursive https://github.com/osu-uwrt/riptide_release.git \
    ~/osu-uwrt/release

# later: bring everything to the current pins
cd ~/osu-uwrt/release
git pull
git submodule update --init --recursive

Pins or current work? A fresh clone builds the pins on release master. This site follows newer branches, the "current work" column above: riptide_motion_panel, for example, is on riptide_control's mpc branch but not at its pin. To match the site, check out those branches. They change over time, so ask a lead which are current.

# the branches this site follows (October 2026)
cd ~/osu-uwrt/release
git -C src/riptide_core checkout followpath-speed
git -C src/riptide_control checkout mpc
git -C src/riptide_perception checkout mapping-estimator
git -C src/riptide_autonomy checkout autonomy-mapping
git -C src/riptide_launch checkout newsim
The other branches: DVL, AprilTag, GUI, old simulator 
git -C src/nortek_dvl checkout DvlWaterTrackFallback
# same commit as the pin; this only leaves detached HEAD
git -C src/riptide_gui checkout newsim
git -C src/riptide_simulator checkout newsim
# apriltag_ros clones from upstream; the fix is on the team's fork
git -C src/apriltag_ros remote add uwrt https://github.com/osu-uwrt/apriltag_ros
git -C src/apriltag_ros fetch uwrt
git -C src/apriltag_ros checkout -b CompressedImages uwrt/CompressedImages

The AprilTag branch matters in the sim too: the tag detector subscribes to compressed images (apriltag.launch.py), and CompressedImages adds one commit that decodes them in the node itself, because the stock decode fails in that process (the commit).

The detached-HEAD trap

git submodule update puts each submodule on its pinned commit, detached from any branch. Commit there and the commit belongs to no branch; switching away loses track of it. Run git status inside a submodule before you commit, and git checkout <branch> first if it says "HEAD detached".

Building: rosdep, then colcon

cd ~/osu-uwrt/release
# underlays: ROS, then riptide_setup
source /opt/ros/humble/setup.bash
source ~/osu-uwrt/riptide_setup/install/setup.bash
# what every package.xml asks for
rosdep install --from-paths src --ignore-src -r -y
# GLFW for camera_faker
sudo apt install libglfw3-dev
# the middleware Talos uses
sudo apt install ros-humble-rmw-zenoh-cpp
# YOLO for the detector (+ PyTorch)
pip install ultralytics "numpy<2"
colcon build
source install/setup.bash
  • Source ROS first. Nothing else does yet: in release mode the ~/.bashrc block sources only release/install/setup.bash, which this build creates. Without it, rosdep doesn't know your ROS version and colcon can't find ament_cmake (ament is ROS 2's build system).
  • rosdep reads every package.xml and apt-installs what's missing. -r keeps going past keys it can't resolve; without it, rosdep installs nothing.
  • Keep numpy below 2. Ultralytics, the YOLO library the detector uses, would otherwise install numpy 2, and ROS Humble's cv_bridge, built against numpy 1, then fails ("compiled using NumPy 1.x"). Tested October 2026.
  • colcon finds every package under src/, orders them by dependency and builds each into its own install/<package>. Errors go to log/latest_build/<package>/stderr.log.
The keys rosdep can't resolve
PackageKeysWhat to do
camera_fakerglfw, libassimp-dev, OpenCVapt install libglfw3-dev. Without it camera_faker fails to configure, and colcon starts nothing new after a failure. OpenCV and Assimp come with ROS desktop.
tensor_detectorultralytics, numpy, scipy, cv2, OpenCV, CUDA, collectionspip install ultralytics "numpy<2" brings the Python ones. CUDA is optional; collections is part of Python.
riptide_bringup2, riptide_hardware2, riptide_rvizriptide_SINB, gpiod, zed_interfacesIgnore: none of their builds uses them.

The flags the team uses:

CommandWhat it's for
colcon build --packages-select riptide_mpcOnly that package. Fast; what colcon deploy runs on the robot.
colcon build --packages-up-to riptide_mpcThat package and everything it depends on.
--symlink-installLinks Python, launch and config files instead of copying them, so edits apply without a rebuild. Do a clean build when you switch it on or off.

The flags CI adds

ros2-ci.yml builds with --packages-skip tensor_detector (no detector), --cmake-args -DCMAKE_BUILD_TYPE=Release (optimized C++; riptide_mpc picks Release on its own when no type is set) and --event-handlers console_cohesion+ (each package's output in one block).

What "source" actually does

A built workspace is only folders. Nothing finds it until a few environment variables point at it:

AMENT_PREFIX_PATH
where ros2 run, ros2 launch and get_package_share_directory look for packages
CMAKE_PREFIX_PATH
where CMake looks when a package says find_package(riptide_msgs2)
PYTHONPATH
where Python imports from (generated message modules, Python nodes)
PATH, LD_LIBRARY_PATH
programs and shared libraries

source runs a script inside your current shell, so whatever it sets stays set. Each workspace's script prepends its folders, and lookups take the first match, so the workspace sourced last is the overlay and wins over the ones beneath it, its underlays.

One more thing makes the order matter: install/setup.bash first re-sources every workspace that was sourced when you built. So build release with ROS and riptide_setup sourced; built without riptide_setup, its setup.bash stops bringing in the colcon deploy command.

You don't type this in every terminal; ~/.bashrc does. setup_bashrc.bash appended a block that asks Release or Development once per boot and sources one or the other. Never source both in one shell. That block never sources ROS itself, so add the missing lines around it. A working terminal runs these, in order:

# you add this, above what setup.bash wrote
source /opt/ros/humble/setup.bash
# setup.bash wrote these (the R/D block runs the second)
source ~/osu-uwrt/riptide_setup/install/setup.bash
source ~/osu-uwrt/release/install/setup.bash
# Nereus's ./setup.sh offers to add this
source ~/osu-uwrt/release/nereus/build/ros-viewer/ros/setup.bash
# you add this
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
  • A new package needs a fresh source after its first build: its install/<package> folder wasn't on the path when you sourced.
  • A removed or renamed package lingers in install/ until a clean build, and can still be found.
  • After changing the middleware (the RMW), run ros2 daemon stop: the ros2 daemon keeps the old one.
  • On the robot, the middleware comes from a saved choice: release's config_rmw.bash reads ~/.uwrt/default_rmw, which the changermw command sets. On a laptop, use the plain export above. To join the real robot, see Joining from your own laptop.

Do you need a GPU?

No, but parts of the stack use one when it's there.

PartOn your laptop
ZED SDK and its ROS wrapperNot needed. The ZED SDK needs an NVIDIA GPU and drives the real cameras on the Orin. Without it, navigation.launch.py prints "zed_wrapper not found" and carries on; in the sim, Nereus publishes the camera images itself.
Detector, no CUDABuilds anyway (find_package(CUDA) is optional) and runs the .pt model on the CPU. Slower, but it works.
Detector, with CUDABuilds a TensorRT .engine on first start, which can take minutes, and falls back to the .pt if that fails (yolo_model.py).
Nereus camerasRendered with OpenGL without a window. cameras:=false turns them off, at the cost of no detections.
Nereus viewerAn OpenGL window. On a laptop with two GPUs, nvidia:=auto (the default) runs it on the NVIDIA one (sim.launch.py).
If the detector fails on the downward camera

A .engine already next to the .pt is used instead of building one, and that path has no fallback. The downward model ships with one, dfc_rs_26.engine, committed to riptide_perception. An engine only runs on the GPU and TensorRT version it was built for, so on a machine with CUDA the detector can fail when it switches to the downward camera. Move that file aside and it builds its own.

Building Nereus

Nereus is the simulator and the operator's viewer (Nereus, the simulator, The Nereus viewer). It sits in release as a submodule but isn't a colcon package: it's a plain CMake project, and a COLCON_IGNORE file keeps colcon out of it.

cd ~/osu-uwrt/release/nereus
# once per machine: apt libraries, uv, the ~/.bashrc line
./setup.sh
# ROS, then release: Nereus needs riptide_msgs2
source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash
./build.sh
setup.sh
apt-installs the C++ libraries, installs uv (a Python package manager) if it's missing, and offers to add the ~/.bashrc line that sources Nereus's launch files.
build.sh
Makes the Python environment with uv, then builds the ros-viewer preset if ROS is sourced (otherwise datasets, the headless dataset renderer). Output goes to build/ros-viewer/.
Jobs
One per 3 GB of free memory after 4 GB for the desktop; NEREUS_JOBS=2 ./build.sh overrides it. An active conda environment is kept out of the build.

Then run it. Talos's stack uses Zenoh as its middleware (ROS 2, the Talos way): it needs a router running, and every terminal needs RMW_IMPLEMENTATION=rmw_zenoh_cpp. Under full camera load, the default FastDDS stalled the simulator's /tf for up to 0.9 s; Zenoh didn't. For the sim you run your own router:

ros2 run rmw_zenoh_cpp rmw_zenohd
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim
# active_control_model:=mpc  run riptide_mpc (the default is the old complete_controller)
# mpc_model:=sim             the MPC uses this sim's vehicle model, not the real robot's

That starts the simulator, Talos's whole stack and the viewer. With CUDA, the first start can take minutes while the detector builds its TensorRT engine. Launching the stack and Working on it yourself go from here.

VS Code

Any editor works. If you use VS Code:

  • Start it from a sourced terminal: cd ~/osu-uwrt/release && code .. It inherits that environment, so its terminals and debugger see ROS and your workspace.
  • C++ navigation needs compile_commands.json. Nereus already writes build/ros-viewer/compile_commands.json. For colcon packages, build with --cmake-args -DCMAKE_EXPORT_COMPILE_COMMANDS=ON and point the C/C++ extension or clangd at build/<package>/compile_commands.json.
  • Ignore committed .vscode folders. riptide_control's lists include paths under one member's home folder.
  • Behaviour trees have their own editor, the team's Groot fork (install_groot.bash builds it); see Writing and testing trees.

Git: branches, pull requests and release

Each repo works the same way: a branch per change, a pull request to merge it. Long-running branches (mpc, newsim, mapping-estimator) carry work far ahead of master, and feature branches merge into them; around competition, dev is merged into master. The release repo then pins the commits that go in the water.

Before your first push, tell git who you are and how to log in. Everything was cloned over https, so the simplest login is the GitHub CLI (sudo apt install gh).

git config --global user.name "Your Name"
git config --global user.email you@example.com
# answer HTTPS, then yes to "Authenticate Git"
gh auth login

The routine, from the release README: before a pool test, bump the submodules to the commits to test and commit to master; after it, commit the fixes and bump again. The log reads like a test diary ("Pre RPAC test 10-12-26", "Post sean test"). The README also asks for a date tag after each test, but the last one is from 2024; tags now mark competitions (robosub2024, robosub2026). Bumping a pin:

cd ~/osu-uwrt/release/src/riptide_control
git status                  # on your branch, nothing uncommitted
git push                    # a pin must be a commit others can fetch
cd ~/osu-uwrt/release
git add src/riptide_control # records the submodule's current commit
git commit -m "Pre RPAC test 10-30-26"
git push

Before a pool test the checks require every pin committed and pushed, and the robot's code to match release exactly (Pool test day).

Getting code onto Talos: colcon deploy

The team's code isn't cross-compiled. colcon deploy, a command added by riptide_setup's colcon_riptide extension, copies package sources to the Orin and builds them there, in ~/colcon_deploy. Run it from ~/osu-uwrt/release:

  • You need riptide_setup sourced (it provides the command), a passwordless SSH key for ros@ the Orin, and the Orin's name in /etc/hosts. The current Orin is orin2; setup.bash only adds an older orin entry. Ask a lead before your first deploy.
  • On the robot, src/ is flat: one folder per package, no git. A package deleted on your side stays there until someone removes it.
  • Packages with a DEPLOY_IGNORE file are never sent: riptide_meshes, riptide_rviz and camera_faker (desktop and simulator tools).
  • The robot builds with -DBUILD_DEPLOY=ON, which packages can test for: riptide_autonomy skips its checkBT tree checker (CMakeLists.txt).
A deploy changes the robot

The Orin runs whatever is in ~/colcon_deploy the next time the stack launches. Before a test, deploy only committed, pushed code, so release says exactly what ran. If code changes during a test session, the bench checks have to be redone. The team's pre-test sequence is a clean build on the laptop, deleting ~/colcon_deploy on the Orin, and colcon deploy orin2 --clean, run by a person.

colcon timesync, the older clock tool

The same extension adds colcon timesync orin2: it sets the Orin's clock to your laptop's over SSH, in one jump. The plan is for the Orin to follow the opbox's chrony server (Computers and networks); until that rollout is done, timesync is the fallback. Never run it while the stack is running: a backward jump of more than 10 s makes Nereus drop TF.

Setting up a Jetson from scratch (rarely needed)

These scripts in release's scripts/ build ROS 2 itself for a Jetson, and set the Jetson up:

cross_build.py
Builds a ROS 2 distribution for arm64 inside a Docker container, from a profile in scripts/meta_files (humble_robot_jetson is 264 repos). It exists for Jetsons whose Ubuntu has no ROS 2 Humble packages. docker_arm64_qemu.bash lets an x86 machine run it, about 8 times slower.
remote_install.py
Sets up SSH keys and passwordless sudo on the target, syncs the clock, installs dependencies, PyTorch and the ROS tarball, edits .bashrc, and configures JetPack (fan profile, no desktop, CAN modules). Enabling can0/can1 in jetson-io is left to you.
