Autonomy · Chapter 1

Behaviour trees

Every Talos mission is a behaviour tree: an XML file of small nodes that a C++ library walks through every 30 ms. Learn how one walk goes and you can read any of the team's trees.

The short version
  • A tree is XML. The doTask node ticks its root about every 30 ms until it returns SUCCESS or FAILURE.
  • Each tick, every node it reaches answers SUCCESS, FAILURE or RUNNING. Leaves do things or check things. Sequence, Fallback and decorators decide what runs next.
  • Nodes share data on a blackboard. A subtree gets its own, and its ports are mapped to the caller's keys, which in BehaviorTree.CPP v3 are always key names. That is why the trees are full of SetBlackboard "15" = "15".
  • Anything slow (a path, a service call) is an async action. It starts on one tick, returns RUNNING, and checks its ROS reply on later ticks. Halting it cancels the request.
  • The team used state machines (SMACH, then FlexBE) until 2022, then switched to BehaviorTree.CPP v3.

Autonomy lives in riptide_autonomy (ROS package riptide_autonomy2). It uses BehaviorTree.CPP version 3 (behaviortree_cpp_v3, 3.8.7 in ROS Humble), a widely used C++ library for behaviour trees in ROS. Version 4 changed a lot, so read the 3.8 docs, not the current ones. The team edits trees in its fork of Groot, a graphical editor (Chapter 4).

Here is a whole real subtree, WaitForKillSwitch, the first subtree the competition mission runs:

<BehaviorTree ID="WaitForKillSwitch">
  <Sequence>
    <Action ID="SetStatus" status="waiting"/>          <!-- LEDs solid red -->
    <Action ID="Info" message="Waiting for kill switch insert..."/>
    <Action ID="Wait" seconds="5"/>
    <RetryUntilSuccessful num_attempts="-1">       <!-- try forever -->
      <Sequence>
        <Action ID="GetBoolTopic" topic="state/kill" value="{kill_switch_inserted}"/>
        <Inverter name="IsFalse">
          <Condition ID="IsTrue" value="{kill_switch_inserted}"/>
        </Inverter>
        <Action ID="Wait" seconds="1"/>
        <Action ID="Info" message="KILL SWITCH INSERTED, TREE STARTING IN 5 SECONDS"/>
      </Sequence>
    </RetryUntilSuccessful>
    <Action ID="SetStatus" status="starting"/>         <!-- LEDs blink blue -->
    <Action ID="Wait" seconds="5"/>
  </Sequence>
</BehaviorTree>

Read it top to bottom. Show red, wait 5 s, then keep reading state/kill until it says false, then blink blue and wait 5 s more. state/kill is true while the robot is killed, so the key named kill_switch_inserted actually holds "killed", and the Inverter makes the check pass once it reads false. The next section draws it as a tree, and the rest of this chapter explains each piece.

Ticks and statuses

A tick is one function call on the root. The root ticks a child, that child ticks one of its children, and so on down. Every node it reaches returns one of three statuses:

  • SUCCESS: done, it worked.
  • FAILURE: done, it didn't (or the answer to a check is no).
  • RUNNING: not finished, tick me again.

There is a fourth state, IDLE: not started, or reset by its parent. A node never returns it. When a parent no longer needs a RUNNING child, it halts it, so the child can clean up (a path follower cancels its goal), and resets it to IDLE.

A tick has to be quick: nothing should block for long inside one. A node that waits (for a path, a reply, two seconds) returns RUNNING and checks again on the next tick.

Statuses travel up: a leaf answers, and each parent turns its children's answers into its own. The thing that calls tick on the root again and again is doTask:

Who sends the goal? Today it is the Nereus viewer's autonomy panel (the viewer chapter). It lists the tree files from autonomy/list_trees and starts one through the autonomy/run_tree action. While the tree runs it shows the node stack that doTask publishes on autonomy/tree_stack. Every run also writes a log, ~/btlogs/BTLog_<date>.fbl, that Groot can replay. Live streaming to Groot (ZMQ) is off in autonomy.launch.py.

Only a cancel (the viewer's Stop) ends a tree early. Pulling the kill switch does not: the check in the tick loop is commented out (// || robotKilled, DoTask.cpp), so the tree keeps ticking with the thrusters off (Chapter 2).

Sequence, Fallback and friends

Control nodes have children and decide which to tick. Two cover most of every tree:

  • Sequence ("do all of these"): ticks children in order. It stops at the first one that fails (and fails) or is RUNNING (and is RUNNING). It succeeds when all have succeeded.
  • Fallback ("try until one works"): ticks children in order until one succeeds (and succeeds). It fails only when all have failed.

A real example, AssertTree: pass the check, or else print why and fail.

<Fallback>
  <Condition ID="CompareNums" a="{a}" b="{b}" test="{test}"/>
  <ForceFailure>
    <Action ID="Info" message="Assertion {aname} ({a} {test} {b}) failed"/>
  </ForceFailure>
</Fallback>

Two details of BehaviorTree.CPP v3 matter when you read Talos's trees:

  • A plain Sequence remembers its RUNNING child. On the next tick it goes straight back to it and does not re-check the children before it. After a failure it starts again from the first child.
  • A ReactiveSequence starts from the first child on every tick. If an earlier child now fails, it halts the one that was running. Put conditions first and a long action last, and the action stops the moment a condition changes. ReactiveFallback is the mirror: it re-checks earlier children every tick and halts the running one if an earlier one now succeeds. Talos does not use it.

Decorators

A decorator has exactly one child and changes how it runs or what it returns.

ForceSuccess is the most common decorator: it is how a tree says "try this, but a failure here is fine". CompMissionTreeMpc wraps each task in one, so a task that times out or fails a check lets the run move on to the next task instead of ending it (Chapter 3 goes through the mission task by task).

Two timing details:

  • The library's RetryUntilSuccessful and Repeat loop inside one tick when the child finishes at once. If the child returns RUNNING, they return RUNNING and carry on next tick.
  • The team's RetryUntilSuccessfulOrTimeout re-ticks its child once per tick until it succeeds, or until num_seconds have passed since its first tick.
Worth knowing

When its time runs out, RetryUntilSuccessfulOrTimeout returns FAILURE without halting a child that is still RUNNING, so the child's onHalted never runs (the library's Timeout would halt it). If SearchMpc's 100 s run out mid-sweep, the tree does not cancel its FollowPath goal. The controller keeps flying the rest of that path until it ends (it arrives or stops making progress), or until a new path or setpoint replaces it (the MPC preempts it then: new path, setpoint). Tick it yourself

The simulator runs the real SearchMpc subtree, loaded from the XML. This is how the torpedo task finds the torpedo board. It sweeps arcs around the mapped estimate until the camera sees the board, chases the detection to centre it, then holds until the map is confident.

Every node follows BehaviorTree.CPP v3's rules. The parts that would talk to ROS are stand-ins, controlled by you: is the torpedo in view, has the map converged, has the path finished. Inputs are what TorpedoTreeMpc passes in: max_dist 2 m, min_dist 1 m, target_cov 0.0025, timeout_secs 100 s.

Things to try:

  1. Step a few times. The first tick runs nine SetBlackboards, SetStatus and Format straight through, then stops at SetMappingTarget, which waits for a service reply. A few ticks later FollowPath has sent its goal and is flying.
  2. Turn Torpedo in view on and step once. The ReactiveSequence re-checks SeenRecently, its Inverter fails, and FollowPath is halted: its goal is cancelled. The chase starts on the same tick.
  3. Press Centred, then set the map to converged. The hold loop succeeds, getCovariance reads the new error, and SearchMpc returns SUCCESS.
  4. Reset and switch to plain Sequence. Put the torpedo in view mid-sweep: nothing happens until the path ends, because a Sequence goes straight back to its RUNNING child.
  5. Reset and let a sweep finish with nothing seen (Path finished). The sweep fails, the retry decorator runs it again, and stage goes from 0 to 1: a wider sweep at 3 m.

The blackboard and ports

The blackboard is a key-value store shared by the nodes of one tree. Nodes reach it through ports, named inputs and outputs each node type declares in C++ (providedPorts()):

  • seconds="5" is a literal. seconds="{hold_secs}" reads the key hold_secs.
  • An output port names the key to write: out="stage" or out="{stage}" both write stage.
  • SetBlackboard writes a value to a key. There are 561 of them in the competition tree file.

Three Talos conventions sit on top of the library:

  • Every port is a string. UwrtInput declares InputPort<std::string>, and nodes convert when they read (tryGetRequiredInput<double>, autonomy_lib.hpp). Nothing checks a number until the node reads it. Then "abc" throws, and doTask aborts the whole tree (LEDs flash red), while "1.5m" quietly reads as 1.5 (std::stod).
  • Empty means default. Groot saves every port, unset ones as "". The nodes treat "" as "use my default", which is why tree lines like FollowPath ... max_speed="" spin_rate="" are fine.
  • {key} inside text. Info, Format and FollowPath fill in {key} anywhere inside a longer string, for example message="Object {object_name} has covariance {cov}". That is Talos's formatStringWithBlackboard, not the library.

Subtrees and remapping

A <BehaviorTree ID="..."> can be used inside another tree as <SubTree ID="..."/>. That is how the team reuses behaviour: Move is called 33 times in the competition file. Each tree file carries its own copy of the shared subtrees (87 in RepairCompMpcTree.xml) and runs the one named by main_tree_to_execute (here BehaviorTree).

Every call in the competition tree gives the subtree its own blackboard (__shared_blackboard="false", also the default when the attribute is left out). Each other attribute maps one key: port="key" means "when the subtree reads or writes port, use my key key".

In BehaviorTree.CPP v3 that value is always a key name, never a literal (xml_parsing.cpp). To pass a fixed value, the caller first writes it to a key named after the value itself. The main tree passes repair_mission = 1 like this:

<BehaviorTree ID="BehaviorTree">
  <Sequence name="MISSION">
    <SetBlackboard output_key="1" value="1"/>   <!-- key "1" now holds "1" -->
    <Action ID="Info" message="MISSION: REPAIR"/>
    <!-- inside the subtree, repair_mission reads this tree's key "1" -->
    <SubTree ID="CompMissionTreeMpc" __shared_blackboard="false" repair_mission="1"/>
  </Sequence>
</BehaviorTree>

Without that SetBlackboard, repair_mission would be empty inside the subtree, and nothing warns you until a node reads it. This happens for real: FireTorpedo calls WaitForActuators with timeout_secs="10" but never writes a key "10". The wait's RetryUntilSuccessfulOrTimeout reads no num_seconds, uses its default of 0 and fails on its first tick, so the robot does not wait for the actuators at all (Chapter 3). Pick it in the explorer below. Two more things to know:

  • Defaults declared for subtree ports in the file's TreeNodesModel (SearchMpc's max_dist 4.0, for example) only document the subtree for Groot. v3 never applies them. An unmapped key is simply missing, and the node falls back to its own C++ default.
  • The library's SubTreePlus accepts literals, but Talos's trees don't use it.

Actions that take time: talking to ROS

Every Talos action node derives from UWRTActionNode, which is the library's StatefulActionNode plus a ROS node handle (UwrtBtNode.hpp). A stateful action has three callbacks (quick nodes such as Info and Math simply return SUCCESS from onStart):

onStart()
The first tick. Read the ports, send the request, return RUNNING. Return SUCCESS or FAILURE to finish at once.
onRunning()
Every later tick while RUNNING. Check the reply without waiting, then return RUNNING, SUCCESS or FAILURE.
onHalted()
Called if a parent halts it while RUNNING. Cancel what it started.

FollowPath sends a path to the MPC's follow_path action server. Cut down to the parts that matter here:

BT::NodeStatus onStart() override {
    startTime = now();  timeout = input("timeout", 60);
    // parse "x,y,z,yaw; frame: x,y,z,yaw | arc=...; ..." into waypoints
    return RUNNING;
}
BT::NodeStatus onRunning() override {
    if (now() - startTime > timeout) { cancel(); return FAILURE; }
    if (!goalFuture.valid()) {                     // once the TF frames resolve
        goalFuture = client->async_send_goal(goal);  return RUNNING;
    }
    if (!goalHandle) {
        if (goalFuture.wait_for(0s) != ready) return RUNNING;   // poll, never block
        goalHandle = goalFuture.get();
        if (!goalHandle) return FAILURE;           // rejected
        resultFuture = client->async_get_result(goalHandle);
    }
    if (resultFuture.wait_for(0s) != ready) return RUNNING;
    return resultFuture.get().code == SUCCEEDED ? SUCCESS : FAILURE;
}
void onHalted() override { cancel(); }            // async_cancel_goal

Each step is a check of a ROS future with wait_for(0s), which returns at once. Services work the same way: CallTriggerService sends the request in onStart, checks the future in onRunning, and gives up after time_limit_secs. One exception: onStart first waits up to 1 s for the service to exist (wait_for_service(1s), line 42). If the service is down, that blocks the whole tree for a second. SetMappingTarget, CallSetBoolService, CallSetStringService, CallStartBinaryClassifierService and PublishEKFPose do the same.

Why so careful? Two reasons.

  • A blocked tick stops the whole tree. A ReactiveSequence above the action could not re-check its conditions, and nothing could halt the action.
  • Replies arrive on another thread. doTask ticks the tree on its own thread. ROS callbacks (action replies, subscriptions) run on a single-threaded executor in main (DoTask.cpp). The README explains why it is single-threaded: Humble's multi-threaded executor can starve service replies.

Conditions are different: they answer at once from data a subscription already cached. SeenRecently stores the last time each class appeared on detected_objects or mapping/fused, and a tick only compares that time with the clock. That is what makes it safe to re-check every tick in a ReactiveSequence.

Every node gets ROS in rosInit(), which initRosForTree calls once the whole tree is built. Don't touch ROS in a node's constructor. Chapter 2 goes through Talos's nodes one by one.

Why trees, not state machines

The team has written mission code in three systems. The technical design reports (TDRs) tell the story:

To see what a tree buys, draw SearchMpc as a state machine:

In the tree, the same logic comes from the structure:

  • Reacting: "stop sweeping when it's seen" is a condition in front of the action in a ReactiveSequence, not an arrow out of the Sweep state.
  • Limits: the time limit is one decorator around the whole thing, not an arrow from every state.
  • Reuse: a subtree doesn't know who called it or what comes next, so Move can be called from 33 places. A state has to name its successors.
  • Failure stays local: ForceSuccess and Fallback decide what a failure means at the place it happens. The mission keeps going.

There is a cost. Things a state machine shows plainly become decorators and blackboard flags. "Go back and sweep wider" is a retry decorator plus the stage key. A loop is not a visible arrow, so you have to know the tick rules to read it, which is the point of this chapter.
