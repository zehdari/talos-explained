Running Talos · Chapter 4

Pool test day

Pool time is short and booked. Whatever can be found on a bench is found there the day before, so the water is only for what needs water. This is the whole day, from bumping submodules to tagging the release, with a checklist you can tick through on your phone.

The short version
  • Do the bench checks the day before at the latest. The team's pre-test document allows 1.5 to 6 hours and says, in capitals, not to do them on the day.
  • Freeze the code. One riptide_release commit pins every repo, a clean deploy puts exactly that on the Orin, and pretest checks that it did.
  • At the pool, the Nereus viewer on op-top is the operator UI. It kills Talos from the moment it opens until someone presses Enable.
  • The physical kill switch is the only kill that works without the tether. One person holds it, and that is their only job.
  • Afterwards, copy the data off the Orin, commit what changed, and tag the release with the date.

A test in three parts

Before
Bench-test the new code on the robot, freeze it in release, deploy, run the checks, seal and pressure-test the hull. The day before at the latest.
At the pool
Set up on deck, check Talos in the water, then fly: small moves, the course, trees, identification. Record everything.
After
Copy the data, commit fixes made at the pool, tag the release, write it up.

The procedure comes from the team's PRE_TEST_CHECKS document and the release README. Most of the bench part is now automated by pretest_checks (below).

Every test leaves a trace in riptide_release: a commit that pins the code before it, like Pre RPAC test 10-12-26. RPAC is Ohio State's Recreation and Physical Activity Center; the 2025 TDR describes bi-weekly testing in its dive well as "competition run" practice, and credits a "multi-day pre-test checklist" with catching unplugged cables and software misconfigurations before pool sessions.

Two things stand out. The team tests roughly weekly in term time, so each test has a short runway. And the README's last step, a tag named for the date after each test, stopped in June 2024. Since then the "Pre" commits are the only record of what ran. After the test brings the tags back.

Before: freeze the code

The rule behind everything else: the code that goes in the water is one release commit, and the Orin runs exactly it. Then a problem at the pool can be reproduced at home, and a good state can be returned to.

  • Bench-test on the robot. New code is tried on the Orin with the real sensors, not just on a laptop. The document: "Integration is hell." This is the part that takes longest.
  • Update days ahead. apt upgrade or new drivers go in days early, because what they break is "often times inexplicable and confusing".
  • Pin and push. Each changed submodule is committed and pushed on its branch, then release records the new pins. A pin that exists only on your laptop can't be checked out by anyone else.
  • Build and deploy clean. colcon never deletes a removed package from install/, and stale caches cause compile errors that look like code bugs.
cd ~/osu-uwrt/release
git submodule status          # '+': away from its pin
git add src/riptide_control   # each one you changed
git commit -m "Pre RPAC test 10-30-26" && git push

rm -rf build install log && colcon build      # clean build
source ~/osu-uwrt/riptide_setup/install/setup.bash
ssh ros@orin2 'rm -rf ~/colcon_deploy'        # clean on the Orin
colcon deploy orin2 --clean
No git at the pool

"NEVER plan on making git changes (like a revert) at a pool test." A revert means rebuilding on the Orin, and the packages depend on each other so tightly that a poolside revert usually breaks something else. If code is wrong, fix it on the bench. At the pool, the release README has you deploy only the packages you need "as you work through bugs"; commit those changes afterwards.

How submodules, pins and colcon deploy work is in Setting up your machine.

pretest_checks: the bench, checked by a script

pretest_checks turns the document into checks that print PASS, WARN or FAIL, with the fix for a person to apply. It was written in October 2026 and lives on op-top in ~/osu-uwrt/release/pretest_checks; it isn't in a GitHub repo yet. Everything robot-specific (hosts, topics, boards, thresholds) is in one profile, robots/talos/robot.yaml, so another robot only needs a new profile.

What it will never do matters as much as what it does:

  • It never changes code on the robot. No deploys, no builds on the Orin, no git or apt commands that modify anything. When the robot is out of date, it prints the commands for a person to run.
  • It never starts the controller as a plain launch. An enabled robot with control_system running spins its thrusters. The bench stage runs the controller only while it holds a software kill and both ESC boards report SAFETY_KILLED.
  • Only the thruster test moves anything, and only after a person has enabled the robot and pressed Enter.
  • It never tares the gyro. An unlevel bench would bias every heading.

The thruster test

thruster_test_canbus (send_thruster_cmd_canbus.c) writes CAN frames straight to the two ESC boards, with no ROS and no controller in between. It runs each thruster in turn at 300 rpm for 3 s (100 frames 30 ms apart), forever, until Ctrl-C. Its Ctrl-C handler sends zeros to every thruster before exiting. One run checks three things:

  1. The software kill. Start it with Talos killed in the viewer: it prints thruster numbers and nothing spins.
  2. The wiring. Enable: each thruster spins in its turn. Check it's the one in the place named. Telemetry shows which ESC turns, but only your eyes see which motor that ESC is wired to.
  3. The physical kill. After a full cycle, pull the switch: everything stops while the program is still commanding.

The program counts thrusters 0 to 7, the same indices as in talos.yaml and the figure below. (The old document says "0 through 8" and warns its picture is 1-indexed; the code is the reference.)

The controller has to be stopped first. The MPC and the test would both write thruster commands to CAN; the document calls this part "strict". pretest guided runs it as G4 with the robot already enabled: it waits for the ESCs to come out of their power-on delay, starts the test on Enter, checks the ESC telemetry in each 3 s window, then checks the physical kill stops everything within 1 s. The killed start (step 1) is only in the by-hand flow, so use that flow for a poolside retest.

Thrusters
  • Before the test: Talos on its stand, propellers clear of hands, hair, cables and tools, and a second person at the kill switch.
  • 300 rpm is the test. Under the MPC a thruster can reach its 24 N limit, about 2,450 rpm (Thrusters and allocation).
  • Never start control_system on the bench with the robot enabled. Out of the water, pulling the physical switch is the one kill that needs no software at all.

The rest of guided works the same way: the tool says what to do, a person does it, the tool checks the data. Tilt Talos about 10° to starboard, nose down, then turn it about 20° left, and the right axis has to move with the right sign. A finger on the depth sensor has to read deeper. A torpedo prop held in front of the front camera has to be detected and mapped, then the torpedo and dropper are fired. Steps are hands-free, because whoever is holding the robot can't reach a keyboard.

The depressurization test

The bench ends with a leak test by hand. In the 2025 TDR, a hand pump lowers the hull pressure by 0.05 bar, and the IMU's pressure and the boards' temperatures are watched for five minutes: by the ideal gas law, a leak shows up as air coming back in. The document's steps:

  1. Only hardware running in the launcher. Keep its log open.
  2. Put the pump in Talos's pressure hole.
  3. Start the PVT, and once it says it's ready, pump. The logs say when to stop.
  4. Pull the pump out quickly and plug the hole.
  5. Leave Talos for at least 5 minutes.
  6. Passed: the green subconn cover goes on. It means sealed and tested.
Unconfirmed

The document starts the PVT from RViz's electrical panel. The viewer's Electrical panel has no PVT button (viewer docs). The node behind the old button, pressure_monitor.py, is still installed: it serves a depressurize action (riptide_msgs2/action/Depressurize) and reads its limits from pressure_monitoring in talos.yaml. But no launch file starts it. Whether the team runs it by hand (ros2 run riptide_hardware2 pressure_monitor.py, then a goal on depressurize) is unconfirmed: ask the mechanical or electrical lead.

Then the rule that protects all of it: nobody opens Talos or swaps a part until the test. Any internal change voids the localization and thruster tests. Open it, and the PVT has to be done again.

Batteries

Packs
Two smart battery housings, port and starboard. Each holds a MaxAmps 8000 mAh 5S2P LiPo pack, 18.5 V nominal, about 148 Wh (gauge notes), with a TI BQ40Z80 gauge and a 45 A protector fuse (The electrical system).
Voltage
Charged to at most 4.15 V a cell (20.75 V) and discharged to no less than 3.2 V a cell (16 V). The gauge raises a swap alert at 17.5 V, MaxAmps' recommended landing voltage (line 389). The pre-test tool's B4 wants at least 18.5 V (nominal) on the bus: that is a start-of-day bar, not a landing limit.
Sharing
The POAC board ORs the two packs through ideal diodes: whichever is higher supplies the bus.
On the housing
A small OLED and three LEDs, one lit for the charge band: above 60 %, 30 to 60 %, 30 % or less (bq40z80.h).
In the viewer
PORT and STBD chips show each pack's charge: amber below 50 %, red below 20 %, gray after 10 s without a reading. Hover for voltage, current and time to empty.
  • Charge both the night before. On the bench Talos runs from a power supply, so the packs are only tested once they're in.
  • B4 fails below 18.5 V on deck? The packs weren't charged: start the day on fresh ones.
  • At the pool, swap when a chip goes red or the gauge's 17.5 V alert fires, whichever comes first. Don't fly a pack down to its 16 V cutoff.
LiPo
  • Charge at no more than 5 A, and only between 0 and 50 °C (Charging and handling).
  • Never force-charge a pack the BMS refuses. A deeply flat LiPo is the dangerous one.
  • Keep the terminals covered and never short a pack. If a housing is hot, swollen or smells, stop using it and tell the electrical lead.

On deck: network, power, launcher, viewer

Talos's Orin, the DVL and op-top share the team router's LAN, 192.168.1.0/24. On deck, the tether joins Talos to it, and the opbox gives the LAN internet and a time server (Computers and networks). Power-on order

The code doesn't enforce an order. This one follows from how the kill system works, and it keeps the thrusters unpowered until the end:

  1. Kill switch out. With it out, the POAC board cuts ESC power, whatever any software says.
  2. Power on. The POAC board starts killed and stays killed until micro-ROS connects. The Orin boots and ros_launcher starts by itself as a service.
  3. Launcher: open http://orin2:8080, load talos_launch_mpc.yaml and start, in the pre-test tool's order, hardware (real DVL this time, not hardware_fake_dvl), navigation (riptide_hardware2's, the first of the two), zed, tensorrt, mapping and autonomy. The diagnostics node is no longer used.
  4. The viewer on op-top. From its first tick it reports a kill on slot 1, so Talos stays killed even if the switch goes in.
  5. A quick health check (below). If the hull was opened or anything rewired since the bench, run the thruster test again now, on the stand, while the controller is still off.
  6. control_system last, with Talos still killed. Killed, the MPC publishes zero thrust.
source ~/osu-uwrt/release/scripts/dds_scripts/config_rmw.bash
ros2 launch nereus robot.launch.py pool:=rpac

cd ~/osu-uwrt/release/pretest_checks
./pretest bench --only B3,B4,B5,B6,B7 --power battery
  • config_rmw.bash makes the terminal a Zenoh client of orin2 (ROS 2 over Zenoh).
  • pool:=rpac draws the RPAC pool around the robot (robosub for the competition pool); robot_only:=true hides the pool. Talos is drawn from the localization estimate, on wall-clock time (robot.launch.py).
  • The health check is five bench checks that start nothing and take under a minute. The planned dayof stage will compare everything with the last passing bench run.
  • In the command bar, check the FOG temperature, DVL and both battery chips. The CPU chip reads the computer monitor in diagnostics.launch.py, which isn't started any more, so it stays gray.

Where every control is, and how to drive with it, is in The Nereus viewer; how a pool run looks to the kill system, step by step, is in Commanding Talos.

The kill switch rules

The mechanism is in Commanding Talos. Pool rules that follow from it:

  • One kill-switch holder. Named before Talos goes in. They hold the switch, watch the robot, and pull it the moment anyone says so. No other job. The pre-test tool's first guided question asks the same: "someone at the kill switch?"
  • Untethered, the switch is the only kill. The viewer's KILL only works while its messages reach the robot. Its enable latches (needs_update false) so that runs survive the tether coming off, which also means losing the link never kills.
  • One operator. A second viewer, or anyone else publishing on slot 1, counts as a competing operator: the viewer drops its enable at once.
  • Hands off an enabled robot. Anyone handling Talos in the water asks for the switch out first, and gets it.
  • After any kill, the ESCs wait. When power comes back, they hold their motors for about 5 s, then the MPC flies to its last reference again, and a tree that is still running carries on. Before the switch goes back in, press KILL in the viewer and Stop the tree (Ending a run).
Lifting

Talos weighs about 32 kg dry and 34 kg wet (scale weights). Two people lift it, in and out, with the kill switch out. Nobody's hands go near a propeller while the robot can be enabled.

In the water: buoyancy and trim

Talos is built to float, slightly. RoboSub requires a vehicle to be positively buoyant by at least 0.5 % of its mass with the kill switch pulled (RoboSub and the course), so a killed robot comes up on its own. Talos's MPC model has it right at that line:

Net buoyancy
+1.63 N in the current model, models/talos.yaml, just under the 0.5 % line (1.68 N for its 34.3 kg). The untethered identification of 2026-10-26 fitted 1.68 N, right on it. If Talos sinks or hangs in the water, add buoyancy before flying.
Rises at
About 4 cm/s with the thrusters off (identification releases).
Centre of buoyancy
About 22 mm above the centre of mass, so Talos rights itself when tilted.

That margin is small on purpose: every newton of extra buoyancy is a newton the vertical thrusters push against for the whole run. Two checks in the water:

  • Killed: does Talos float up slowly and sit at the surface?
  • Enabled, holding still: plot the MPC's disturbance estimate (controller/mpc/disturbance; plot disturbance in the viewer's Ctrl+P search). The MPC learns whatever force and torque its model is missing. A few newtons or newton-metres held constant means the model's buoyancy or trim no longer matches the robot: something was added or moved, or the tether is pulling. The model's own rule: "Change the body and re-identify."

First moves stay small. Type them into the viewer's search (Ctrl+P): forward 0.5, turn 30, down 0.3, and watch the error column in the Motion panel (typed moves).

Mapping the course

The trees navigate in the map frame, using a prior map: where each prop is expected, relative to a map origin, in riptide_mapping's config/config.yaml. At a new pool, or with the props moved, the map has to match the water.

  1. Place the props, measure them. Then open Edit map in the viewer (Ctrl+M) and move each prop to where it is. The origin is either AprilTag, on a wall where a floor line meets it, or Robot frame, Talos's start pose (viewer docs).
  2. Save and deploy it. The editor writes the file in op-top's release source tree. Deploy just that package and restart mapping in the launcher so it reads the new file.
  3. Calibrate. With the tag in view, Calibrate in the Mapping panel averages the tag board's pose and sets world → map from it.
  4. Commit the map afterwards, in riptide_perception, so the next test starts from it.
cd ~/osu-uwrt/release
colcon deploy orin2 --packages-select riptide_mapping2

Running trees

A tree is started from the viewer's Autonomy panel, but it doesn't move until the physical switch goes in. The mission trees begin with WaitForKillSwitch (CompMissionTree.xml): wait 5 s, poll state/kill until it reads false, then wait 6 s more. That is how a run goes untethered:

  1. Talos at the surface, switch out.
  2. Enable in the viewer. Talos stays killed by the switch, but slot 1 is now clear, and latched.
  3. Autonomy: pick the tree, Start. The viewer only allows it while it holds the enable. The tree logs "Waiting for kill switch insert...".
  4. Unplug the tether, if this run is untethered. Slot 1 stays clear.
  5. Insert the switch. Six seconds later the tree moves.
  6. Pulling the switch stops the thrusters, not the tree. The executor's kill check is commented out (DoTask.cpp), and only a running path goal fails, with "vehicle killed" (MPC). The tree can retry or go on to its next task, and it drives Talos again the moment the switch goes back in.
Ending a run
  1. Switch out. Killed, Talos floats up on its own.
  2. A swimmer brings Talos to the side. Plug the tether back in.
  3. Autonomy panel: Stop, and wait until Start is free again.
  4. Viewer: KILL. Slot 1 now holds Talos killed even with the switch in.
  5. Only now: switch back in, hands on Talos, or the next run from step 2 above.

Skip a step and the viewer's latched enable plus a live tree can move Talos as soon as the switch goes in.

While a tree runs, the viewer blocks manual commands. Which trees exist and how they're built: The competition mission and Writing and testing trees.

Identification runs

pool_identify flies a scripted session and fits Talos's buoyancy, drag and added mass (System identification). At the pool it needs space and no tether:

  • It starts at the map origin. IdentificationTree dives to 0.85 m, flies to the mapping origin facing map +x, and only then starts pool_identify (IdentificationTree.xml). So the clear water is measured from the origin, along the map axes: put the prior map in and calibrate first.
  • Room: 3 m of clear water ahead (map +x) and to port (map +y) of that start, and 2.5 m below it for the heave lanes and releases. It starts at least 0.75 m deep and ends if Talos comes within 0.4 m of the surface (identification.yaml; the tree's own comment still says 1.5 m).
  • Untethered: start pool_identify on the Orin before unplugging. With wait_for_trigger:=true it waits for IdentificationTree to start it, so run that tree like any other.
  • Not tied to your SSH session. When the tether comes off, the SSH link drops, and a launch running in that shell can go with it. Start it inside tmux, or with nohup … & if tmux isn't installed. How the 2026-10-26 sessions were started isn't recorded.
  • From the committed model: start untethered fits from talos.yaml, never from a tethered fit.
  • Data: each session writes a folder under ~/osu-uwrt/mpc_identification on the Orin, with its own bag.

Recording

A run that wasn't recorded can't be debugged at home. Start a bag before every run, from the viewer's Bagging panel (viewer docs):

  • Record on: Robot. ros2 bag record runs on ros@orin2 into ~/bags. It keeps recording if the viewer closes or the tether comes off, and any viewer can stop it. A bag on "This computer" stops with the viewer and only gets what crosses the tether.
  • Topics. All, or Leave out with a pattern such as image|point_cloud to skip the camera streams. The panel shows the robot's free disk (yellow under 5 GB).
  • Stop sends Ctrl-C, so the recorder writes its metadata.yaml. A red BAG chip in the command bar shows one is running.
  • Camera video comes from the Recording panel instead: the ZED nodes write lossless .svo2 files on the robot, one per camera.

What to do with a bag afterwards is in Debugging, bags and data. The panel's Copy path gives the last bag as ros@orin2:/home/ros/bags/…, ready for rsync.

When something goes wrong

The order is always the same: make Talos safe, get the link back, then look.

  1. Switch out. Killed, Talos floats up. This works whatever the software is doing.
  2. Tether in. Untethered, nothing on op-top reaches the robot. Then Stop the tree and KILL in the viewer, as in Ending a run.
  3. Read the viewer. The FOG, DVL and battery chips, the Motion panel's error column, the camera cards.
  4. Read the logs. The launcher's nodes write to the journal on the Orin: journalctl -u ros_launcher --since "10 min ago" (SSH and logs).
  5. Restart one launch, not everything. Stop and Start the launch that failed in the launcher page. Restarting ros_launcher itself stops every node.
  • The viewer freezes or its pose goes stale: it releases manual control and the robot holds its last command. It never kills on its own (viewer docs). Pull the switch.
  • DVL lock lost or depth wrong mid-run: the MPC flies to wherever the estimate says Talos is, so a bad estimate means a bad run. Switch out, then work through When a sensor misbehaves.
  • Water in the hull: the leak sensor is no longer used, so nothing raises an alarm. Rising humidity on a board (state/humidity/poacboard, state/humidity/cameracage, status/humidity/smartbattery; plot them in the viewer) is the early sign (Housekeeping sensors). Any sign of water: switch out, Talos out, power off, and no dive until it's opened, dried and the PVT passes again.

After the test

Kill switch out, Talos out with two people, power off. Then, before anyone goes home:

  1. Copy the data off the Orin. Bags, SVOs and identification sessions exist only on the robot until copied.
  2. Commit what changed at the pool (prior map, parameters, models) in its own repo, then bump release.
  3. Tag release with the date and publish a GitHub release whose notes say what was tested and how it went. The README calls it "a backup for future pool tests, should software need to be rolled back".
  4. Write it up: what worked, what broke, and where the data is.
