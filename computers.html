Sensors and computing · Chapter 4

Computers and networks

One computer in the hull runs the whole robot. A few machines on the surface watch it, record it and keep its clock right. Which box does what, how they connect, and how your laptop joins in.

The short version
  • Every ROS node of the real robot runs on one Jetson AGX Orin (orin2). A service called ros_launcher starts them, from code copied to ~/colcon_deploy.
  • The circuit boards talk to the Orin over a CAN bus, can0. The MPC writes thruster speeds straight onto that bus.
  • ROS 2 runs over Zenoh: one router on the Orin, and laptops connect to it, on the LAN or through Tailscale. Both ways run over the tether.
  • The opbox, a Raspberry Pi, shares campus Wi-Fi with the robot network and serves the team clock. op-top, the team laptop, is the operator station.

The Orin does all the real-time work: sensors, estimation, control, vision, mapping and the mission tree. Everything outside the hull is optional while Talos runs; competition runs have no tether at all. This chapter covers the machines, the links between them, and the commands you'll use to reach them.

The network at a glance

The top box is inside the hull, the bottom one on the surface, joined by the tether. Pick a kind of traffic to see where it flows.

The Orin: Talos's only computer

The Orin is an NVIDIA Jetson AGX Orin, bought in 2022 (2026 design report). It's an ARM (aarch64) computer with an NVIDIA GPU, which the YOLO detector and the ZED depth processing use. It sits in the starboard hull tube, in the camera cage with the forward camera and the IMU.

Hostname
orin2, 192.168.1.24 on the robot LAN. Log in as user ros.
Software
Ubuntu 22.04, ROS 2 Humble, rmw_zenoh_cpp, the ZED SDK and the micro-ROS agent.
Interfaces
eth0 to the switch; can0 to the boards and can1 to the batteries (configure_jetpack.bash).
Serial
IMU on /dev/ttyTHS1, fibre-optic gyro on /dev/ttyTHS2 through a team-made board in the Orin's M.2 slot (talos_launch_mpc.yaml, 2024 TDR).
Cameras
Two ZED X Mini stereo cameras (forward and down) on the GMSL2 capture card. GMSL2 is a camera link: one coax cable per camera.

Why one computer

Sensors, the EKF, the 50 ms MPC and the thruster commands run on one machine with one clock, so a dropped tether can't stall control, and competition runs need no help from the surface. Raw camera streams are also far too big for the tether (below), so the detector has to run next to the cameras.

What starts the nodes: ros_launcher

Nobody types ros2 launch on the robot. At boot the Orin starts the remote launcher as a systemd service, ros_launcher. It does three jobs:

  • It starts the Zenoh router that every node and laptop connects to. If the router dies, the whole service restarts.
  • It serves a page at http://orin2:8080 with a Start and Stop button for each entry of a launch list. Nothing starts until someone presses Start.
  • It watches. An entry reads Running once every topic it lists has published.
Thrusters

Starting control_system on an enabled robot spins the thrusters. On the bench, keep the robot killed before you start it, and keep hands clear.

Which entries to start, in what order, and what the launcher page shows: Launching the stack, the pool list.

op-top, the operator laptop

op-top is the team laptop (user uwrt, with an RTX 4070 laptop GPU). Anything an operator does goes through it:

  • The Nereus viewer, the operator screen for both the simulator and the real robot. It enables and kills Talos, drives it, starts trees and records bags (The Nereus viewer).
  • The Nereus simulator, which needs the GPU to draw camera images for the real YOLO detector (Nereus).
  • The release workspace, ~/osu-uwrt/release. You deploy from here.
  • The pre-test checks, which read the robot over SSH, the launcher and ROS (Pool test day).
  • Its keyboard (optop_software). Its backlight is bright white while orin2 answers pings (every 2 s), dim white when two in a row go unanswered, and Talos's own LED colour once something publishes command/led.

The opbox

The opbox is the operator box. Inside it is a Raspberry Pi (Compute Module 4, Debian 12), hostname opbox. It has two jobs:

  • Internet for the robot LAN. The Pi joins campus Wi-Fi and shares that connection with the team router through its Ethernet port (192.168.5.69), using NAT: every LAN machine reaches the internet through the Pi's one Wi-Fi address. That's how the Orin and laptops get apt, pip and GitHub. Don't change its routing, DNS or Wi-Fi without asking whoever looks after it.
  • The team clock. It runs chrony as a time server (Time). A battery-backed clock keeps its time across reboots, even with no internet.

Its kill button, LEDs and buzzer (opbox_software) are not in use: the opbox button does not kill Talos (the robot side is commented out in main.cpp).

CAN: the link to the boards

CAN is a two-wire bus made for cars: every device on it hears every message, and each message carries an ID instead of an address. Talos's circuit boards talk to the Orin only over CAN. Each board has an RP2040 microcontroller and its own client ID in the team's protocol, CANmore. The Orin has two buses: can0 inside the hull, and can1, which runs out to the battery housings. The internal bus runs CAN FD, a faster variant: 1 Mbit/s for the header, 5 Mbit/s for the data (talos.h).

Two programs talk on can0:

  • The micro-ROS agent, copro_agent. Each board runs a small ROS client (micro-ROS), and this agent on the Orin turns its messages into ordinary ROS topics, such as state/depth/raw (copro_agent.launch.py). A second agent for can1 is in the same file but commented out ("until poac/batteries happy", 720bdd9), so battery data doesn't reach ROS today.
  • The MPC itself. mpc_controller opens a raw CAN socket and sends each ESC board one 8-byte frame every control tick: four signed 16-bit RPMs (send_thruster_cmd_canbus.c). Thrusters 0–3 go to client 2, thrusters 4–7 to client 3. The same numbers are published on command/requested_rpm so you can see them.

The MPC only writes to CAN on the real robot: its hardware_output parameter isn't off, the model file has a hardware section, the node isn't on simulation time, and can0 exists (configureHardwareOutput). On your laptop, in Nereus, the same node only publishes thruster_forces. The boards themselves: The circuit boards.

The robot LAN and the tether

Talos and the lab machines sit on one wired network, the robot LAN (192.168.1.0/24), behind the team router (192.168.1.1); the opbox sits on the router's upstream side. Inside Talos, the Orin, the DVL and the tether meet at the switch in the camera cage. For pool tests an Ethernet tether joins Talos to the LAN; for competition runs it comes off and Talos is on its own.

  • Names come from /etc/hosts. Add 192.168.1.24 orin2 to it on your laptop. (setup_hosts.bash adds an older orin, 192.168.1.23; Talos is orin2.)
  • A tether pulls on the robot. Fine for testing, but don't trust physics measured with it on: a tethered identification run fitted the tether's pull as buoyancy (System identification).
  • Losing the link doesn't stop Talos. The viewer's watchdogs only drop manual control; they never kill (ros_runtime.cpp). That's what lets untethered runs work. It also means a dropped link leaves Talos doing whatever it was last told.
  • The pool may differ. The map is the lab. Which router is used at the pool, and where op-top plugs in, isn't written down; ask a lead.
Kill

With the tether off or the link down, the only stop is the physical kill switch, the handle on the port bow window. Software KILL only works while your messages reach the robot. See Commanding Talos, the kill system.

ROS 2 over Zenoh

ROS 2 sends messages through a swappable middleware layer, the RMW. Talos uses rmw_zenoh_cpp. The team switched because Fast DDS, the default, was unreliable for them, and Zenoh copes better with heavy traffic (2025 TDR).

  • One router, on the Orin. The launcher starts rmw_zenohd, the Zenoh router. On Talos it loads zenoh_router_test.json5 (checked on the Orin, October 2026), which only listens, on TCP port 7447, and dials nobody. Nodes on the Orin find each other through it.
  • Laptops are clients. A client opens one TCP connection to the router, and every message to or from your laptop goes over it. The robot never opens a connection to you.
  • Both ends need the same RMW. A laptop on Fast DDS won't see a single topic. If topics are missing, check echo $RMW_IMPLEMENTATION first.
  • The ros2 daemon remembers the old RMW. Run ros2 daemon stop, or add --no-daemon to ros2 topic list.

The release repo's config_rmw.bash sets this up (pick the RMW with changermw); two environment variables do the same (below).

Follow a camera frame to your laptop

Camera images are the biggest thing on the network. Step one forward-camera frame from the sensor to the Nereus viewer on op-top.

Two habits follow:

  • From a laptop, subscribe to /compressed topics, never raw images or point clouds. Each laptop gets its own copy over the tether.
  • Measure topic rates one at a time. Several camera streams at once load the link and skew every rate. The pre-test checks expect at least 8 Hz on each compressed camera topic.

Time: why every clock has to agree

Every ROS message carries a timestamp from the clock of the machine that made it. Talos's own timing uses the Orin's one clock, so it's safe. The trouble starts with a second machine:

  • Bags. A bag recorded on op-top only lines up with one from the robot if the clocks agree.
  • The viewer. Its plots compare each stamp with the arrival time. Above 0.5 s they show clock offset, which is really offset plus delay (plots_ui.cpp).
  • Jumps. A clock that steps back more than about 10 s during a run makes the Nereus viewer drop TF.

Drag the sliders to see what a laptop makes of a message from the robot.

The fix is chrony, with the opbox as the one clock everyone follows. Today (checked October 2026) only half of that is in place: the opbox serves time, but the Orin still sets its clock from us.pool.ntp.org with systemd-timesyncd, which needs the opbox's internet. Check a machine with chronyc sources, or timedatectl where chrony isn't installed. The plan:

MachineFollowsSteps the clock
opboxThe internet pool when online, else its battery-backed clockn/a, it's the server
Talos (Orin)The opbox onlyOnly in its first 3 updates after boot. After that it slews (adjusts gradually), so a running stack never sees a jump.
op-topThe opbox, with the internet pool as a fallbackAny time it's more than 1 s off, for example after booting offline

Fallback: colcon timesync orin2 sets the robot's clock from your laptop over SSH (timesync.py).

Joining from your own laptop

Any Ubuntu 22.04 machine with ROS 2 Humble can join the robot's ROS graph (Setting up your machine). There are two ways to reach the Orin:

  • On the robot LAN, plugged into the team router: use orin2, with the hosts entry above.
  • From anywhere, with Tailscale, the team's private network of encrypted tunnels. It only reaches Talos while the tether is in and the opbox has internet. Ask a team lead to add your machine, and for the Orin's Tailscale name to use in place of orin2.
sudo apt install ros-humble-rmw-zenoh-cpp
source /opt/ros/humble/setup.bash
# team message types
cd ~/osu-uwrt/release
source install/setup.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
# connect to the Orin's router
export ZENOH_CONFIG_OVERRIDE=\
'mode="client";'\
'connect/endpoints=["tcp/orin2:7447"];'\
'scouting/multicast/enabled=false'
ros2 daemon stop
ros2 topic list --no-daemon | head
ros2 topic hz /talos/odometry/filtered

The override's three settings make your laptop a Zenoh client, point it at the router on the Orin (TCP port 7447), and stop it looking for other Zenoh machines on the local network. The quoted pieces join into one value.

  • Client mode works one way. Your laptop dials the Orin; nothing on the robot ever has to reach you. Keep it that way: never set up anything that makes the robot open connections to a personal machine.
  • Running the simulator at your desk? Keep it off the robot's graph: no ZENOH_CONFIG_OVERRIDE, and your own router (Setting up your machine, Building Nereus).
  • One operator at a time. Anyone connected can publish. Two viewers enabling the same kill-switch slot fight each other, and the viewer drops its enable when it sees another publisher there.

SSH, logs and the usual commands

SSH is for looking, not for running the stack. Use a key, not a password: the release repo's relationship.bash makes one and installs it. colcon deploy and the viewer's bag recorder need it.

ssh ros@orin2
# the launcher's own messages, live
journalctl -u ros_launcher -f -o cat
# is it up, what is it running
systemctl status ros_launcher
# last resort: stops every node
sudo systemctl restart ros_launcher
# raw CAN traffic (Ctrl-C to stop)
candump can0
# room left for bags
df -h ~
  • Node output is on the launcher page. Afterwards read ~/.ros/log/ on the Orin (Launching the stack, Logs). The journal holds only the launcher's own lines, and the router's if it dies.
  • Record bags on the robot. The viewer's Bagging panel records on the Orin, into /home/ros/bags/, and keeps recording if the link drops. Copy bags off with rsync (Debugging).

Getting code onto the Orin

~/colcon_deploy isn't a git checkout. Code goes on with colcon deploy orin2, a command the team added to colcon (colcon_riptide). It copies package sources from your release workspace to ~/colcon_deploy/src and builds them there, because the Orin is ARM and op-top is x86: binaries built on op-top won't run on the Orin (Setting up your machine, colcon deploy). Don't edit code, run apt upgrade or rebuild on the Orin by hand: nothing tracks those changes, and the next deploy overwrites them.

Where this lives: riptide_launch/remote_launch (launcher, launch lists), riptide_release/scripts (Orin setup, Zenoh configs), riptide_setup/colcon_riptide (deploy, timesync), opbox_software, optop_software, titan_canmore (CAN IDs).
