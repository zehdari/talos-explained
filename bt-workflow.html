Autonomy · Chapter 4

Writing and testing trees

How to change what Talos does on its own: edit a tree, add a C++ node when the existing ones can't do the job, test it alone, then fly it in Nereus before the pool.

The short version
  • Trees are XML files in riptide_autonomy/trees/. doTask reads the file fresh on every run, so a tree edit needs no rebuild.
  • Edit the competition trees as text: Groot can overwrite their subtrees.
  • New behaviour means a new C++ node. btassistant.py writes one; rebuild with --cmake-clean-cache so it gets registered, then relaunch doTask.
  • Three checks: the node's unit tests, test_all_trees_load (every tree must build) and checkBT (the XML against the C++).
  • Fly it in Nereus first, from the viewer's Autonomy panel, with Talos starting next to the task.

The practical side of behaviour trees, Talos's nodes and the competition tree. Everything here is on the autonomy-mapping branch of riptide_autonomy (package riptide_autonomy2), which uses BehaviorTree.CPP v3.

The loop

A change to numbers or structure in a tree skips steps 2 to 4. A new node goes through all seven.

Where things live

All in the riptide_autonomy repo: the trees in trees/, one header per custom node in include/riptide_autonomy/bt_<kind>s/, a test per node in test/.

The files you will edit most are the two competition trees, RepairCompMpcTree.xml and RescueCompMpcTree.xml: the trees written for riptide_mpc, called the Comp Mpc files below. Older files without "Mpc" in the name, such as RepairCompTree.xml, were written for the legacy controller.

Editing a tree

Groot is a visual editor: you drag nodes into a tree and it writes the XML. Use the team's Groot fork, a desktop app for BehaviorTree.CPP v3 and the editor the riptide_autonomy README recommends. Install it with install_groot.bash from riptide_setup; it builds the fork in ~/groot and adds a groot command.

Other editors, and BehaviorTree.CPP v4

The other editors on the team's GitHub don't fit today: btstudio writes v4 XML and ignores workspace.xml, and the VS Code extension is an empty, archived repo. A port of riptide_autonomy to v4 sits on the bt4 branch (Oct 2026), not merged. Until it is, everything here is v3.

Groot overwrites the file's subtrees

Opening a file, Groot draws the file's trees, then loads every subtree in .groot/workspace.xml into the tab of the same name, replacing the file's copy. Saving writes every tab back to the file (mainwindow.cpp L427, L1179, L508). Open and save RepairCompMpcTree.xml and seven of its subtrees turn back into the workspace's older copies (PrimitiveMovePosition, SurfaceTree, ...). It also adds every workspace subtree the file didn't have.

So edit the Comp Mpc files as text, and read git diff after any Groot save.

In a text editor, keep the structure Groot expects: one <BehaviorTree> per tree, a <TreeNodesModel> listing every custom node and subtree, and every port written out. Empty attributes trip Groot up too: the team writes empty retreat paths as ";" rather than "" "so Groot can save" (commit debcd47).

The workspace file and the tree files

BehaviorTree.CPP loads one file and nothing else, so every tree file carries its own copy of each subtree it uses. workspace.xml was meant to be the master copy: Groot loads it into every file you open, checkBT checks its node models against the C++, and checkBT --apply-workspace copies its subtrees into tree files, replacing any with the same ID.

In practice the newest work is in the tree files. The workspace holds 71 subtrees and 38 node models, but not 4 header nodes (CenterDetection, FollowPath, LatestDetection, MapConverged) or the simple nodes AddWaypoint and AddArc. The Mpc subtrees that fly the competition (SearchMpc, SpinTreeMpc and others) exist only in the two Comp Mpc files.

  • Edit the file you will run. The two Comp Mpc files differ only in their main tree (repair_mission 1 or 0), so a subtree change goes into both.
  • Don't run --apply-workspace on the whole folder. It would put the workspace's older copies of seven subtrees into the Comp Mpc files.
  • To share a subtree, paste its new <BehaviorTree> into workspace.xml by hand too.

Ports and the blackboard

The port rules ({key} versus a literal, every port a string, SubTree ports naming a blackboard entry) are in Behaviour trees: the blackboard and ports and Subtrees and remapping. One catches people out in practice: an empty SubTree port is not a default.

Groot writes z="" for every unset port. On a leaf node's input that means "use the default". On a SubTree port it links to the parent's entry named "", which every empty output port writes to, so the subtree reads another node's value. RepairCompMpcTree.xml has such ports (target_3=""), and checkBT skips empty values, so nothing warns you.

Tunables go in a SetBlackboard at the top of the subtree, its name saying what the number means, with units. SearchMpc starts with name="Once seen, hold there at most this long for the map to converge (s)" output_key="hold_secs" value="8".

Adding a subtree

Most changes are a new or changed subtree, not a new node. Three pieces, all in the file you run (DeeperThan is the example node written below):

<!-- 1. The subtree, beside the
     file's other <BehaviorTree>s -->
<BehaviorTree ID="HoldUnlessRising">
  <ReactiveSequence>
    <Condition ID="DeeperThan"
      max_age_secs="" z="{ceiling}"/>
    <Action ID="Wait"
      seconds="{seconds}"/>
  </ReactiveSequence>
</BehaviorTree>
<!-- 2. Its ports, in the same
     file's <TreeNodesModel> -->
<SubTree ID="HoldUnlessRising">
  <input_port name="ceiling"
    required="true"/>
  <input_port name="seconds"
    required="true"/>
</SubTree>
<!-- 3. The call, in the parent tree.
     Port values name its entries. -->
<SetBlackboard
  name="Hold this long (s)"
  output_key="hold_secs" value="10"/>
<SubTree ID="HoldUnlessRising"
  __shared_blackboard="false"
  ceiling="ceiling"
  seconds="hold_secs"/>

BehaviorTree.CPP ignores the model (2), but Groot draws the ports from it and checkBT reads it (CheckBT.cpp). Keep __shared_blackboard="false" on the call (3), like the Comp Mpc files, so the subtree sees only what its ports pass in. Copy all three pieces into both Comp Mpc files.

Writing a node

Write one for a new topic, service or calculation. Each node is one header in include/riptide_autonomy/bt_<kind>s/: a class deriving from UWRTActionNode (anything that takes time), UWRTConditionNode (a yes/no answer now) or UWRTDecoratorNode (changes how one child runs), all in UwrtBtNode.hpp.

You write providedPorts() (the node's ports) and rosInit() (its subscribers and clients; doTask calls it once the tree is built, and rosNode() is still null in the constructor).

What each base class needs, and the helpers
Base classUse forYou write
UWRTActionNodeAnything that takes timeonStart() once, then onRunning() each tick until SUCCESS or FAILURE; onHalted()
UWRTConditionNodeA yes/no answer nowtick(): SUCCESS or FAILURE, never RUNNING
UWRTDecoratorNodeA decorator: changes how one child runstick(), ticking child_node_
  • static BT::PortsList providedPorts() lists UwrtInput("name", "description") and UwrtOutput(...).
  • From autonomy_lib.hpp: tryGetRequiredInput<T>(this, "port", default) (warns if empty), tryGetOptionalInput (doesn't), postOutput<T>, and topic constants such as ODOMETRY_TOPIC, relative so they resolve under /talos.
  • UwrtBtNode gives you lookupTransform(from, to, tf), false if the transform isn't available (L21).

File name, class name and XML ID must be the same word: the code that registers nodes is generated from the file names. A node that finishes within one tick can instead be a function in SimpleActions.simple.cpp.

That generated code is where people get caught. CMake, which colcon runs for each package, works in two phases: configure decides what to build and generates code, and build compiles. colcon builds every time but configures only when there is no build folder yet or the CMake arguments changed. So after adding a header, build with --cmake-clean-cache, which forces a configure.

The BT assistant

btassistant.py does the chores: create writes a new node's header and test, reconfigure_autonomy does the clean rebuild, and check runs the checks. It edits src/ even when run from the installed copy.

Worked example: a depth guard

DeeperThan is a condition: SUCCESS while Talos is deeper than a given z. Inside a ReactiveSequence, which re-checks it on every tick, it stops a running subtree when Talos rises too far. It is not in the team's repo; the files are in tools/bt-workflow/example/. Six steps, from an empty header to a run; tap one to open it.

1. Generate the files

cd ~/osu-uwrt/release
ros2 run riptide_autonomy2 \
  btassistant.py create \
  condition DeeperThan --no-rebuild

That writes DeeperThan.btcondition.hpp (a "Hello world" tick()) and TestDeeperThan.cpp with one skipped test.

2. Fill in the header

Two ports (z, max_age_secs), an odometry subscription made in rosInit() that keeps the latest z and its time, and this tick():

BT::NodeStatus tick() override {
  auto z = tryGetRequiredInput<double>(
    this, "z", 0.0);
  auto maxAge =
    tryGetOptionalInput<double>(
      this, "max_age_secs", 0.5);
  bool stale = !haveOdom ||
    (rosNode()->now() - lastStamp)
      .seconds() > maxAge;
  if(stale) {
    return BT::NodeStatus::FAILURE;
  }
  return lastZ < z
    ? BT::NodeStatus::SUCCESS
    : BT::NodeStatus::FAILURE;
}
The whole header 
#pragma once
#include "riptide_autonomy/autonomy_lib.hpp"

using nav_msgs::msg::Odometry;

// SUCCESS while Talos is deeper than `z`
// (odometry z: 0 at the surface, negative
// below). FAILURE before any odometry, or
// when the newest is older than
// `max_age_secs`.
class DeeperThan
  : public UWRTConditionNode {
public:
  DeeperThan(const std::string& name,
    const BT::NodeConfiguration& config)
    : UWRTConditionNode(name, config) { }

  static BT::PortsList providedPorts() {
    return {
      UwrtInput("z", "Succeed while "
        "odometry z is below this "
        "(m, negative underwater)"),
      UwrtInput("max_age_secs", "Fail if "
        "the newest odometry is older "
        "than this (default 0.5)")
    };
  }

  void rosInit() override {
    auto onOdom =
      [this](Odometry::SharedPtr msg) {
        lastZ = msg->pose.pose.position.z;
        lastStamp = rosNode()->now();
        haveOdom = true;
      };
    odomSub = rosNode()->
      create_subscription<Odometry>(
        ODOMETRY_TOPIC, 10, onOdom);
  }

  BT::NodeStatus tick() override {
    auto z = tryGetRequiredInput<double>(
      this, "z", 0.0);
    auto maxAge =
      tryGetOptionalInput<double>(
        this, "max_age_secs", 0.5);
    bool stale = !haveOdom ||
      (rosNode()->now() - lastStamp)
        .seconds() > maxAge;
    if(stale) {
      return BT::NodeStatus::FAILURE;
    }
    return lastZ < z
      ? BT::NodeStatus::SUCCESS
      : BT::NodeStatus::FAILURE;
  }

private:
  bool haveOdom = false;
  double lastZ = 0;
  rclcpp::Time lastStamp;
  rclcpp::Subscription<Odometry>::SharedPtr
    odomSub;
};

The pattern of SeenRecently: subscribe in rosInit(), keep the latest value, answer from it in tick(), fail on stale data.

3. Write the test

The test publishes fake odometry at z = −1.2 m and expects SUCCESS, then at −0.3 m and expects FAILURE. Two more cases check that it fails before any odometry and on stale odometry.

The test file 
#include "autonomy_test/autonomy_testing.hpp"

using namespace std::chrono_literals;
using nav_msgs::msg::Odometry;

namespace {
Odometry odomAt(double z) {
  Odometry msg;
  msg.pose.pose.position.z = z;
  return msg;
}

std::shared_ptr<BT::TreeNode> deeperThan(
  std::shared_ptr<BtTestTool> tool,
  double z)
{
  BT::NodeConfiguration cfg;
  cfg.input_ports["z"] = std::to_string(z);
  return tool->createLeafNodeFromConfig(
    "DeeperThan", cfg);
}
}

TEST_F(BtTest,
  test_DeeperThan_fails_before_any_odometry)
{
  auto node = deeperThan(toolNode, -0.5);
  ASSERT_EQ(node->executeTick(),
            BT::NodeStatus::FAILURE);
}

TEST_F(BtTest,
  test_DeeperThan_follows_depth)
{
  auto node = deeperThan(toolNode, -0.5);
  auto pub = toolNode->create_publisher<
    Odometry>(ODOMETRY_TOPIC, 10);
  // let discovery finish
  toolNode->spinForTime(0.3s);
  pub->publish(odomAt(-1.2));
  toolNode->spinForTime(0.2s);
  ASSERT_EQ(node->executeTick(),
            BT::NodeStatus::SUCCESS);
  // above the limit
  pub->publish(odomAt(-0.3));
  toolNode->spinForTime(0.2s);
  ASSERT_EQ(node->executeTick(),
            BT::NodeStatus::FAILURE);
}

TEST_F(BtTest,
  test_DeeperThan_fails_on_stale_odometry)
{
  auto node = deeperThan(toolNode, -0.5);
  auto pub = toolNode->create_publisher<
    Odometry>(ODOMETRY_TOPIC, 10);
  toolNode->spinForTime(0.3s);
  pub->publish(odomAt(-1.2));
  toolNode->spinForTime(0.2s);
  ASSERT_EQ(node->executeTick(),
            BT::NodeStatus::SUCCESS);
  // older than the default 0.5 s
  toolNode->spinForTime(0.8s);
  ASSERT_EQ(node->executeTick(),
            BT::NodeStatus::FAILURE);
}

Unit tests

The tests use GTest, Google's C++ unit-test framework. They are only compiled with -DAUTONOMY_BUILD_TESTS=ON, into one program, test_nodes: 178 test cases in 36 files on this branch, about 95 s for the lot. Each test builds one node with the real plugin libraries, publishes fake topics and ticks it.

Checking the XML: checkBT

Run it on your laptop: deploy builds leave it out (CMakeLists.txt).

cd ~/osu-uwrt/release/src/riptide_autonomy
# the workspace, then every tree
ros2 run riptide_autonomy2 checkBT
# one file
ros2 run riptide_autonomy2 checkBT \
  $PWD/trees/MyTree.xml

It checks the C++ nodes against the models (missing or extra nodes, port names and directions; header nodes only, so simple nodes such as AddWaypoint are never reported missing), unbalanced braces such as {key|, and SubTree port values that no earlier node writes (skipping empty values and numbers). It answers "no" to its fix-it prompts unless you pass -a (ask) or -y (yes to all), and exits 2 if anything is unresolved.

What it reports on the team's trees today

152 warnings (mostly ports filled further up, out of its sight) and 8 issues of three kinds:

[ERROR] [btchecker]: Node SeenRecently: port min_score has a different direction (inout_port) in Groot than in the c++ implementation (input_port).
[ERROR] [btchecker]: Node CenterDetection has a c++ implementation but is missing from the Groot workspace.
[ERROR] [btchecker]: Node CompareNums in tree TorpedoTree (trees/DemoTableTree.xml) has a malformed blackboard reference in port "a": {repair_mission|. Check that every '{' has a matching '}'.
checkBT edits your files
  • It saves every file it checks back in place, so a file can come back reformatted. Commit first and read git diff after.
  • Its "make one?" fix adds a SetBlackboard as the first child of the SubTree's parent. If that parent is a decorator such as ForceSuccess, the tree no longer loads. An older checkBT did this to ActuatorTrees.xml and SurfaceTree.xml.
  • It crashes on a tree file with no <TreeNodesModel>.

Running a tree

Trees are run by doTask, which the robot's launch (bringup) starts as node /talos/autonomy (DoTask.cpp, messages in riptide_msgs). The goal is the tree file's full path, sent to the action /talos/autonomy/run_tree (riptide_msgs2/action/ExecuteTree). doTask ticks the tree every 30 ms on its own thread and answers with error and returncode.

The tree list, the stack topic, its log file
List
/talos/autonomy/list_trees: every .xml in the source trees/ folder and in the installed copy.
Stack
/talos/autonomy/tree_stack: the nodes running now. The action's feedback is never sent; read this topic.
Log file
~/btlogs/BTLog_YYYY_MM_DD_HH:MM:SS.fbl: every status change, for Groot's Log Replay (parameter log_file_dir).
Bag trigger
/<hostname>/autonomy/bag_trigger, every second: true while a tree runs. Groot's live monitor is off (enable_zmq: false).

The file is read when the goal arrives, so an edit in src/riptide_autonomy/trees/ is live on the next run. On the robot, deploy again after editing.

The team runs trees from the Nereus viewer, in the sim and at the pool: open Autonomy, pick a tree, press Enable, then Start. The list shows only trees outside install/, by file name. Start stays grey until the viewer's Enable is on, Talos's pose is coming in, and no other viewer is using the same Enable switch. Stop, or the viewer's Kill button, cancels the tree, whoever started it. The physical kill switch does not (Behaviour trees). How a run ends:

After a run

  • Info messages go to doTask's log: the launch terminal and /rosout.
  • The stack without the viewer: ros2 topic echo /talos/autonomy/tree_stack.
  • The .fbl log, doTask's record of every status change, stays on the computer that ran it, the Orin at the pool. Copy it off (rsync -a ros@orin2:btlogs/ ~/btlogs/) and open it in Groot's Log Replay mode.
  • If doTask crashed, it stays down (respawn=False) until you relaunch.

Committing

riptide_autonomy is a submodule of riptide_release (src/riptide_autonomy, branch autonomy-mapping).

  1. Work on a branch made from autonomy-mapping.
  2. Commit the header, its test and the trees that use the node. For Groot's palette, also paste the node's model (its <Condition> or <Action> entry in your tree file's <TreeNodesModel>) into the <TreeNodesModel> of workspace.xml, by hand. Don't use Groot's Add To Workspace: it only reaches the file through a Groot save (the trap above).
  3. Leave test and demo trees out: everything in trees/ shows up in everyone's viewer list.
  4. Merge into autonomy-mapping, then bump the submodule in riptide_release so a deploy picks it up (Pool test day).

Common mistakes

Symptom first: find what you're seeing.
