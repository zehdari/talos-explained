Running Talos · Chapter 5

Debugging, bags and data

"Talos isn't working" is never the real problem. This chapter is how to find the real one: what to check in what order, what each failure has looked like before, and how to record a run so you can study it at home.

The short version
  • Work down the chain: network, launches, topic rates, enable, values, logs. Stop at the first step that fails.
  • Live, use the ros2 command line (with --no-daemon over Zenoh), the launcher page for node output and the Nereus viewer's Plots.
  • Record a bag of every run, on the robot. The navigation and control topics are about 0.4 MB/s; the detector's annotated image alone adds about 2.3 MB/s (measured in sim). Leave camera images and depth maps out; record camera video as .svo2.
  • A bag is a database file you can read in twenty lines of Python, replay into the viewer, or replay into a node with new parameters to test a fix without the pool.
  • header.stamp is when something was measured, on the clock of the machine that stamped it. Compare stamps only from the same clock.

Work down the chain

Talos is a chain: your laptop reaches the Orin over Zenoh, the launcher starts the nodes, the nodes publish topics, the kill system lets the thrusters move, and the code turns all of that into behaviour. A break anywhere looks the same from the deck: nothing happens. So check the links in order, cheapest first.

Before a pool test, pretest bench runs most of this chain for you: reachability and clock, the bench launches, topic rates, kill and ESC state, the MPC's live parameters and stationary drift (Pool test day).

Symptoms seen on Talos

Each entry below happened, or is written into the code as a known way to fail. Search for the words you see (a log line, a topic, a flag), or open a part of the system. Each entry says where it comes from: the code, a config, or the chapter that explains it.

The ros2 command line

Everything on Talos is a topic, a service, an action or a parameter, and the ros2 tool can look at all of them from any machine on the robot's Zenoh network. First, a shell that can see Talos (details in Computers and networks):

source /opt/ros/humble/setup.bash
# riptide_msgs2 and friends, or echo
# can't decode them
source ~/osu-uwrt/release/install/setup.bash
# applies your RMW choice (changermw
# picks zenoh; rmw prints it)
source ~/osu-uwrt/release/scripts/dds_scripts/config_rmw.bash
# the daemon may still hold an old RMW
ros2 topic list --no-daemon | grep /talos

The RMW is the layer that carries ROS messages (Zenoh on Talos). The ros2 daemon is a background process that caches what it has seen; --no-daemon asks the network directly.

Topics

# rate: 400 Hz on Talos
ros2 topic hz /talos/vectornav/imu
# one message, then exit
ros2 topic echo /talos/state/kill --once
# both ESC boards, in turn
ros2 topic echo --no-arr \
  /talos/state/thrusters/telemetry
# just the position
ros2 topic echo /talos/odometry/filtered \
  --field pose.pose.position
# who publishes, with what QoS
ros2 topic info -v \
  /talos/command/software_kill
  • hz measures what reaches you. From a laptop, a camera's rate is the tether's rate. Measure one stream at a time, or on the Orin.
  • --field keeps the output to the part you care about; --no-arr hides arrays (covariances, per-ESC telemetry).
  • One topic can carry several sources. ESC telemetry alternates between the two boards: start_thruster_num 0 and 4. Both must show disabled_flags: 0.
  • info -v lists every publisher and its QoS (delivery settings). It is how you find a second publisher you didn't expect, like a competing operator on the kill topic.

Nodes and parameters

ros2 node list
# its topics, services, actions
ros2 node info /talos/mpc_controller
ros2 param get /talos/mpc_controller \
  table_mode
ros2 param set /talos/mpc_controller \
  table_mode false
# then diff against the deployed
# riptide_mpc/config/mpc.yaml
ros2 param dump /talos/mpc_controller \
  > live.yaml

A parameter set at the pool lives until the node restarts. The pre-test checks compare the node's live parameters with the deployed mpc.yaml to catch tuning left behind.

Services, actions and TF

# detector: switch to the down camera
ros2 service call \
  /talos/set_camera_is_dfc \
  std_srvs/srv/SetBool "{data: true}"
# tare the FOG: Talos still and level
ros2 action send_goal /talos/gyro/tare \
  riptide_msgs2/action/TareGyro \
  "{num_samples: 100000,
    timeout_seconds: 20}"
# where the DVL sits on the robot
ros2 run tf2_ros tf2_echo \
  talos/base_link talos/dvl_link
# the whole TF tree, as a PDF
ros2 run tf2_tools view_frames

Services and actions change things on the robot. Read what they do before calling one (Appendix A lists them).

Where the logs are

Nodes started by the launcher have no terminal. Their output goes to four places, and each answers a different question:

WhereWhat's in itUse it for
Launcher page
http://orin2:8080		Every launch's output, live, only while the page is open: nothing is kept. Cyan while starting, green while running, orange while stopping (the launcher).A node that crashes on start-up: open the page, then restart the launch.
/rosoutEvery node's log messages (info, warnings, errors) as a topic.Watching warnings from a laptop: ros2 topic echo /rosout --field msg, or rqt_console.
journalctl -u ros_launcherThe launcher itself: launches starting, stopping, dying; the Zenoh router's crash output."Why did everything stop?"
~/.ros/log/ on the Orin (over SSH)ROS 2's log file per node, and a launch.log per launch.Anything from before you opened the launcher page; reading back a run.

The launcher sends each line of a launch's output (stderr merged into stdout) to the pages open at that moment, then drops it; it never reaches the journal (launcher.py). The MPC's lines worth searching for, all from mpc_controller_node.cpp:

  • Hardware output ENABLED or Hardware output disabled (…): at start-up, says whether RPM goes to the ESCs.
  • Table mode ON: thruster RPM capped at 500
  • Stale sensors, using EKF instead: … and No fresh odometry; thrusters off
  • MPC failed, thrusters off: …, MPC produced a nonfinite command, CAN thruster command failed
  • MPC solve … ms exceeds the control period

Plotting live

The Nereus viewer's Plots window (Windows › Plots) is the team's live plotter, on the robot and in sim (Chapter 3):

  • Lanes of series on one time axis; type plot odom z in the search (Ctrl+P), or right-click a Motion table row for Plot Z (actual, commanded, error).
  • Time from Header (default) plots each sample at its stamp. On the robot a row that says clock offset 1.2 s means your clock and the Orin's disagree.
  • A row says why a line stopped: stale 4.2 s, no publisher.
  • Export visible span as CSV writes ~/Documents/Nereus/plots/ for a quick look in Python or a spreadsheet.

Recording bags

A bag is a recording of topics: every message, with the time the recorder received it. Record one for every pool run; a run that wasn't recorded can't be debugged at home.

  • On the robot. The viewer's Bagging panel runs ros2 bag record on ros@orin2 into ~/bags. It keeps going if the tether drops, and it gets every message, not just what crossed the tether (Pool test day).
  • By hand, the panel's command with the launcher's environment (from talos_uwrt_panels.yaml):
source ~/colcon_deploy/install/setup.bash
source ~/uwrt_config/source/zenoh_server.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
# everything except camera images,
# depth maps and point clouds
SKIP='image|point_cloud|depth_registered'
SKIP+='|confidence_map|annotated'
ros2 bag record -a -x "$SKIP" \
  -o ~/bags/run_$(date +%F_%H%M%S)
# Ctrl-C stops it and writes metadata.yaml
# then: duration, topics, counts
ros2 bag info ~/bags/run_...
# bags stay on the robot until copied
rsync -a ros@orin2:/home/ros/bags/ ~/bags/
Format
A folder holding metadata.yaml and one .db3 file, an SQLite database (a single-file database that Python's sqlite3 opens directly). That is Humble's default. The other format, MCAP, needs its storage plugin installed (-s mcap).
Killed recorder
No metadata.yaml. ros2 bag reindex <folder> rebuilds it.
Leave out
  • Camera images, unless you need them: the image pattern above.
  • Depth and confidence maps. The image pattern misses the ZED's depth/depth_registered and confidence/confidence_map (wrapper), and depth is on (ffc_config.yaml). They are the largest streams on the robot: about 140 MB/s of depth per camera (the figure below).
  • The detector's annotated image. It is drawn only while something subscribes, and -a subscribes (yolo_orientation.py).
For camera video, the viewer's Recording panel writes lossless .svo2 files instead.
Presets
Selected plus a preset records just one task's topics: Random pinger comes from talos_uwrt_panels.yaml; Save adds your own to ~/.config/nereus/bag_presets.yaml (viewer.md).
Sim
Add --use-sim-time so bag times follow the simulator's /clock (Perception, Chapter 11).
Camera files
An .svo2 plays back through the ZED wrapper in place of a live camera: ros2 launch zed_wrapper zed_camera.launch.py camera_model:=<model> svo_path:=<file> (zed_camera.launch.py; needs the ZED SDK).
Disk
The Bagging panel shows the robot's free space, yellow under 5 GB.

Two lessons from the numbers. Of the core topics, the 400 Hz IMU and 475 Hz FOG are about four fifths. Keep them anyway: no estimator can be replayed without them. With a camera, the camera is the bag: the annotated image alone is about six times all the core topics.

Reading a bag in Python

rosbag2_py reads a bag message by message; deserialize_message turns the stored bytes (CDR, the format ROS sends messages in) back into the ROS message. This reads the EKF and the DVL from the 2026-10-26 pool session and compares their horizontal speeds (read_bag.py):

import sys
import numpy as np
import rosbag2_py
from rclpy.serialization import deserialize_message
from rosidl_runtime_py.utilities import get_message

reader = rosbag2_py.SequentialReader()
reader.open(rosbag2_py.StorageOptions(uri=sys.argv[1], storage_id='sqlite3'),
            rosbag2_py.ConverterOptions('cdr', 'cdr'))
types = {t.name: t.type for t in reader.get_all_topics_and_types()}
want = ['/talos/odometry/filtered', '/talos/dvl_twist']
# skip everything else
reader.set_filter(rosbag2_py.StorageFilter(topics=want))

rows = {k: [] for k in want}
while reader.has_next():
    # t_recv: when the recorder got it (ns)
    topic, data, t_recv = reader.read_next()
    msg = deserialize_message(data, get_message(types[topic]))
    # when it was measured
    stamp = msg.header.stamp.sec + msg.header.stamp.nanosec * 1e-9
    v = msg.twist.twist.linear
    if topic.endswith('filtered'):
        rows[topic].append([stamp, msg.pose.pose.position.z, np.hypot(v.x, v.y)])
    else:   # dvl_link is turned 45° from the body
        rows[topic].append([stamp, np.hypot(v.x, v.y), t_recv * 1e-9 - stamp])

odom, dvl = (np.array(rows[k]) for k in want)
print(f'odometry: {len(odom)} msgs, depth {odom[:, 1].min():.2f} to {odom[:, 1].max():.2f} m')
print(f'dvl: {len(dvl)} msgs, median age when recorded {np.median(dvl[:, 2]) * 1000:.0f} ms')
# EKF speed at the DVL's stamps
ekf = np.interp(dvl[:, 0], odom[:, 0], odom[:, 2])
print(f'horizontal speed, EKF minus DVL: rms {np.sqrt(np.mean((ekf - dvl[:, 1]) ** 2)):.3f} m/s')
$ python3 read_bag.py talos_20261026_204748/bag
odometry: 37009 msgs, depth -3.43 to -0.76 m
dvl: 9856 msgs, median age when recorded 126 ms
horizontal speed, EKF minus DVL: rms 0.022 m/s
  • Source the workspace first (/opt/ros/humble and release/install), or get_message can't find riptide_msgs2 types.
  • Filter topics: deserializing 500,000 IMU messages you don't need is most of the run time. Images are slowest of all.
  • Index by header.stamp for anything about physics; use the receive time only to ask how late something arrived.
  • Save to .npz once and analyse from that. Reading a 20-minute bag takes seconds to minutes; loading an array takes milliseconds.

Replaying a bag

ros2 bag play publishes a bag's messages again, in time. With --clock it also publishes /clock, and nodes started with use_sim_time:=true take their time from it instead of the computer's clock, so they live in the bag's time. Two uses:

Into the viewer

The viewer draws a real robot from map → talos/base_link in TF, so a bag with /tf, /tf_static and odometry is enough to watch a run again, with the recorded thrust as arrows:

source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash
# a private graph: nothing here reaches
# the robot, nothing reaches in
unset ZENOH_CONFIG_OVERRIDE \
  ZENOH_ROUTER_CONFIG_URI \
  ZENOH_SESSION_CONFIG_URI
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_LOCALHOST_ONLY=1
export ROS_DOMAIN_ID=91
# runs until Ctrl-C; see below
python3 static_tf_from_bag.py BAG
cd ~/osu-uwrt/release/nereus
./build/ros-viewer/nereus-viewer \
  --scenario /tmp/resolved.json \
  --pose-source estimate \
  --use-sim-time true \
  --robot-only --thrust
# --clock 100: publish /clock at 100 Hz
# --start-offset 622: start 622 s in
ros2 bag play BAG --clock 100 \
  --start-offset 622 \
  --topics /tf /tf_static \
  /talos/odometry/filtered \
  /talos/thruster_forces /talos/state/kill
  • Isolate the replay. On the team's Zenoh network the bag's messages would mix with the live robot's, and a replayed command could reach it. A local-only FastDDS domain can't.
  • --start-offset skips /tf_static: most static frames (sensor mounts that never move) are published only once, at start-up (one is re-sent every 2 s). static_tf_from_bag.py re-publishes the bag's statics; without it TF can't join world to odom.
  • robot.launch.py runs the viewer on wall-clock time for the live robot; for a bag, start it yourself with --use-sim-time true. Make /tmp/resolved.json with .venv/bin/python -m nereus.packs resolve content/packs/scenarios/talos_uwrt -o /tmp/resolved.json. The full recipe is viewer_replay.sh.

Into a node, with new parameters

The most useful offline check: replay a run's inputs into a node, change one thing, and compare its output with what the robot did. The EKF lag (symptom above) was worked out this way, without a pool test:

  1. Play only the EKF's inputs: vectornav/imu, gyro/twist, dvl_twist, depth/pose. Not its old output, or two EKFs publish odometry/filtered.
  2. Run robot_localization's ekf_node with talos_ekf.yaml, use_sim_time:=true, under the robot's name (-r __ns:=/talos -r __node:=ekf_localization_node) and with the change under test.
  3. Publish the sensor mounts: the bag's static TF, plus dvl_link, which is on /tf (it hangs off a revolute joint), not /tf_static.
  4. Record the new odometry/filtered and compare. First run it unchanged: the replay must match the live EKF, or nothing after means anything. It did, exactly.

Applied to the EKF, this found a fix that cuts the velocity lag from 351 to 96 ms (results in Where am I?, Finding the fix).

The same recipe works for mapping (replay detected_objects, odometry and TF) and for anything else whose inputs you recorded. The MPC's identification fits can be redone offline too: ros2 run riptide_mpc identify_fit --dir <session copy> --model <prior> refits a saved session.

Stamps and clocks

Every message in a bag carries two times:

  • header.stamp: set by the publisher, meant to say when the data was measured, on the publisher's clock.
  • Receive time: when the recorder got it, on the recorder's clock.

The difference is a message's age when recorded. On a bag recorded on the Orin, both clocks are the same, so the age is real latency plus any deliberate back-dating:

  • The DVL is 125 ms old by design. The driver back-dates each stamp by the DVL's own dt2, the time from the echo to the output (dvl_driver.cpp). The stamp says when the water moved, which is what a filter needs.
  • The MPC's reference is ~32 ms old because it is stamped at the start of the tick and published after the solve (median 30 ms).
  • The bench bag's ages are all about −37 ms. It was recorded on a team member's computer over the network, not on the Orin. Messages can't arrive before they were sent: that computer's clock was behind the Orin's, and every cross-machine comparison from that bag is off by that much. Its dvl_twist isn't back-dated: the bench launch file runs fake_dvl.py, not the DVL driver.

What this means when debugging:

  • Compare stamps only from one clock. Anything that checks freshness against its own clock breaks across machines with different clocks: the MPC stops the thrusters when the newest odometry's stamp is 0.5 s old (odom_timeout), and its estimator drops sensor messages stamped more than 1 s ago.
  • Keep the clocks together. The opbox runs a chrony time server, and the robot and laptops are meant to follow it (Computers and networks). chronyc sources says what a machine really follows; chronyc tracking how far off it is. The older colcon timesync orin2 sets the Orin's date over SSH as text to the second, so it is only good to about a second (timesync.py).
  • Don't step a running robot's clock. A backwards step of more than about 10 s makes the Nereus viewer drop TF.
  • In sim, everything runs on /clock. A node that reads the clock before /clock arrives gets zero; that is the cause of the sim-only mapping offset bug.
