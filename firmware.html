The vehicle · Chapter 4

Firmware on the boards

Every circuit board in Talos has a small computer of its own, running C that the team wrote. It reads sensors, switches power, spins thrusters and decides whether Talos may move. This chapter is that code: how it is built, how it talks over CAN, how it keeps Talos safe, and how to flash and debug it.

The short version
  • Each board has a Raspberry Pi RP2040 microcontroller. Its firmware lives in titan_firmware: one CMake project per board, on the Pico SDK, sharing one set of libraries and one main loop.
  • Boards talk over CAN with CANmore, the team's protocol. The frame ID carries the board's client ID, the direction and a channel or sequence number, so all the data bytes are payload.
  • Each board is a micro-ROS node. The copro_agent on the Orin bridges its topics into ROS. Thruster RPMs skip ROS: the MPC writes raw CAN frames straight to the ESC boards.
  • Every board starts killed and kills itself if it loses the agent. The POAC board decides kill from its four slots (the hull switch and three software ones); the other boards kill themselves if state/kill from the POAC goes quiet for 500 ms.
  • Boards are reflashed over CAN through a bootloader with upload_tool, and inspected with canmore_cli or a debug probe on the board's SWD pads.

Building an image

The firmware is C on the Pico SDK, built with CMake and the gcc-arm-none-eabi cross compiler, on Linux (WSL works). Full setup: docs/01_Setup.md.

sudo apt install git build-essential cmake pkg-config gcc-arm-none-eabi \
  libnewlib-arm-none-eabi libstdc++-arm-none-eabi-newlib libusb-1.0-0-dev
cd ~/osu-uwrt/development/titan_firmware
git submodule update --init
(cd lib/pico-sdk && git submodule update --init)
(cd lib/micro_ros_pico && ./build.sh)      # once: builds libmicroros in Docker

cd talos/ESCBoard && mkdir build && cd build
cmake ..                                   # RelWithDebInfo unless you ask for Debug

On ROS each board is a node in /talos (poac_board, esc_board_0 and _1, camera_cage_bb, led_board, ivc_board). Every second each publishes state/firmware: name, client ID, version, uptime, fault bits and kill-switch bits.

One loop, every board

There is no operating system. Each board runs one loop on core 0, written the same way in every project (PoacBoard/src/main.c): background tasks (CAN heartbeat, status LED), then the ROS tasks if the agent is connected, then safety_tick(), which checks the kill switches and feeds the watchdog.

  • Never block. Slow work goes to interrupts, DMA, the PIO state machines or core 1.
  • At most one ROS timeout per pass. A reliable publish can wait 30 ms for the agent, and the ROS task list stops at its first error.
  • Core 1 runs the timing-critical work (the ESC thruster loop, the battery gauge) and must check in every 250 ms, or the board panics and resets.
  • Periodic tasks are checked. A critical task that misses a run raises TIMER_MISSED.

CAN and CANmore

CAN is a two-wire bus where every node hears every frame. A frame has an identifier (11 bits, or 29 in an "extended" frame) and up to 8 data bytes. The lower ID wins when two nodes start at once, and every frame must be acknowledged by another node.

BusOn the OrinSpeedBoards
Internalcan01 Mbit/sPOAC, both ESC boards, camera cage, LED, IVC
Externalcan1250 kbit/sThe smart battery housings

The firmware sets the internal bus up for CAN FD (robots/talos.h), but in practice every frame is classic, at most 8 bytes: the boards only send classic frames ("TODO: Enable CAN FD"), and the Orin brings can0 up as classic CAN (configure_jetpack.bash).

Why a protocol of their own

micro-ROS packets are much longer than 8 bytes, and XRCE's own framing for byte streams would repeat what CAN already does. CANmore (titan_canmore) puts what is needed to reassemble a message into the frame ID, so all 8 data bytes carry payload, and leaves room for traffic that isn't ROS.

  • ID layout. Client ID (5 bits, 1–31), type (0 message, 1 utility), direction (0 board to Orin, 1 Orin to board) and a 4-bit sequence number or channel. The client ID is the top of the ID, so the POAC (1) wins arbitration over the ESC boards (2, 3).
  • Messages carry ROS traffic, up to 1024 bytes. The first frame is extended and holds the length; the last is extended and holds a CRC-18 of the whole message. Lose one frame and the message is dropped; XRCE's reliable streams resend it.
  • Utility frames are single frames on 16 channels: 0 thruster commands, 13 remote terminal, 14 control interface (register reads and writes for debugging and the bootloader), 15 heartbeat (one byte every 500 ms from every board).

Pick a kind of frame to see how it is built, or paste a line from candump to decode it.

From topic to frames: micro-ROS

A board doesn't run DDS itself. It runs a small XRCE-DDS client that asks an agent on the Orin to create its publishers and subscribers and carry its messages.

On the board
One rclc node, up to 15 publishers and 15 subscribers (colcon.meta). transport_can.c hands each packet to the CANmore encoder.
On the Orin
copro_agent runs micro_ros_agent can -D can0 -v4 -m rmw, restarted if it dies (copro_agent.launch.py, started by hardware.launch.py)
The agent
osu-uwrt/micro-ros-agent pins four submodules and builds them with build_agent.bash: the team's fork of eProsima's agent, Micro-XRCE-DDS-Agent at Happyxrce; micro-ROS-Agent-impl, the team's fork of micro_ros_agent; titan_canmore; and micro_ros_msgs.
can
The CAN transport, not in upstream micro-ROS (CanAgentLinux.cpp). It reassembles each board's frames with canmore_cpp.
-m rmw
A middleware the team added in 2025 (RmwMiddleware.cpp): the agent hands messages to the Orin's ROS 2 middleware (Zenoh today) instead of speaking DDS itself.
External bus
The can1 agent in copro_agent.launch.py is commented out. How the battery housings reach ROS today is unconfirmed.
  • Connecting. A board pings the agent once a second. When it answers, the board creates its node and turns its safety on. If more than 7 heartbeat publishes in a row fail (one every 100 ms), it tears the node down, kills itself and pings again.
  • No services. The boards only use topics, since June 2025 (783b8e0, for the Zenoh agent).
nano_ros: not on Talos

osu-uwrt/nano_ros (started August 2026) is an experiment to replace micro-ROS with something lighter. Only a USB test project on its nano_ros branch uses it; every Talos board still runs micro-ROS.

Watchdogs, faults and crashes

titan_safety is the first thing every board starts (safety.h). It assumes the firmware will hang or crash sometime, and makes sure the board then resets into a safe state and leaves a record.

Watchdog
3 s while starting and waiting for the agent, 250 ms once connected (safety_internal.h). A pass with under 50 ms to spare (500 ms at start-up) raises WATCHDOG_WARNING.
Last words
One timer tick before the watchdog fires, an interrupt saves the address the code was stuck at.
Crash log
24 entries in RAM that survives a reset: reason, uptime and fault bits. A crashed board comes back with WATCHDOG_RESET raised.
Faults
A 32-bit word, one bit per fault (bits 0 and 1 the library's, the rest per board). Any fault flashes the LED red and sets the error bit in the CAN heartbeat.
Debugger
The watchdog pauses while a debugger halts the CPU.

The status LED (blue enabled, green killed, yellow no agent, red no CAN, flashing red a fault) is explained, with a tester, in The circuit boards. The bootloader adds three: white in its 0.5 s boot delay, cyan blinking blue while being flashed, and dim red if it couldn't start the CAN chip (status_led.c).

Kill switches in firmware

The kill logic is part of titan_safety and runs on every board. A board has slots. Each report sets a slot's "asserting kill" flag and, optionally, "needs update": the report must then repeat within 500 ms. The rule (kill_switch.c):

\text{killed} = \text{no slot reported yet} \;\lor\; \text{a slot asserts kill} \;\lor\; \text{a needs-update slot is older than 500 ms}
  • One board decides. Only the POAC board has the switch and four slots (physical, viewer, topside, debug). It drives the soft-kill pin that gates thruster power, and publishes the result on state/kill every 150 ms.
  • The rest follow. Every other board has one slot, fed by state/kill with "needs update" set. If the POAC board or the agent goes quiet, they all kill themselves 500 ms later (a little more: timeouts are checked in safety_tick).
  • Losing the agent kills a board: safety_deinit calls the kill handler (kill_switch.c).
  • An agent restart doesn't hold Talos killed. Slots keep their last report across an agent outage; only a reboot clears them (safety.c). When the agent returns, the board re-runs the rule at once, so a latched enable, like the Nereus viewer's, comes back without anyone pressing Enable. To keep Talos killed, pull the switch.
  • Actuators. The POAC board won't arm the servo while killed, or fire unless enabled and armed (ros_torp.c). A kill doesn't disarm an armed servo: that is a TODO in safety_handle_kill.

Who owns which slot, the sender lock and the kill circuit are in Commanding Talos.

Thrusters: from RPM to DShot

Each ESC board drives four ESCs (Thrusters and ESCs has the hardware). Targets arrive two ways, and expire after 500 ms either way:

  • Raw CAN, channel 0. The MPC sends one 8-byte frame per board every 50 ms, ID 0x0B0 for board 0 and 0x0F0 for board 1 (Commanding Talos), handled with no ROS involved.
  • The ROS topic command/thruster_rpm (eight values; each board takes its four), used by some calibration scripts.

Core 1 runs the loop (core1.c):

  • Talk. Each ESC gets its throttle over DShot600, a 600 kbit/s digital protocol generated by the PIO. With bidirectional DShot the ESC answers with its electrical RPM; over 7 pole pairs, that is the motor RPM.
  • Control. Per thruster: a fitted feed-forward from RPM to throttle, plus P on a 100-sample average of the measured RPM, plus I within 300 RPM of the target. Output is limited to ±725 of ±999; a change of direction is held at zero for 2 ms.
  • Guard. If any disabled flag below is set, all four ESCs get zero. A pass takes at least 400 µs; in the 2026-10-24 pool run the loop ran at 2376 Hz.
BitDisabled flagSet while
0SAFETY_KILLEDThe board's kill rule says killed

A kill cuts ESC power, so after every kill the ESC boards show ESC_BOARD_OFF, then ESC_POWERON_DELAY for 5 s (dshot.h): the pause between Enable and the first thrust.

  • Reversible DShot. The team patched the APD 80F3 ESCs' own firmware so they reverse in DShot mode (README).
  • Reversed motors. Slots 0 and 3 on each board are inverted (mask 0b1001): thrusters 0, 3, 4 and 7 spin the other way for the same target.
  • Telemetry. Every 500 ms each board publishes state/thrusters/telemetry: supply voltage, disabled flags, loop ticks, and per ESC its RPM, current, temperature and error counts. state/thrusters/rpm stays empty on the CAN path.
A one-byte bug

Until the fix (3135fe2, written 4 October) was merged to master on 10 October 2026, the channel-0 handler read each RPM as (buf[idx] << 8) | buf[idx]: the high byte twice. A 300 RPM target (01 2C) arrived as 257. The CAN explorer above shows what the old firmware heard.

The depth sensor

The camera cage board reads the Bar02 pressure sensor over I²C (driver_depth; Navigation sensors covers the physics).

  • Every 50 ms (20 Hz) a reading goes out on state/depth/raw, variance 0.003, frame talos/pressure_link, negative below the surface.
  • Zeroed at power-up: it skips 20 readings and blends the next 20 into a surface pressure. Depth is (p - p_\text{surface}) / (997 \cdot 9.80665).
  • The zero survives a watchdog reset (it sits in RAM a reset doesn't clear), but not a power cycle. Re-zero at the surface with CLEAR_DEPTH on command/electrical.
  • Timestamps. On master the clock syncs with the agent once per connection, drifts about 43 ppm (150 ms an hour), and a stamp lands 35–45 ms after the measurement. The unmerged fix/depth-timestamps branch resyncs every 5 s (39c07af).

Flashing and upgrading

The first 16 kB of flash hold the titan bootloader; the application starts at 0x10004000 (memmap_bootloader.ld). At power-up it listens 500 ms for a request on channel 14 (B0 07 10 AD). Then it checks the CRC-32 of the application's first 256-byte page (its boot stage), so a blank or half-erased image isn't started, and jumps to it. A request or a bad CRC keeps it in the bootloader, taking an image, until it finishes or sits idle for 30 s (main.c). upload_tool can also send a running board there, so an upgrade needs no buttons.

Before you flash
  • Kill the robot and keep clear of the propellers. A flashed POAC board reboots and cuts thruster power, and every board comes back killed.
  • Send the _ota image over CAN, not _with_bl. An interrupted bootloader upload needs USB or SWD to recover, which is hard on a sealed battery housing.
  • Mind USB power. The battery housing's MCU board takes USB power unprotected: unplug everything else first (testing docs).

  • canmore_cli (~/firmware_deploy/bin) finds every board from its heartbeats. Pick one, then version, safetystatus, fault, crashlog, reboot, enterbl, gdbserver (GDB over CAN), or @ for a board's own commands.
  • Wireshark decodes CANmore with canmore_dissector.lua in ~/.local/lib/wireshark/plugins ("Decode As" CANMORE).
  • Serial console. Every board logs on a 115200-baud debug UART, passed through by the Picoprobe (screen /dev/ttyACM0 115200), boot messages and last crash included.
  • GDB. openocd -f interface/cmsis-dap.cfg -c 'adapter speed 2000' -f target/rp2040.cfg, then gdb-multiarch -ex "target extended-remote :3333" esc_board.elf, with the ELF from the same build.
