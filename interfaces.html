Appendices · Appendix A

Topics, services and frames

Every name Talos's programs use to talk to each other, in one searchable list: who sends it, who listens, how often, on the robot or only in the simulator, and which chapter explains it.

The short version
  • Open a group (Sensors, Control, …) or search a name, a message type or a node. Tap a row for its publishers, subscribers, rates, source code and the chapter that explains it.
  • Almost every name sits under /talos/. This page leaves that prefix off: odometry/filtered means /talos/odometry/filtered. Names that start with / are outside it.
  • Robot + sim exists in both. Robot only comes from sensor drivers and the boards' firmware, which Nereus replaces. Sim only is Nereus's own.
  • Two kinds of rate: measured on Talos (a pool bag) or set in code, and measured in a Nereus run on a busy desktop. The Nereus numbers are not robot specs.

The ROS 2 chapter explains what topics, services, actions and frames are. This appendix is the list itself. Keep it open while you read a launch file, a tree or a bag: when you meet a name you don't know, search it here.

Reading a name

The launch files start almost every node in the namespace talos. These names are outside it:

  • /tf and /tf_static, the shared transform tree;
  • /clock, the simulated time in Nereus;
  • /rosout and /parameter_events, which every node has;
  • /<hostname>/autonomy/bag_trigger: doTask names it after the computer it runs on.

Each row is one of five kinds:

topic
A stream of messages. Columns: message type, publishers → subscribers, rate.
service
A request and one reply. Publishers are the servers; subscribers are the callers seen in the graph.
action
A long job with feedback and a result (a path, a tree run, a calibration).
frame
A TF frame, shown with its parent. Static frames never move.
node
A program: its package, where it runs, its launch and config files, and its parameters.

The reference

Start with a group: each shows its most-used names first. Or type in the box to search names, message types, node names and notes; every word must match.

A few things the list shows that are easy to miss:

  • Hundreds of connections from one node. Each node in a behaviour tree opens its own publisher or subscription, so in the capture doTask (autonomy) holds 491 subscriptions to odometry/filtered and 339 publishers on controller/linear. The rows show these as ×491.
  • The same name as a topic and a service. command/actuator/torpedo is a topic the POAC firmware listens to, and a service that ActuatorTranslator (actuator_service_translator.py) serves for the trees. Both have rows.
  • Leftovers. Some names have subscribers but no publisher anywhere in the current stack (ff_auto_tune, controller/drag_comp/forward, thrusterSolver/thrusterState). They belong to the older controllers that the MPC replaced. They are folded under unused or debug and marked no publisher.
  • Missing on purpose. The six parameter services every node has, the hidden transform_listener_impl nodes, and the launch process itself are left out.

Robot or simulator: who sends what

In Nereus the simulator stands in for the hardware: the sensor drivers, the cameras and the firmware boards. Everything above them (EKF, MPC, detector, mapping, trees, viewer) is the same code with the same names, which is why a tree that works in Nereus can run on Talos unchanged. These are the names where the sender or receiver changes.

Three differences matter most when something works in one and not the other:

  • Thrust. On Talos the MPC sends RPM to the ESC boards itself over CAN, and nothing in the normal stack subscribes to thruster_forces (only pool_identify, during an identification session). In Nereus the simulator applies thruster_forces (Commanding Talos).
  • Time. In Nereus every node runs on /clock (use_sim_time; the detector is the exception). On Talos there is no /clock and nodes use the Orin's clock (ROS 2: time).
  • Extras on each side. Talos has topics Nereus never publishes (raw gyro counts, DVL status, board temperatures, heartbeats), and Nereus has its simulator/* topics and services, which don't exist on Talos.

TF frames

Frames are in the reference too: choose . The tree has three parts:

  • The robot: world → odom → talos/base_link, then talos/origin and one frame per sensor, thruster and tool from the URDF. The EKF moves odom → talos/base_link; the others don't move, though some are sent on /tf rather than /tf_static. Where am I? walks through it.
  • The course: world → map → offset and one frame per object, published by mapping. AprilTag calibration moves world → map (Frames, targets and the mission tree).
  • Nereus truth: world → simulator/talos/base_link, where the simulated Talos really is, so it can be drawn beside the EKF's estimate.

The cameras differ between the two. On Talos the ZED's own description hangs talos/ffc_camera_center, the left and right lens frames and their optical frames under talos/ffc_camera_link (the same for dfc). In Nereus the bridge hangs the left optical frame straight under the camera link and the right optical frame under the left one (bridge.yaml). Both stamp images in talos/<cam>_left_camera_optical_frame, so nothing downstream notices.

Parameters and config files

Where the nodes you are most likely to edit get their settings. A node's row in the reference lists the same files and, for seven nodes, every parameter with the value it loaded in the Nereus run.

Two parameter values in the Nereus run differ from the robot because of how the capture was run: use_sim_time is true for most nodes (false on Talos), and the MPC's vehicle_config and hydrodynamics_config point at the simulator's own plant because the run used mpc_model:=sim. On Talos they point at riptide_descriptions/config/talos.yaml and riptide_mpc/config/models/talos.yaml (mpc_controller.launch.py).

Check it yourself

The list is a snapshot. To see the live graph, connect to the robot's or your simulator's Zenoh router (ROS 2: Zenoh) and ask ROS directly. Add --no-daemon if lists come back empty.

# every topic with its type
ros2 topic list -t
# publishers, subscribers and their QoS
ros2 topic info -v /talos/odometry/filtered
# measure one topic at a time; print one message
ros2 topic hz /talos/vectornav/imu
ros2 topic echo --once /talos/state/kill
# everything one node touches, and every parameter it loaded
ros2 node info /talos/mpc_controller
ros2 param dump /talos/mpc_controller
# services and actions with their types
ros2 service list -t
ros2 action list -t
# one transform, live
ros2 run tf2_ros tf2_echo odom talos/base_link
  • Measure one topic at a time. Each hz subscription adds load over the tether, and camera topics are big (The cameras: bandwidth).
  • Reading is safe; writing isn't. topic pub, service call and action send_goal act on the real robot. Leave command/software_kill to the viewer (Commanding Talos: kill).
  • The board topics appear only while the boards are up. They come through copro_agent, the micro-ROS agent on can0 (Firmware: micro-ROS).

Where this list comes from

  • The Nereus capture: every node of the full stack, with its topics, services and actions, the TF tree and seven parameter dumps, taken while the competition tree ran (sim.launch.py active_control_model:=mpc mpc_model:=sim, 30 Oct 2026). It is the same capture the ROS 2 chapter's graph and the TF explorer use.
  • The robot's launch: talos_launch_mpc.yaml and the launch files it starts. The drivers that only run on Talos (IMU, FOG, DVL, ZED cameras, micro-ROS agent, actuator and pinger helpers) were read from their code.
  • The firmware: each board's publishers and subscriptions, with their QoS, parsed from titan_firmware master. The pinger topics come from IVCBoard2 on branch blake/ivc, as in Navigation sensors.
  • Robot rates: a 20-minute pool bag from 26 Oct 2026 (an MPC identification session), which recorded the sensor, EKF and controller topics. Other robot rates are the periods set in the code, linked in each row.
  • Not covered: riptide_navigation's alternative navigation (its package isn't in the release sources; see Launching the stack), and the topics of the diagnostics nodes, which are still in the launch list but no longer run (they have one row, marked not used).
  • Not covered either: the ZED nodes publish many more topics than the ones listed (the left and right streams, the camera's own IMU, status and health). Nothing in the stack reads them. On the robot, ros2 topic list | grep zed_node shows them all.
For page authors: linking to a row, rebuilding the data

Every row has an address: #<kind>-<name>, with the name written without /talos/ and without a leading /. For example #topic-odometry/filtered, #topic-tf_static, #service-mapping_target, #action-follow_path, #frame-talos/base_link (frames by their child frame) and #node-mpc_controller. A course object's own topic or frame also works: #topic-mapping/gate and #frame-gate_frame open the shared mapping/<object> and <object>_frame rows.

Rebuild the data with python3 -I tools/interfaces/build.py. It reads the local clones and tools/interfaces/curated.yaml, which also lists each group's key rows and the rows folded away as unused or debug.
