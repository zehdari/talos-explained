Running Talos · Chapter 4

Pool test day

Pool time is short and booked. Whatever can be found on a bench is found there the day before, so the water is only for what needs water. This is the whole day, from bumping submodules to tagging the release, with a checklist you can tick through on your phone.

The short version
  • Do the bench checks the day before at the latest. The team's pre-test document allows 1.5 to 6 hours for them and says, in capitals, not to do them on the day.
  • Freeze the code. One riptide_release commit pins every repo, a clean deploy puts exactly that on the Orin, and pretest checks that it did.
  • At the pool, the Nereus viewer on op-top is the operator's screen. It holds Talos killed from the moment it opens until someone presses Enable.
  • The kill switch is a red handle on Talos's port bow window. Underwater and untethered, nothing stops Talos until someone reaches it.
  • Afterwards, copy the data off the Orin, commit what changed, and tag the release with the date.

A test in three parts

Before
Bench-test the new code on the robot, freeze it in release, deploy, run the checks, seal and pressure-test the hull. The day before at the latest.
At the pool
Set up on deck, check Talos in the water, then fly: small moves, the course, trees, identification. Record everything.
After
Copy the data, commit fixes made at the pool, tag the release, write it up.

The procedure comes from the team's pre-test document, PRE_TEST_CHECKS.docx (it isn't in any repo: ask a lead for a copy), and the release README. Most of the bench part is now automated by pretest_checks (below).

Every test leaves a trace in riptide_release: a commit that pins the code before it, like Pre RPAC test 10-12-26. RPAC is Ohio State's Recreation and Physical Activity Center, whose dive well the team tests in; a few commits name other pools (Pre Sean Test, Pre Tirpak test): ask a lead which.

Tests come one to four weeks apart in term, with gaps over the breaks, so each one has a short runway. The README's last step, a tag named for the date after each test, stopped after 6-29-24_talos; since then only robosub2024 and robosub2026 were tagged, and the "Pre" commits are the only record of what ran. After the test brings the tags back.

Before: freeze the code

The rule behind everything else: the code that goes in the water is one release commit, and the Orin runs exactly it. Then a problem at the pool can be reproduced at home, and a good state can be returned to.

  • Bench-test on the robot. New code is tried on the Orin with the real sensors, not just on a laptop. The document: "Integration is hell." This is the part that takes longest.
  • Update days ahead. apt upgrade or new drivers go in days early, because what they break is "often times inexplicable and confusing".
  • Pin and push. Each changed submodule is committed and pushed on its branch, then release records the new pins. A pin that exists only on your laptop can't be checked out by anyone else.
  • Build and deploy clean. colcon never deletes a removed package from install/, and stale caches cause compile errors that look like code bugs.
cd ~/osu-uwrt/release
git submodule status          # '+': away from its pin
git add src/riptide_control   # each one you changed
git commit -m "Pre RPAC test 10-30-26" && git push

rm -rf build install log && colcon build      # clean build
source ~/osu-uwrt/riptide_setup/install/setup.bash
ssh ros@orin2 'rm -rf ~/colcon_deploy'        # clean on the Orin
colcon deploy orin2 --clean
No git at the pool

"NEVER plan on making git changes (like a revert) at a pool test." A revert means rebuilding on the Orin, and the packages depend on each other so tightly that a poolside revert usually breaks something else. If code is wrong, fix it on the bench. At the pool, the release README has you deploy only the packages you need "as you work through bugs"; commit those changes afterwards.

How submodules, pins and colcon deploy work is in Setting up your machine.

pretest_checks: the bench, checked by a script

pretest_checks turns the document into checks that print PASS, WARN or FAIL, with the fix for a person to apply. It was written in October 2026 and lives on op-top in ~/osu-uwrt/release/pretest_checks; it isn't in a GitHub repo yet. Everything robot-specific (hosts, topics, boards, thresholds) is in one profile, robots/talos/robot.yaml. It runs in stages: repo, bench and guided are built; sim and dayof are planned.

cd ~/osu-uwrt/release/pretest_checks
./pretest                      # repo → bench → guided
./pretest bench --only B3,B5   # chosen checks
./pretest --list               # every check

What it will never do matters as much as what it does:

  • It never changes code on the robot. No deploys, no builds on the Orin, no git or apt commands that modify anything. When the robot is out of date, it prints the commands for a person to run.
  • It never starts the controller as a plain launch. An enabled robot with control_system running spins its thrusters. The bench stage runs the controller only while it holds a software kill and both ESC boards report themselves killed (SAFETY_KILLED).
  • Only the thruster test moves anything, and only after a person has enabled the robot and pressed Enter.
  • It never tares the gyro. An unlevel bench would bias every heading.

The thruster test

thruster_test_canbus (send_thruster_cmd_canbus.c) writes CAN frames straight to the two ESC boards, with no ROS and no controller in between. It runs each thruster in turn at 300 rpm for 3 s (100 frames 30 ms apart), forever, until Ctrl-C. Its Ctrl-C handler sends zeros to every thruster before exiting. One run checks three things: the software kill (started with the viewer on KILL, nothing spins), the wiring (enabled, each thruster spins in its turn: check it's the one in the place named, because telemetry can't see which motor an ESC is wired to), and the physical kill (after a full cycle, pulling the handle stops everything while the program is still commanding).

Thrusters
  • Before the test: Talos on its stand, propellers clear of hands, hair, cables and tools, and a second person with a hand on the kill switch handle.
  • 300 rpm is the test. Under the MPC a thruster can reach its 24 N limit, about 2,450 rpm (Thrusters and allocation).
  • Stop control_system first: the MPC and the test would both write thruster commands to CAN. Never start it on the bench with the robot enabled.

The rest of guided works the same way, hands-free because whoever holds the robot can't reach a keyboard: tilt and turn Talos and the right axis has to move with the right sign, a finger on the depth sensor has to read deeper, a torpedo prop in front of the camera has to be detected and mapped, then the torpedo and dropper fire.

The pressure test (PVT)

The bench ends with a leak test by hand, the depressurization test, PVT for short. In the 2025 TDR, a hand pump lowers the hull pressure by 0.05 bar, and the IMU's pressure and the boards' temperatures are watched for five minutes: by the ideal gas law, a leak shows up as air coming back in. The document's steps:

  1. Only hardware running in the launcher. Keep its log open.
  2. Put the pump on the hull's vacuum valve. Where it is and how the pump fits: ask the mechanical lead.
  3. Start the PVT (how, now that RViz is gone, is unconfirmed: see the old-document notes below), and once it says it's ready, pump. The logs say when to stop.
  4. Pull the pump off quickly and close the valve.
  5. Leave Talos for at least 5 minutes.
  6. Passed: the green SubConn cover goes on over the connectors on the port stern lid. It means sealed and tested.

Then the rule that protects all of it: nobody opens Talos or swaps a part until the test. Any internal change voids the localization and thruster tests. Open it, and the PVT has to be done again.

Batteries

Talos runs on two LiPo packs in smart battery housings, port and starboard, sharing one bus. The cells, the gauge, the LEDs and how to charge safely are in The electrical system and Charging and handling. For a test, three rules:

  • Charge both the night before. On the bench Talos runs from a power supply, so the packs are only tested once they're in.
  • Start the day at about 21 V. That is what freshly charged packs read on the bus. B4 fails below 18.5 V (the packs' nominal voltage), which means they weren't charged.
  • Swap at 17.5 V, MaxAmps' recommended landing voltage. Never fly a pack down to its 16 V cutoff.

Watch the bus voltage, balanced_voltage in state/electrical (from the POAC, on the internal CAN bus can0): plot it in the viewer (Plotting live) or ros2 topic echo state/electrical --field balanced_voltage. The housings report on the external bus, can1, whose agent on the Orin has been commented out since 27 October 2026 (720bdd9): until it's back, the viewer's PORT and STBD chips stay gray and B3 reports both housings missing.

Pack list

The repos don't hold a packing list, so this one is built from what the steps on this page use.

On deck: network, power, launcher, viewer

Talos's Orin, the DVL and op-top share the team router's LAN, 192.168.1.0/24. On deck, the tether joins Talos to it, and the opbox gives the LAN internet and a time server (Computers and networks). Power-on order

The code doesn't enforce an order. This one follows from how the kill system works, and it keeps the thrusters unpowered until the end:

  1. Kill switch out: the handle off the port bow window (below). Out, the POAC board cuts the thrusters' power, whatever any software says.
  2. Power on. The POAC starts killed, and stays killed until a software kill slot reports enabled over its micro-ROS link to the Orin. The Orin boots and ros_launcher starts by itself as a service.
  3. Launcher: open http://orin2:8080, load talos_launch_mpc.yaml and start, in the pre-test tool's order: hardware (the real DVL; the bench file uses hardware_fake_dvl), riptide_hardware2's navigation (not riptide_navigation's), zed, tensorrt, mapping and autonomy. Skip diagnostics: it's no longer used.
  4. The viewer on op-top. The POAC kills Talos if any of several software kill slots asserts a kill, and the viewer owns slot 1. From its first tick it asserts it, so Talos stays killed even with the handle in.
  5. A quick health check (below). If the hull was opened or anything rewired since the bench, run the thruster test again now, on the stand, while the controller is still off.
  6. control_system last, with Talos still killed. Killed, the MPC publishes zero thrust.
source ~/osu-uwrt/release/scripts/dds_scripts/config_rmw.bash
ros2 launch nereus robot.launch.py pool:=rpac

cd ~/osu-uwrt/release/pretest_checks
./pretest bench --only B3,B4,B5,B6,B7 --power battery
  • config_rmw.bash makes the terminal a Zenoh client of orin2 (ROS 2 over Zenoh).
  • pool:=rpac draws the RPAC pool (robosub for the competition one) around Talos's own estimate of where it is (robot.launch.py).
  • The health check is five bench checks that start nothing and take under a minute: boards, rails and the battery bus, topic rates, the kill state, the ESCs. B3 will list the battery housings as missing (can1). The planned dayof stage will compare everything with the last passing bench run.

Who does what, and the kill switch

The kill switch is on the robot, not on deck: the red handle on the port bow window. A Hall-effect sensor (a magnet detector) behind the window feels the magnet in the handle. In means the handle is seated; out means it's pulled off, and the POAC board cuts the thrusters' power, whatever any software says (The kill switch, glossary). The computer and sensors stay on.

So pulling it takes someone at the robot. Name these before Talos goes in, one person per line:

Operator
The only person at the viewer: Enable, KILL, moves, trees, bags. A second operator on slot 1 drops the viewer's enable (viewer docs).
Swimmer
In the water with Talos. Seats the handle to start a run and pulls it to end one, or the moment anyone calls for it. Brings Talos to the side and plugs the tether back in.
Lifters
Two people lift Talos in and out, with the handle out. It weighs about 32 kg dry and 34 kg wet (scale weights).
Notes
What ran, when, which bag, what broke: the release notes after the test need it.

These roles are this page's split, not a written team rule. Where the swimmer waits during an untethered run is the test lead's call: ask.

  • Tethered, two kills. The handle, and the viewer's KILL, which reaches Talos through the tether. The viewer's Enable latches (needs_update false): it holds until the next message, so a run survives the tether coming off, and losing the link never kills.
  • Untethered, only the handle. Nothing on deck can stop Talos. It stops when the tree ends or when someone reaches the handle; underwater, that means the swimmer going to it.
  • Hands off an enabled robot. Anyone handling Talos pulls the handle first.
  • After any kill, Talos drives again once the handle is back in. Before it goes in, follow Ending a run.

In the water: buoyancy and trim

Talos is built to float, slightly. RoboSub requires a vehicle to be positively buoyant by at least 0.5 % of its mass when killed (RoboSub and the course), so a killed robot comes up on its own. Talos's MPC model puts it just under that line, and the latest untethered fit right on it:

Net buoyancy
+1.63 N in models/talos.yaml; the line is 1.68 N for its 34.3 kg, which the 2026-10-26 untethered fit matched. If Talos sinks or hangs in the water, add buoyancy before flying.
Rises at
About 4 cm/s with the thrusters off (identification releases).
Centre of buoyancy
About 22 mm above the centre of mass, so Talos rights itself when tilted.

That margin is small on purpose: every newton of extra buoyancy is a newton the vertical thrusters push against for the whole run. Two checks in the water:

  • Killed: does Talos float up slowly and sit at the surface?
  • Enabled, holding still: plot the MPC's disturbance estimate (plot disturbance in the viewer's Ctrl+P search). The MPC learns whatever force and torque its model is missing. A few newtons or newton-metres held constant means the model's buoyancy or trim no longer matches the robot: something was added or moved, or the tether is pulling. The model's own rule: "Change the body and re-identify."

Sensor checks in the water

The bench can't test what needs water, and the DVL only locks once it's under. So the first dive is by hand, from the viewer:

  1. Enable in the viewer, with the handle still out.
  2. The swimmer seats the handle and moves clear. About 5 s later the ESCs are ready and Talos drives to its last target.
  3. Dive in place (Motion panel): it holds Talos's x, y and heading, level, at 0.75 m deep (dive_z in talos_uwrt_panels.yaml).

Then, before any other move, check these:

Then the first moves, small ones. Type them into the viewer's search (Ctrl+P): forward 0.5, turn 30, down 0.3, and watch the error column in the Motion panel (typed moves).

Mapping the course

The trees navigate in the map frame, using a prior map: where each prop is expected, relative to a map origin, in riptide_mapping's config/config.yaml. At a new pool, or with the props moved, the map has to match the water. Steps 1 and 2 are deck work and can be done before Talos goes in; step 3 needs Talos in the water.

  1. Place the props, measure them. Then open Edit map in the viewer (Ctrl+M) and move each prop to where it is. The origin is either AprilTag, on a wall where a floor line meets it, or Robot frame, Talos's start pose (viewer docs).
  2. Save and deploy it. The editor writes the file in op-top's release source tree. Deploy just that package and restart mapping in the launcher so it reads the new file.
  3. Calibrate. With the tag in view, Calibrate in the Mapping panel averages the tag board's pose and sets world → map from it.
  4. Commit the map afterwards, in riptide_perception, so the next test starts from it.
cd ~/osu-uwrt/release
colcon deploy orin2 --packages-select riptide_mapping2

Recording

A run that wasn't recorded can't be debugged at home. Start a bag before every run, from the viewer's Bagging panel (viewer docs):

  • Record on: Robot. ros2 bag record runs on ros@orin2 into ~/bags. It keeps recording if the viewer closes or the tether comes off, and any viewer can stop it. A bag on "This computer" stops with the viewer and only gets what crosses the tether.
  • Topics. All, or Leave out with a pattern such as image|point_cloud to skip the camera streams. The panel shows the robot's free disk (yellow under 5 GB).
  • Stop sends Ctrl-C, so the recorder writes its metadata.yaml. A red BAG chip in the command bar shows one is running.
  • Camera video comes from the Recording panel instead: the ZED nodes write lossless .svo2 files on the robot, one per camera.

What to do with a bag afterwards is in Debugging, bags and data. The panel's Copy path gives the last bag as ros@orin2:/home/ros/bags/…, ready for rsync.

Running trees

A tree is started from the viewer's Autonomy panel, but it doesn't move until the handle goes in. The mission trees begin with WaitForKillSwitch (RepairCompMpcTree.xml): it polls state/kill until it reads false, then waits 6 s more. That is how a run goes untethered:

  1. Talos at the surface, handle out.
  2. Enable in the viewer. Talos stays killed by the handle, but slot 1 is now clear, and latched.
  3. Autonomy: pick the tree, Start. The viewer only allows it while it holds the enable. The tree logs "Waiting for kill switch insert...".
  4. Unplug the tether, if this run is untethered. Slot 1 stays clear.
  5. The swimmer seats the handle and moves away. Six seconds later the tree moves.
  6. Pulling the handle stops the thrusters, not the tree. End every run as in Ending a run.
Ending a run
  1. Handle out, by the swimmer, or by whoever reaches Talos once it's at the surface. Killed, Talos floats up on its own.
  2. Bring Talos to the side. Plug the tether back in.
  3. Autonomy panel: Stop, and wait until Start is free again.
  4. Viewer: KILL. Slot 1 now holds Talos killed even with the handle in.
  5. Only now: handle back in, hands on Talos, or the next run from step 2 above.

Why the order: the viewer's Enable latches, and a tree keeps running when the handle is pulled (the executor's kill check is commented out in DoTask.cpp; only a running path goal fails, "vehicle killed", in the MPC). Put the handle back with either still live and, about 5 s later, Talos drives again.

While a tree runs, the viewer blocks manual commands. Which trees exist and how they're built: The competition mission and Writing and testing trees.

Identification runs

pool_identify flies a scripted session and fits Talos's buoyancy, drag and added mass (System identification). At the pool it needs space and no tether:

  • It starts at the map origin. IdentificationTree dives to 0.85 m, flies to the mapping origin facing map +x, and only then starts pool_identify (IdentificationTree.xml). So put the prior map in and calibrate first.
  • Room: 3 m of clear water ahead (map +x) and to port (map +y) of that start, and 2.5 m below it, so the water must be at least about 3.4 m deep at the origin. It starts at least 0.75 m deep and ends if Talos comes within 0.4 m of the surface (identification.yaml; the tree's own comment still says 1.5 m).
  • Untethered, from the committed model. Start untethered fits from talos.yaml, never from a tethered fit (below).
  • Launch it on the Orin before unplugging, inside tmux so it survives the SSH link dropping. With wait_for_trigger:=true it waits for IdentificationTree to start it, so run that tree like any other.
  • Data: each session writes a folder under ~/osu-uwrt/mpc_identification on the Orin, with its own bag.

When something goes wrong

The order is always the same: make Talos safe, get the link back, then look.

  1. Kill it. Tethered: KILL in the viewer, then the handle out. Untethered: the handle, as soon as someone reaches Talos. Killed, it floats up.
  2. Tether in (untethered, nothing on op-top reaches the robot), then Ending a run, steps 2 to 4.
  3. Read the viewer. The FOG and DVL chips, the bus voltage, the Motion panel's error column, the camera cards.
  4. Read the logs. Live node output is on the launcher page (http://orin2:8080), only while it's open. Warnings are on /rosout (ros2 topic echo /rosout --field msg), and each node's log file is under ~/.ros/log/ on the Orin (Where the logs are).
  5. Restart one launch, not everything. Stop and Start the launch that failed in the launcher page. Restarting ros_launcher itself stops every node.
  • The viewer freezes or its pose goes stale: it releases manual control and the robot holds its last command. It never kills on its own (viewer docs). Pull the handle.
  • DVL lock lost or depth wrong mid-run: the MPC flies to wherever the estimate says Talos is, so a bad estimate means a bad run. Kill it, then work through When a sensor misbehaves.
  • Water in the hull: the leak sensor is no longer used, so nothing raises an alarm. Rising humidity on a board (state/humidity/poacboard, state/humidity/cameracage; plot them in the viewer) is the early sign (Housekeeping sensors). Any sign of water: handle out, Talos out, power off, and no dive until it's opened, dried and the PVT passes again.

After the test

Handle out, Talos out with two people, power off. Then, before anyone goes home:

  1. Copy the data off the Orin. Bags, SVOs and identification sessions exist only on the robot until copied.
  2. Commit what changed at the pool (prior map, parameters, models) in its own repo, then bump release.
  3. Tag release with the date and publish a GitHub release whose notes say what was tested and how it went. The README calls it "a backup for future pool tests, should software need to be rolled back".
  4. Write it up: what worked, what broke, and where the data is.
