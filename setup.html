Setting up your machine

From a blank laptop to Talos's code built and running in the simulator. What each script installs, where the code lives, what "sourcing" does, and how your changes get onto the robot.

The short version
  • Install Ubuntu 22.04, then run riptide_setup/setup.bash. It installs ROS 2 Humble, clones the code and edits your ~/.bashrc.
  • The code Talos runs is one repo, riptide_release, in ~/osu-uwrt/release. Every package repo inside it is a git submodule pinned to one exact commit. Build it with colcon build, and Nereus inside it with ./build.sh.
  • source install/setup.bash puts a workspace's packages on top of the ones already sourced. The last one sourced wins, and every new terminal starts from nothing.
  • A GPU helps but isn't required: the ZED SDK only runs on the robot, and the detector falls back to the CPU.
  • Code reaches Talos as commits: push your branch, bump its submodule in release, then colcon deploy copies the sources to the Orin and builds them there. The checklist at the end tracks your progress.

Before you start

Operating system
Ubuntu 22.04. The setup script reads lsb_release and stops on any other version (update_system.bash), because ROS 2 Humble's packages are built for 22.04. Install it on the laptop itself (dual boot is fine).
GPU
Optional. Install the NVIDIA driver first if you have one: the script checks for nvidia-smi. See Do you need a GPU?
Disk
More than you'd guess. Measured on a team member's machine:
  • ROS in /opt/ros/humble: 550 MB
  • release: 4.2 GB (git history 797 MB, sources 515 MB, build/ 845 MB, install/ 756 MB, log/ 191 MB, Nereus 882 MB)
  • development, which setup.bash always clones and builds: about 1 GB, plus 4.3 GB for titan_firmware, nearly all of it the Pico SDK's nested submodules and their git history
  • PyTorch for the detector, with its CUDA libraries: 5.4 GB in ~/.local
That's about 15 GB, before the system libraries apt installs alongside ROS.
Memory
Nereus's build.sh runs one compile job per 3 GB of free memory, after keeping 4 GB for the desktop. 8 GB free gives 1 job, 16 GB free gives 4.
GitHub
The code repos are public, so cloning needs no account. Pushing needs write access to osu-uwrt (ask a lead) and a way to log in from git: see Git.
Time
The script says the ROS install alone "will take about 20 min", depending on your connection.

riptide_setup: one script, ten steps

riptide_setup is the team's installer. Clone it to exactly this path; every script inside uses ~/osu-uwrt/... paths.

sudo apt install git
mkdir -p ~/osu-uwrt && cd ~/osu-uwrt
git clone https://github.com/osu-uwrt/riptide_setup.git
~/osu-uwrt/riptide_setup/setup.bash      # not with sudo: it asks when it needs to
Answer the prompts like this
  • Enter your install (Default is desktop): press Enter.
  • Install release setup? (default is no): type y. The rest of this site assumes ~/osu-uwrt/release exists.
  • After the reboot, the first terminal asks Setup bashrc for Release (R) or Development (D)?: type R and press Enter. It asks once per boot.
  • Until you build release (below), every terminal then prints release/install/setup.bash: No such file or directory. That's expected: the script clones release but doesn't build it.

Five things the script does not do. You do them next, in Building and Building Nereus:

  • Build the release workspace. setup_release.bash only clones it.
  • Install GLFW for camera_faker (libglfw3-dev). rosdep can't resolve its key.
  • Install the Zenoh middleware the team uses (ros-humble-rmw-zenoh-cpp).
  • Install the detector's Python packages (Ultralytics and PyTorch). rosdep can't.
  • Build Nereus.

Two quirks worth knowing:

  • The development workspace clones the branches listed in riptide.repos, which are old (master, ros2, ros2_dev, galactic): riptide_control's master has no riptide_mpc at all.
  • Running setup.bash again appends a second Release/Development block to ~/.bashrc (nothing checks whether one is there). Delete the duplicate.

Two workspaces: development and release

A workspace is a folder with a src/ of ROS packages that colcon builds into build/ and install/. The team has two layouts:

developmentrelease
Folder~/osu-uwrt/development/ dependencies + software~/osu-uwrt/release
How code arrivesvcs import: a clone of each repo on a branchgit clone --recursive: submodules at pinned commits
Workspacestwo, chained: software on top of dependenciesone
Used forthe original day-to-day layoutwhat the robot runs: deployed, tagged after tests; Nereus lives here

Work in release. Its README says to deploy from it and to run GUI tools from it so configs match the robot. Nereus is built against it. And current work lives on branches that riptide.repos doesn't check out.

A submodule is a repo inside a repo. The outer repo stores only a commit hash for it, the pin. Cloning or git submodule update checks out exactly that commit, so one release commit names the whole robot's code at once. That's why the team commits "Pre RPAC test" to release before a pool test.

# the first time (setup.bash does this if you answered y)
git clone --recursive https://github.com/osu-uwrt/riptide_release.git \
    ~/osu-uwrt/release

# later: bring everything to the current pins
cd ~/osu-uwrt/release
git pull
git submodule update --init --recursive

# work on a branch inside a submodule
cd src/riptide_control
git checkout mpc         # submodules start on a detached HEAD at the pin
git pull

Pins or current work? A fresh clone builds the pins on release master. This site follows newer branches, where the current work is: the last column above. riptide_motion_panel, for example, is on riptide_control's mpc branch but not at its pin. To match the site, check those branches out. They change over time, so ask a lead which are current.

# the branches this site follows (October 2026)
cd ~/osu-uwrt/release
git -C src/riptide_core checkout followpath-speed
git -C src/riptide_control checkout mpc
git -C src/riptide_perception checkout mapping-estimator
git -C src/riptide_autonomy checkout autonomy-mapping
git -C src/riptide_launch checkout newsim
git -C src/riptide_gui checkout newsim         # same commit as the pin;
git -C src/riptide_simulator checkout newsim   # this only leaves detached HEAD
git -C src/nortek_dvl checkout DvlWaterTrackFallback
# apriltag_ros clones from upstream; CompressedImages is on the team's fork
git -C src/apriltag_ros remote add uwrt https://github.com/osu-uwrt/apriltag_ros
git -C src/apriltag_ros fetch uwrt
git -C src/apriltag_ros checkout -b CompressedImages uwrt/CompressedImages

The AprilTag branch matters in the sim too: Nereus's mission stack starts the tag detector with image_transport: compressed (apriltag.launch.py), and the one commit CompressedImages adds on top of the pin decodes those images in the node itself, because the stock compressed plugin's decode fails in that process (the commit).

The detached-HEAD trap

git submodule update puts each submodule on its pinned commit, detached from any branch. Commit there and the commit belongs to no branch; switching away loses track of it. Run git status inside a submodule before you commit. The branch = lines in .gitmodules only matter for git submodule update --remote, which CI uses as a fallback when a pinned commit can't be fetched.

Building: rosdep, then colcon

cd ~/osu-uwrt/release
# the underlays: nothing else sources ROS yet, and riptide_setup
# makes release's setup.bash bring in colcon deploy
source /opt/ros/humble/setup.bash
source ~/osu-uwrt/riptide_setup/install/setup.bash
# system packages every package.xml asks for
rosdep install --from-paths src --ignore-src -r -y
# camera_faker needs GLFW; rosdep can't resolve its key
sudo apt install libglfw3-dev
# the middleware Talos uses
sudo apt install ros-humble-rmw-zenoh-cpp
# the detector's YOLO library; pulls in PyTorch
pip install ultralytics "numpy<2"
colcon build
source install/setup.bash
  • Source ROS first. In release mode, the ~/.bashrc block from setup.bash sources only release/install/setup.bash, which this build creates. riptide_setup's install was built without ROS sourced, so it doesn't bring ROS in either. Without the first line, rosdep doesn't know your ROS distribution (it fails on keys like ament_cmake) and colcon can't find ament_cmake.
  • rosdep reads every package.xml and apt-installs what's missing. -r keeps going past keys it can't resolve; without it, rosdep installs nothing. Five packages have such keys (table below). GLFW is the one that breaks the build: without it camera_faker fails to configure, and colcon starts nothing new after a failure.
  • Keep numpy below 2. Ultralytics would otherwise install numpy 2 into ~/.local, and ROS Humble's cv_bridge, built against numpy 1, then fails ("compiled using NumPy 1.x"). With "numpy<2" pip picks 1.26 and a matching OpenCV (tested October 2026).
  • colcon finds every package under src/, orders them by dependency and builds each into its own install/<package>. Errors go to log/latest_build/<package>/stderr.log.

tensor_detectorultralytics, numpy, scipy, cv2, OpenCV, CUDA, collectionspip install ultralytics "numpy<2" brings the Python ones. CUDA is optional; collections is part of Python.

riptide_hardware2,

What "source" actually does

A built workspace is only folders. Nothing finds it until a few environment variables point at it:

AMENT_PREFIX_PATH
where ros2 run, ros2 launch and get_package_share_directory look for packages
CMAKE_PREFIX_PATH
where CMake looks when a package says find_package(riptide_msgs2)
PYTHONPATH
where Python imports from (generated message modules, Python nodes)
PATH, LD_LIBRARY_PATH
programs and shared libraries

source file runs a script inside your current shell, so whatever it sets stays set. (./setup.bash would run it in a child shell that exits at once, taking its variables with it.) Each workspace's script prepends its folders. Lookups take the first match, so the workspace sourced last is the overlay and wins over its underlays.

One more thing makes the order matter: install/setup.bash first re-sources every workspace that was sourced when you built. colcon writes that list into the file. Here is release's, from a team member's machine:

# ~/osu-uwrt/release/install/setup.bash (generated by colcon, trimmed)
COLCON_CURRENT_PREFIX="/opt/ros/humble"
_colcon_prefix_chain_bash_source_script "$COLCON_CURRENT_PREFIX/local_setup.bash"
COLCON_CURRENT_PREFIX="$HOME/osu-uwrt/riptide_setup/install"
_colcon_prefix_chain_bash_source_script "$COLCON_CURRENT_PREFIX/local_setup.bash"
# then this workspace's own local_setup.bash

So build with the right underlays sourced. Build release in a terminal without riptide_setup sourced, and its setup.bash stops bringing in the colcon deploy command.

You don't type this in every terminal; ~/.bashrc does. With release installed, setup_bashrc.bash appends a block that asks Release or Development once per boot (the answer lives in /tmp, which a reboot clears) and sources one or the other. Never source both in one shell: two copies of the same packages, and whichever came last wins.

What to do with it: keep that block, and add the lines it lacks above it. In release mode it never sources ROS itself; release's setup.bash brings ROS in only once release has been built with ROS sourced. Then add Nereus and the middleware below it (Nereus's ./setup.sh offers to add its line). Together, a working terminal runs these, in order:

# you add this, above what setup.bash wrote
source /opt/ros/humble/setup.bash
# setup.bash wrote these: colcon deploy, then the R/D block (with R, it runs:)
source ~/osu-uwrt/riptide_setup/install/setup.bash
source ~/osu-uwrt/release/install/setup.bash
# Nereus's ./setup.sh offers to add this
source ~/osu-uwrt/release/nereus/build/ros-viewer/ros/setup.bash
# you add this
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
  • A new package needs a fresh source after its first build: its install/<package> folder wasn't on the path when you sourced.
  • A removed or renamed package lingers in install/ until a clean build, and can still be found.
  • After changing the middleware, run ros2 daemon stop: the ros2 command-line daemon keeps the old one.
  • On the robot, the middleware comes from release's switcher, config_rmw.bash: the changermw command saves a choice in ~/.uwrt/default_rmw (default fastdds) and rmw prints it. On a laptop for the sim, use the plain export above instead: the team's Zenoh profile connects to orin2 (see Joining from your own laptop).

Do you need a GPU?

No, but parts of the stack use one when it's there.

If your laptop has an NVIDIA GPU, install its driver before running setup.bash, and check that nvidia-smi works.

Building Nereus

Nereus is the simulator and the operator's viewer, for the pool and the real robot (Nereus, the simulator and The Nereus viewer). It sits in release as a submodule but isn't a colcon package: it's a plain CMake project that also builds without ROS (the headless dataset renderer), and a COLCON_IGNORE file keeps colcon out of it.

cd ~/osu-uwrt/release/nereus
# once per machine: apt libraries, uv, the ~/.bashrc block
./setup.sh
# ROS, then release: the UWRT integration needs riptide_msgs2
source /opt/ros/humble/setup.bash
source ~/osu-uwrt/release/install/setup.bash
# the Python environment, then the ros-viewer build
./build.sh
setup.sh
apt-installs the libraries (Eigen, yaml-cpp, Bullet, Assimp, GLFW, GLEW, EGL, OpenCV, ...), installs uv if it's missing, and offers to add a # >>> nereus >>> block to ~/.bashrc that sources build/ros-viewer/ros/setup.bash.
build.sh
Runs uv sync --locked (the .venv with the pack and dataset tools), then the CMake preset: ros-viewer if ROS is sourced, otherwise datasets. ./build.sh <preset> picks another from CMakePresets.json.
Jobs
One per 3 GB of free memory after 4 GB for the desktop, at most one per core; its heaviest files need about 3 GB each to compile. NEREUS_JOBS=2 ./build.sh overrides it.
conda
An active conda environment is stripped from PATH for the build: its libraries would shadow the system ones OpenCV links against.
Output
build/ros-viewer/: nereus-viewer, the simulator, the tests, and ros/, a one-package ROS prefix that makes ros2 launch nereus ... work.

Then run it. Talos's stack uses Zenoh as its ROS middleware (ROS 2, the Talos way): it needs a router running, and every terminal needs RMW_IMPLEMENTATION=rmw_zenoh_cpp. The launch file's comment gives the reason: under full load with camera traffic, the default FastDDS stalled the simulator's /tf for 0.4 to 0.9 s; Zenoh didn't. For the sim you run your own router (terminal 1). On the real robot the Orin runs the router and your laptop joins it as a client: see Joining from your own laptop.

ros2 run rmw_zenoh_cpp rmw_zenohd
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim

That starts the simulator, Talos's whole stack and the viewer. On a machine with CUDA, the first start can take minutes while the detector builds its TensorRT engine for the forward camera (above). Launching the stack and Working on it yourself go from here.

VS Code

Any editor works. If you use VS Code:

  • Start it from a sourced terminal: cd ~/osu-uwrt/release && code .. It inherits that environment, so its terminals, tasks and debugger see ROS and your workspace.
  • C++ navigation needs compile_commands.json. Nereus's presets already write build/ros-viewer/compile_commands.json. For colcon packages, add --cmake-args -DCMAKE_EXPORT_COMPILE_COMMANDS=ON and point the C/C++ extension or clangd at build/<package>/compile_commands.json.
  • Ignore committed .vscode folders. riptide_control's c_cpp_properties.json lists include paths under one member's home folder. colcon deploy skips .vscode.
  • Format C++ the project's way. Nereus has .clang-format and .clang-tidy at its root.
  • Behaviour trees have their own editor, the team's Groot fork (riptide_setup's setup_scripts/optional_installs/install_groot.bash builds it in ~/groot and adds a groot command); see Writing and testing trees.

A VS Code dev container was tried in riptide_dev (a ros:humble image; last commit September 2025, empty README). riptide_setup doesn't use it.

Git: branches, pull requests and release

Each repo works the same way: a branch per change, a pull request to merge it. Before competition, dev merges into master. Some long-running branches (mpc, newsim, mapping-estimator) carry work far ahead of master, and feature branches merge into them. The release repo then pins the commits that go in the water.

Before your first push, tell git who you are and how to log in. Everything was cloned over https, so the simplest login is the GitHub CLI (sudo apt install gh); an SSH key works too if you switch the remotes to git@github.com: URLs.

git config --global user.name "Your Name"
git config --global user.email you@example.com
# answer HTTPS, then yes to "Authenticate Git"
gh auth login

The release README sets the routine: before a pool test, bump the submodules to the versions to test and commit to master; after it, commit any fixes, bump again, and tag the date. The log reads like a test diary ("Pre RPAC test 10-12-26", "Post sean test"), and the tags mark events (6-1-24-talos, robosub2026). Bumping a pin:

cd ~/osu-uwrt/release/src/riptide_control
git status                  # on your branch, nothing uncommitted
git push                    # a pin must be a commit others can fetch
cd ~/osu-uwrt/release
git add src/riptide_control # records the submodule's current commit
git commit -m "Pre RPAC test 10-30-26"
git push

Before a pool test the checks require every pin committed and pushed, and the robot's code to match release exactly (Pool test day). A commit that exists only on your laptop can't be checked out by anyone else.

Getting code onto Talos: colcon deploy

The team's code isn't cross-compiled. colcon deploy, a colcon verb from riptide_setup's colcon_riptide extension, copies package sources to the Orin and builds them there, in ~/colcon_deploy. Run it from ~/osu-uwrt/release:

  • You need source ~/osu-uwrt/riptide_setup/install/setup.bash (it provides the verb), the Python packages fabric and scantree (setup_release.bash installs both), a passwordless SSH key for ros@ the Orin, and the Orin's name in /etc/hosts. The current Orin is orin2 (192.168.1.24 on the robot's network at the time of writing); setup.bash only adds an older orin entry.
  • On the robot, src/ is flat: one folder per package, no git. A package deleted on your side stays there until someone removes it.
  • Packages with a DEPLOY_IGNORE file are never sent: riptide_meshes, riptide_rviz and camera_faker (desktop and simulator tools).
  • The robot builds with -DBUILD_DEPLOY=ON, which packages can test for. riptide_autonomy uses it to skip building the checkBT tree checker (CMakeLists.txt).
A deploy changes the robot

The Orin runs whatever is in ~/colcon_deploy the next time the stack launches. Deploy only committed, pushed code before a test, so release says exactly what ran. If code changes during a test session, the bench checks have to be redone. The team's pre-test sequence is a clean build on the laptop, deleting ~/colcon_deploy on the Orin, and colcon deploy orin2 --clean; a person runs it by hand.

The same extension adds colcon timesync orin2, the older manual tool: it sets the Orin's clock (and its hardware clock) to your laptop's over SSH, in one jump. The Orin is set up to take its time from the opbox's chrony server instead, which never steps the clock under a running stack (Computers and networks); check with chronyc sources on the Orin. Use timesync only when that server isn't available, and never while the stack is running: a backward jump of more than 10 s makes Nereus drop TF.

Setting up a Jetson from scratch

Rarely needed, and never on your first day. These scripts in release's scripts/ build ROS 2 itself for a Jetson, and set the Jetson up:

cross_build.py
Builds a ROS 2 distribution for arm64 inside a Docker container (an osrf/ubuntu_arm64 or debian_arm64 image), from a profile in scripts/meta_files: humble_robot_jetson is 264 repos, humble_core_jetson 117. It exists for Jetsons whose Ubuntu has no ROS 2 Humble packages. The result is ~/osu-uwrt/<profile>_built.tar.gz.
docker_arm64_qemu.bash
Lets an x86 machine run the arm64 container through QEMU, about 8 times slower (the README's figure).
remote_install.py
Picks the target from /etc/hosts and the tarball from ~/Downloads, sets up SSH keys and passwordless sudo, syncs the clock, checks the target is aarch64, installs dependencies and PyTorch, unpacks ROS, edits .bashrc, and configures JetPack (fan profile, no desktop, CAN modules). Enabling can0/can1 in jetson-io is left to you.
