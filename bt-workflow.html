Autonomy · Chapter 4

Writing and testing trees

How to change what Talos does on its own: edit a tree, add a C++ node when the existing ones can't do the job, test it alone, then fly it in Nereus before the pool.

The short version
  • Trees are XML files in riptide_autonomy/trees/. doTask reads the file fresh on every run, so a tree edit needs no rebuild.
  • Groot loads workspace.xml's subtrees over the file's own copies. For the competition files, edit the XML as text, and read git diff after any Groot save.
  • New behaviour means a new C++ node. btassistant.py create writes the header and a test stub. Rebuild with --cmake-clean-cache so it gets registered.
  • Three checks: the node's GTest cases, test_all_trees_load (every tree must build) and checkBT (the XML against the C++).
  • Fly it in Nereus first, from the viewer's Autonomy panel, with a scenario that puts Talos next to the task.

The practical side of behaviour trees, Talos's nodes and the competition tree, on the autonomy-mapping branch of riptide_autonomy (package riptide_autonomy2, BehaviorTree.CPP v3). The worked example was built and run for this page.

The loop

A change to numbers or structure in a tree skips steps 2 to 4. A new node goes through all seven.

Install Groot with install_groot.bash from riptide_setup: it builds the fork in ~/groot and links a groot command. A text editor is just as good, and safer for the competition files:

Groot replaces the file's subtrees

Opening a file in Groot loads every subtree in .groot/workspace.xml over the file's copy of the same name; saving writes what's on screen to both files (mainwindow.cpp; read from the code, not tried). Open and save RepairCompMpcTree.xml and seven of its subtrees turn back into the workspace's copies, which lag behind (PrimitiveMovePosition, SurfaceTree, ...). Edit the Comp Mpc files as text, and read git diff after any Groot save.

In a text editor, keep the structure Groot expects: one <BehaviorTree> per tree, a <TreeNodesModel> listing every custom node and subtree, and every port written out. Empty attributes trip Groot up too: the team's retreat paths are written ";" rather than "" "so Groot can save" (commit debcd47).

The workspace file and the tree files

BehaviorTree.CPP loads one file and nothing else, so every tree file carries its own copy of each subtree it uses. workspace.xml was meant to be the master copy: Groot loads it into every file you open, checkBT checks its node models against the C++, and checkBT --apply-workspace copies its subtrees into tree files, replacing any with the same ID.

In practice the newest work is in the tree files. The workspace holds 71 subtrees and 38 node models. The Mpc subtrees that fly the competition (SearchMpc, SpinTreeMpc and others) exist only in the two Comp Mpc files.

What that means for you:

  • Edit the file you will run. RepairCompMpcTree.xml and RescueCompMpcTree.xml differ only in their main tree (repair_mission="1" or "0"), so a subtree change goes into both.
  • Don't run --apply-workspace on the whole folder. It would put the workspace's copies of the same seven subtrees into the Comp Mpc trees.
  • If a subtree should be shared, paste its new <BehaviorTree> into workspace.xml by hand too.

Ports and the blackboard

Every value reaches a node through a port, an XML attribute. BehaviorTree.CPP v3 has four rules, three of them surprising:

  • Leaf nodes (actions, conditions): z="{ceiling}" reads the blackboard entry ceiling; z="-0.5" is the literal value.
  • SubTree ports name an entry in the parent tree, without braces: depth="depth". A number is a name too, so z="-1" needs <SetBlackboard output_key="-1" value="-1"/> above it.
  • Empty (z="", which Groot writes for every unset port) means "use the default" on a leaf input (tryGetInput). On a SubTree port it doesn't: it links to the parent's entry named "", which every empty output port writes to, so the subtree can get another node's value. RepairCompMpcTree.xml has such ports (target_3=""), and checkBT skips empty values.
  • Every UWRT port is a string, converted when read: std::stod reads "1.5m" as 1.5 silently and throws on "abc", aborting the tree.

Tunables go in a SetBlackboard at the top of the subtree, its name saying what the number means, with units: SearchMpc has name="Once seen, hold there at most this long for the map to converge (s)" output_key="hold_secs" value="8".

Adding a subtree

Most changes are a new or changed subtree, not a new node. Three pieces, all in the file you run:

<!-- 1. The subtree itself, next to the file's other <BehaviorTree>s -->
<BehaviorTree ID="HoldUnlessRising">
    <ReactiveSequence>
        <Condition ID="DeeperThan" max_age_secs="" z="{ceiling}"/>
        <Action ID="Wait" seconds="{seconds}"/>
    </ReactiveSequence>
</BehaviorTree>

<!-- 2. Its ports, inside the same file's <TreeNodesModel> -->
<SubTree ID="HoldUnlessRising">
    <input_port name="ceiling" required="true">Give up above this z (m)</input_port>
    <input_port name="seconds" required="true">How long to hold (s)</input_port>
</SubTree>

<!-- 3. The call, in the parent tree: port values name the parent's entries -->
<SetBlackboard name="Hold this long (s)" output_key="hold_secs" value="10"/>
<SubTree ID="HoldUnlessRising" __shared_blackboard="false" ceiling="ceiling" seconds="hold_secs"/>
  • The model (2) lists every port as input_port or output_port. BehaviorTree.CPP ignores it, but Groot draws the ports from it, and checkBT starts each subtree's list of known entries from its input_port names (CheckBT.cpp). Groot also adds a __shared_blackboard port line.
  • The call (3) keeps __shared_blackboard="false", as every call with ports in the Comp Mpc trees does (it is also v3's default), so the subtree sees only what its ports pass in.
  • Copy all three into both Comp Mpc files, and into workspace.xml if others should get it in Groot.

Writing a node

Write one for a new topic, service or calculation. Each node is one header in include/riptide_autonomy/bt_<kind>s/, a class deriving from a UWRT base class (UwrtBtNode.hpp):

Base classUse forYou write
UWRTActionNodeAnything that takes timeonStart() once, then onRunning() each tick until SUCCESS or FAILURE; onHalted()
UWRTConditionNodeA yes/no answer nowtick(): SUCCESS or FAILURE, never RUNNING
UWRTDecoratorNodeChanging how one child runstick(), ticking child_node_
  • static BT::PortsList providedPorts() lists UwrtInput("name", "description") and UwrtOutput(...).
  • void rosInit() creates subscribers and clients; doTask calls it once the tree is built. rosNode() is null in the constructor.
  • From autonomy_lib.hpp: tryGetRequiredInput<T>(this, "port", default) (warns if empty), tryGetOptionalInput (doesn't), postOutput<T>, formatStringWithBlackboard, and topic constants such as ODOMETRY_TOPIC, relative so they resolve under /talos.
  • UwrtBtNode gives you lookupTransform(from, to, tf), false if the transform isn't available (L21).

File name, class name and XML ID must be the same word: registration is generated from the file name. A node that finishes within one tick can instead be a function in SimpleActions.simple.cpp, registered with registerSimpleUwrtAction.

The BT assistant

btassistant.py does the chores. It finds the source package from its own path, so the installed copy edits src/ too. Four commands:

ros2 run riptide_autonomy2 btassistant.py [-s] [-f] <command> ...
CommandWhat it does
create <action|condition|decorator> <Name> [--no-rebuild]Writes bt_<kind>s/Name.bt<kind>.hpp and test/…/bt_<kind>s/TestName.cpp from templates, then a clean rebuild (no tests) unless --no-rebuild.
reconfigure_autonomy [--with-tests] [--debug]colcon build --cmake-clean-cache --packages-select riptide_autonomy2 from the workspace root, adding -DAUTONOMY_BUILD_TESTS=ON or a debug build.
check <files|behaviortree|nodes|system>files: every header has a TestName.cpp and the reverse. behaviortree: runs checkBT. nodes: rebuilds with tests and runs test_nodes. system: all three, then a summary.
generate_registrators <dir>Writes the three register*.cpp files. CMake runs it; you never need to.

-f (before the command) skips every prompt: it answers yes to "overwrite?" and "do nothing" in check files. -s hides the assistant's own messages.

Worked example: a depth guard

DeeperThan is a condition: SUCCESS while Talos is deeper than a given z. In a ReactiveSequence it stops a running subtree when Talos rises too far. It is not in the team's repo; files in tools/bt-workflow/example/.

1. Generate the files

cd ~/osu-uwrt/release
ros2 run riptide_autonomy2 btassistant.py create condition DeeperThan --no-rebuild

That writes bt_conditions/DeeperThan.btcondition.hpp (a "Hello world" tick()) and test/…/TestDeeperThan.cpp with one skipped test. Without --no-rebuild it also runs the clean rebuild.

2. Fill in the header

#pragma once
#include "riptide_autonomy/autonomy_lib.hpp"

// SUCCESS while Talos is deeper than `z` (odometry z: 0 at the surface, negative below).
// FAILURE before any odometry, or when the newest is older than `max_age_secs`.
class DeeperThan : public UWRTConditionNode {
    public:
    DeeperThan(const std::string& name, const BT::NodeConfiguration& config)
    : UWRTConditionNode(name, config) { }

    static BT::PortsList providedPorts() {
        return {
            UwrtInput("z", "Succeed while odometry z is below this (m, negative underwater)"),
            UwrtInput("max_age_secs", "Fail if the newest odometry is older than this (default 0.5)")
        };
    }

    void rosInit() override {
        odomSub = rosNode()->create_subscription<nav_msgs::msg::Odometry>(
            ODOMETRY_TOPIC, 10,
            [this](const nav_msgs::msg::Odometry::SharedPtr msg) {
                lastZ = msg->pose.pose.position.z;
                lastStamp = rosNode()->get_clock()->now();
                haveOdom = true;
            });
    }

    BT::NodeStatus tick() override {
        const double z = tryGetRequiredInput<double>(this, "z", 0.0);
        const double maxAge = tryGetOptionalInput<double>(this, "max_age_secs", 0.5);
        if(!haveOdom || (rosNode()->get_clock()->now() - lastStamp).seconds() > maxAge) {
            return BT::NodeStatus::FAILURE;
        }
        return (lastZ < z) ? BT::NodeStatus::SUCCESS : BT::NodeStatus::FAILURE;
    }

    private:
    bool haveOdom = false;
    double lastZ = 0;
    rclcpp::Time lastStamp;
    rclcpp::Subscription<nav_msgs::msg::Odometry>::SharedPtr odomSub;
};

The pattern of SeenRecently: subscribe in rosInit(), keep the latest value, answer from it in tick(), fail on stale data.

3. Write the test

TEST_F(BtTest, test_DeeperThan_fails_before_any_odometry) {
    auto node = deeperThan(toolNode, -0.5);
    ASSERT_EQ(node->executeTick(), BT::NodeStatus::FAILURE);
}

TEST_F(BtTest, test_DeeperThan_follows_depth) {
    auto node = deeperThan(toolNode, -0.5);
    auto pub = toolNode->create_publisher<nav_msgs::msg::Odometry>(ODOMETRY_TOPIC, 10);
    toolNode->spinForTime(0.3s); // discovery
    pub->publish(odomAt(-1.2));
    toolNode->spinForTime(0.2s);
    ASSERT_EQ(node->executeTick(), BT::NodeStatus::SUCCESS);
    pub->publish(odomAt(-0.3)); // above the limit
    toolNode->spinForTime(0.2s);
    ASSERT_EQ(node->executeTick(), BT::NodeStatus::FAILURE);
}
The helpers and the third case 
#include "autonomy_test/autonomy_testing.hpp"

using namespace std::chrono_literals;

namespace {
nav_msgs::msg::Odometry odomAt(double z) {
    nav_msgs::msg::Odometry msg;
    msg.pose.pose.position.z = z;
    return msg;
}

std::shared_ptr<BT::TreeNode> deeperThan(std::shared_ptr<BtTestTool> tool, double z) {
    BT::NodeConfiguration cfg;
    cfg.input_ports["z"] = std::to_string(z);
    return tool->createLeafNodeFromConfig("DeeperThan", cfg);
}
}

TEST_F(BtTest, test_DeeperThan_fails_on_stale_odometry) {
    auto node = deeperThan(toolNode, -0.5);
    auto pub = toolNode->create_publisher<nav_msgs::msg::Odometry>(ODOMETRY_TOPIC, 10);
    toolNode->spinForTime(0.3s);
    pub->publish(odomAt(-1.2));
    toolNode->spinForTime(0.2s);
    ASSERT_EQ(node->executeTick(), BT::NodeStatus::SUCCESS);
    toolNode->spinForTime(0.8s); // older than the default 0.5 s
    ASSERT_EQ(node->executeTick(), BT::NodeStatus::FAILURE);
}

5. Use it in a tree

Wait 10 s unless Talos rises above −0.5 m: the ReactiveSequence re-checks DeeperThan on every tick and halts Wait the moment it fails.

<root main_tree_to_execute="BehaviorTree">
    <BehaviorTree ID="BehaviorTree">
        <Sequence>
            <SetBlackboard name="Give up if Talos rises above this z (m)" output_key="ceiling" value="-0.5"/>
            <Action ID="GetOdometry" op="" or="" oy="" x="" y="" z="start_z"/>
            <Action ID="Info" message="At z = {start_z}; holding 10 s while deeper than {ceiling} m"/>
            <ReactiveSequence name="wait, unless Talos rises">
                <Condition ID="DeeperThan" max_age_secs="" z="{ceiling}"/>
                <Action ID="Wait" seconds="10"/>
            </ReactiveSequence>
            <Action ID="Info" message="Stayed deep the whole time"/>
        </Sequence>
    </BehaviorTree>
    <TreeNodesModel>   <!-- as Groot writes it -->
        <Condition ID="DeeperThan">
            <input_port name="max_age_secs" required="false">Fail if the newest odometry is older than this (default 0.5)</input_port>
            <input_port name="z" required="true">Succeed while odometry z is below this (m, negative underwater)</input_port>
        </Condition>
    </TreeNodesModel>
</root>

Without GetOdometry (which waits up to 3 s for a message) the first version failed 30 ms in: DeeperThan was ticked before any odometry arrived. Fixing the XML took no rebuild.

7. Commit it

riptide_autonomy is a submodule of riptide_release (src/riptide_autonomy, branch autonomy-mapping):

  1. Work on a branch of riptide_autonomy made from autonomy-mapping.
  2. Add the node to workspace.xml so the next person sees it in the palette: in Groot, right-click it in the palette and pick Add To Workspace. Or, in src/riptide_autonomy, run ros2 run riptide_autonomy2 checkBT -a $PWD/trees/.groot/workspace.xml and answer y only to DeeperThan was not found… (eight questions today). Without the file, -a asks about every tree too (160 questions); -y applies every fix in every tree.
  3. Commit the header, the test, workspace.xml and the real tree that uses the node, together, and push. Leave test and demo trees like DeeperThanDemo.xml out: anything in trees/ shows up in everyone's viewer list and in test_all_trees_load. Get it into autonomy-mapping by a pull request or a merge, as the team agrees; its history has both.
  4. Once it's merged, bump the submodule in riptide_release so a deploy picks it up (Pool test day).

Checking the XML: checkBT

Run it on your machine: deploy builds leave it out (CMakeLists.txt).

cd ~/osu-uwrt/release/src/riptide_autonomy
ros2 run riptide_autonomy2 checkBT                       # workspace, then every tree
ros2 run riptide_autonomy2 checkBT $PWD/trees/MyTree.xml # one file
  • C++ nodes against the model: missing nodes, extra nodes, port names and directions. Only header nodes: simple nodes such as AddWaypoint and AddArc are never reported missing.
  • Unbalanced braces such as {key|.
  • SubTree port values that no earlier node writes (empty values and numbers are skipped).

It answers "no" to its fix-it prompts unless you pass -a (ask) or -y (yes to all), and exits 2 if anything is unresolved. Today: 152 warnings (mostly ports filled further up, out of its sight) and 8 issues of three kinds:

[ERROR] [btchecker]: Node SeenRecently: port min_score has a different direction (inout_port) in Groot than in the c++ implementation (input_port).
[ERROR] [btchecker]: Node CenterDetection has a c++ implementation but is missing from the Groot workspace.
[ERROR] [btchecker]: Node CompareNums in tree TorpedoTree (trees/DemoTableTree.xml) has a malformed blackboard reference in port "a": {repair_mission|. Check that every '{' has a matching '}'.
checkBT edits your files
  • It saves every file it checks back in place, so a file can come back reformatted. Commit first and read git diff after.
  • Its "make one?" fix adds a SetBlackboard as the first child of the SubTree's parent. If that parent is a decorator such as ForceSuccess, the tree no longer loads. An older checkBT did this to ActuatorTrees.xml and SurfaceTree.xml (with numbers, which it now skips); it still does it for names.
  • It crashes on a tree file with no <TreeNodesModel>.

Running a tree

Trees are run by doTask, started by bringup as node /talos/autonomy (DoTask.cpp, messages in riptide_msgs):

Action
/talos/autonomy/run_tree, riptide_msgs2/action/ExecuteTree. Goal: tree, the file's full path. Result: error, returncode.
List
/talos/autonomy/list_trees: every .xml in the source trees/ folder and in the installed copy.
Stack
/talos/autonomy/tree_stack: the running branch. The action's feedback is never sent; read this topic.
Ticks
Every 30 ms, on its own thread.
Log file
~/btlogs/BTLog_YYYY_MM_DD_HH:MM:SS.fbl: every status change (parameter log_file_dir).
Also
/<hostname>/autonomy/bag_trigger, published every second: true while a tree runs, false otherwise. Groot's live monitor (ZMQ) is off: enable_zmq: false.

The file is read when the goal arrives, so an edit in src/riptide_autonomy/trees/ is live on the next run. On the robot, deploy again after editing.

The team runs trees from the Nereus viewer, in the sim and at the pool: open Autonomy, pick a tree, press Enable, then Start. Start stays grey until the viewer's motion is enabled, fresh and uncontested; while a tree runs the panel's manual motion is blocked. Stop, or the viewer's Kill button, cancels the tree, whoever started it. The physical kill switch does not (Behaviour trees). How a run ends:

After a run

  • Info messages go to doTask's log: the launch terminal (output='screen') and /rosout.
  • The stack without the viewer: ros2 topic echo /talos/autonomy/tree_stack.
  • The .fbl log is on the computer that ran doTask, the Orin at the pool. Copy it off like a bag (rsync -a ros@192.168.1.24:btlogs/ ~/btlogs/) and open it in Groot's Log Replay mode.
  • If doTask crashed, it stays down (respawn=False) until you relaunch.

Testing in Nereus

Nereus runs Talos's real stack, doTask included, so a tree behaves there as it will in the pool, minus real water and noise (Nereus, the simulator):

ros2 run rmw_zenoh_cpp rmw_zenohd          # terminal 1: the Zenoh router
ros2 launch nereus sim.launch.py active_control_model:=mpc mpc_model:=sim   # terminal 2

Then Enable, pick the tree, Start. To test one task without flying the whole course:

  • Make a test tree: a copy of the competition file whose main tree calls the one subtree, like TestTorpedoTree.xml.
  • Start Talos next to the task. Copy scenarios/talos_uwrt/scenario.yaml into a new pack folder, change initial.position_m (or a task's task_placements), and launch with scenario:=<folder>. Pack paths in it must stay relative. Moving props: Perception's "Working on it yourself".
  • Run it headless for a repeatable check. acceptance/mission.py starts the sim and stack in a private ROS domain, releases the kill switch, runs --tree, and writes mission.json (result, visited stack, scores) and the bridge's tasks.json into --output.
cd ~/osu-uwrt/release/nereus
python3 integrations/uwrt/acceptance/mission.py --output /tmp/mission_run1   # folder must not exist yet

It runs RepairCompTree.xml unless you pass --tree, and gives up after --timeout (1800 s). It passes no controller arguments, so the stack comes up with the launch files' default controller (hybrid, the legacy one), not riptide_mpc. For the Mpc trees, use sim.launch.py with the MPC arguments above.

Every sim run writes its records (resolved.json, execution.json, summary.json, tasks.json) to /tmp/nereus_sim/<timestamp>. Record a bag too, to tell a tree mistake from a perception or control one. Before the pool, run the exact file you will run there, start to finish.

Common mistakes

Each came from the code or happened while writing this page.
