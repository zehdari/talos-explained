Running Talos · Chapter 5

Debugging, bags and data

"Talos isn't working" is never the real problem. This chapter is how to find the real one: what to check in what order, what each failure has looked like before, and how to record a run so you can study it at home.

The short version
  • Work down the chain: network, launches, topic rates, enable, values, logs. Stop at the first step that fails; most problems are in the first two.
  • Live, use the ros2 command line (with --no-daemon over Zenoh), the launcher page for node output and the Nereus viewer's Plots.
  • Record a bag of every run, on the robot. Without cameras the robot's topics are about 0.4 MB/s of messages (about 0.5 MB/s on disk); one camera stream adds about 2.3 MB/s.
  • A bag is a SQLite file you can read in twenty lines of Python, or replay into the viewer, or into a node with new parameters to test a fix without the pool.
  • header.stamp is when something was measured, on the clock of the machine that stamped it. Compare stamps only from the same clock.

Work down the chain

Talos is a chain: your laptop reaches the Orin over Zenoh, the launcher starts the nodes, the nodes publish topics, the kill system lets the thrusters move, and the code turns all of that into behaviour. A break anywhere looks the same from the deck: nothing happens. So check the links in order, cheapest first.

Symptoms seen on Talos

Each entry below happened, or is written into the code as a known way to fail. Search for the words you see (a log line, a topic, a flag), or filter by part of the system. Every entry links to where it comes from.

The ros2 command line

Everything on Talos is a topic, a service, an action or a parameter, and the ros2 tool can look at all of them from any machine on the robot's Zenoh network. First, a shell that can see Talos (details in Computers and networks):

source /opt/ros/humble/setup.bash
# riptide_msgs2 and friends, or echo can't decode them
source ~/osu-uwrt/release/install/setup.bash
# Zenoh client to tcp/orin2:7447
source ~/osu-uwrt/release/scripts/dds_scripts/config_rmw.bash
# --no-daemon: the daemon may still hold an old RMW
ros2 topic list --no-daemon | grep /talos

Topics

ros2 topic hz /talos/vectornav/imu                # rate: 400 Hz on Talos
ros2 topic echo /talos/state/kill --once          # one message, then exit
ros2 topic echo /talos/state/thrusters/telemetry --field disabled_flags
ros2 topic echo /talos/odometry/filtered --field pose.pose.position --no-arr
ros2 topic info -v /talos/command/software_kill   # who publishes, with what QoS
  • hz measures what reaches you. From a laptop, a camera's rate is the tether's rate. Measure one stream at a time, or on the Orin.
  • --field keeps the output to the part you care about; --no-arr hides covariance arrays.
  • info -v is how you find a second publisher you didn't expect, like a competing operator on the kill topic.

Nodes and parameters

ros2 node list
ros2 node info /talos/mpc_controller              # its topics, services, actions
ros2 param get /talos/mpc_controller table_mode
ros2 param set /talos/mpc_controller table_mode false
ros2 param dump /talos/mpc_controller > live.yaml # then diff against riptide_mpc/config/mpc.yaml

A parameter set at the pool lives until the node restarts. The pre-test checks compare the node's live parameters with the deployed mpc.yaml to catch tuning left behind.

Services, actions and TF

ros2 service call /talos/set_camera_is_dfc std_srvs/srv/SetBool "{data: true}"
ros2 action send_goal /talos/gyro/tare riptide_msgs2/action/TareGyro \
  "{num_samples: 100000, timeout_seconds: 20}"     # still and level only
ros2 run tf2_ros tf2_echo talos/base_link talos/dvl_link
ros2 run tf2_tools view_frames                    # the whole TF tree as a PDF

Services and actions change things on the robot. Read what they do before calling one (Appendix A lists them).

Where the logs are

Nodes started by the launcher have no terminal. Their output goes to four places, and each answers a different question:

http://orin2:8080		Every launch's stdout and stderr, live. Cyan while starting, green while running, orange while stopping (the launcher).A node that crashed on start-up; what a launch printed.

The launcher pipes each launch's output to its web page only; it doesn't reach the journal (launcher.py). The MPC's lines worth searching for, all from mpc_controller_node.cpp:

  • Hardware output ENABLED or Hardware output disabled (…): at start-up, says whether RPM goes to the ESCs.
  • Table mode ON: thruster RPM capped at 500
  • Stale sensors, using EKF instead: … and No fresh odometry; thrusters off
  • MPC failed, thrusters off: …, MPC produced a nonfinite command, CAN thruster command failed
  • MPC solve … ms exceeds the control period

Plotting live

The Nereus viewer's Plots window (Windows › Plots) is the team's live plotter, on the robot and in sim (Chapter 3):

  • Lanes of series on one time axis; type plot odom z in the search (Ctrl+P), or right-click a Motion table row for Plot Z (actual, commanded, error).
  • Time from Header (default) plots each sample at its stamp. On the robot a row that says clock offset 1.2 s means your clock and the Orin's disagree.
  • A row says why a line stopped: stale 4.2 s, no publisher.
  • Export visible span as CSV writes ~/Documents/Nereus/plots/ for a quick look in Python or a spreadsheet.

PlotJuggler is the usual third-party tool for this. The team's old FastDDS scripts ran it as a discovery-server superclient, but riptide_setup doesn't install it today.

Recording bags

A bag is a recording of topics: every message, with the time the recorder received it. Record one for every pool run; a run that wasn't recorded can't be debugged at home.

  • On the robot. The viewer's Bagging panel runs ros2 bag record on ros@orin2 into ~/bags. It keeps going if the tether drops, and it gets every message, not just what crossed the tether (Pool test day).
  • By hand, the panel's command with the launcher's environment (from talos_uwrt_panels.yaml):
source ~/colcon_deploy/install/setup.bash
source ~/uwrt_config/source/zenoh_server.bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
# everything except the camera streams
ros2 bag record -o ~/bags/run_$(date +%F_%H%M%S) -a -x 'image|point_cloud'
# Ctrl-C to stop: that writes metadata.yaml
ros2 bag info ~/bags/run_...                      # duration, topics, counts
# bags exist only on the robot until copied
rsync -a ros@orin2:/home/ros/bags/ ~/bags/
Format
A folder holding metadata.yaml and one .db3 SQLite file: Humble's default sqlite3 storage. Every Talos bag used on this site is one. MCAP needs its storage plugin installed (-s mcap).
Killed recorder
No metadata.yaml. ros2 bag reindex <folder> rebuilds it.
What to leave out
Images and point clouds, unless you need them (-x 'image|point_cloud'). For camera video, the viewer's Recording panel writes lossless .svo2 files instead.
Presets
Selected plus a preset records just one task's topics: Random pinger comes from talos_uwrt_panels.yaml; Save adds your own to ~/.config/nereus/bag_presets.yaml (viewer.md).
Sim
Add --use-sim-time so bag times follow /clock (Perception, Chapter 11).
Camera files
An .svo2 plays back through the ZED wrapper in place of a live camera: ros2 launch zed_wrapper zed_camera.launch.py camera_model:=<model> svo_path:=<file> (zed_camera.launch.py; needs the ZED SDK).
Disk
The Bagging panel shows the robot's free space, yellow under 5 GB.

Two lessons from the numbers. Without cameras, the 400 Hz IMU and 475 Hz FOG are about four fifths of a robot-only bag. Keep them anyway: no estimator can be replayed without them. With a camera, the camera is the bag.

Reading a bag in Python

rosbag2_py reads a bag message by message; deserialize_message turns the bytes back into the ROS message. This reads the EKF and the DVL from the 2026-10-26 pool session and compares their horizontal speeds (read_bag.py):

import sys
import numpy as np
import rosbag2_py
from rclpy.serialization import deserialize_message
from rosidl_runtime_py.utilities import get_message

reader = rosbag2_py.SequentialReader()
reader.open(rosbag2_py.StorageOptions(uri=sys.argv[1], storage_id='sqlite3'),
            rosbag2_py.ConverterOptions('cdr', 'cdr'))
types = {t.name: t.type for t in reader.get_all_topics_and_types()}
want = ['/talos/odometry/filtered', '/talos/dvl_twist']
reader.set_filter(rosbag2_py.StorageFilter(topics=want))   # skip everything else

rows = {k: [] for k in want}
while reader.has_next():
    topic, data, t_recv = reader.read_next()     # t_recv: when the recorder got it (ns)
    msg = deserialize_message(data, get_message(types[topic]))
    stamp = msg.header.stamp.sec + msg.header.stamp.nanosec * 1e-9   # when it was measured
    v = msg.twist.twist.linear
    if topic.endswith('filtered'):
        rows[topic].append([stamp, msg.pose.pose.position.z, np.hypot(v.x, v.y)])
    else:                                         # dvl_link is turned 45° from the body
        rows[topic].append([stamp, np.hypot(v.x, v.y), t_recv * 1e-9 - stamp])

odom, dvl = (np.array(rows[k]) for k in want)
print(f'odometry: {len(odom)} msgs, depth {odom[:, 1].min():.2f} to {odom[:, 1].max():.2f} m')
print(f'dvl: {len(dvl)} msgs, median age when recorded {np.median(dvl[:, 2]) * 1000:.0f} ms')
ekf = np.interp(dvl[:, 0], odom[:, 0], odom[:, 2])   # EKF speed at the DVL's stamps
print(f'horizontal speed, EKF minus DVL: rms {np.sqrt(np.mean((ekf - dvl[:, 1]) ** 2)):.3f} m/s')
$ python3 read_bag.py talos_20261026_204748/bag
odometry: 37009 msgs, depth -3.43 to -0.76 m
dvl: 9856 msgs, median age when recorded 126 ms
horizontal speed, EKF minus DVL: rms 0.022 m/s
  • Source the workspace first (/opt/ros/humble and release/install), or get_message can't find riptide_msgs2 types.
  • Filter topics: deserializing 500,000 IMU messages you don't need is most of the run time. Images are slowest of all.
  • Index by header.stamp for anything about physics; use the receive time only to ask how late something arrived.
  • Save to .npz once and analyse from that. Reading a 20-minute bag takes seconds to minutes; loading an array takes milliseconds.

Replaying a bag

ros2 bag play publishes a bag's messages again, in time. With --clock it also publishes /clock, and nodes started with use_sim_time:=true live in the bag's time. Two uses:

Into the viewer

The viewer draws a real robot from map → talos/base_link in TF, so a bag with /tf, /tf_static and odometry is enough to watch a run again, with the recorded thrust as arrows:

source /opt/ros/humble/setup.bash
# a private graph: nothing here reaches the robot, nothing reaches in
source ~/osu-uwrt/release/install/setup.bash
unset ZENOH_CONFIG_OVERRIDE ZENOH_ROUTER_CONFIG_URI ZENOH_SESSION_CONFIG_URI
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp ROS_LOCALHOST_ONLY=1 ROS_DOMAIN_ID=91
# runs until Ctrl-C; see below
python3 static_tf_from_bag.py BAG
cd ~/osu-uwrt/release/nereus
./build/ros-viewer/nereus-viewer --scenario /tmp/resolved.json \
  --pose-source estimate --use-sim-time true --robot-only --thrust
ros2 bag play BAG --clock 100 --start-offset 622 --topics /tf /tf_static \
  /talos/odometry/filtered /talos/thruster_forces /talos/state/kill
  • Isolate the replay. On the team's Zenoh network the bag's messages would mix with the live robot's, and a replayed command could reach it. A local-only FastDDS domain can't.
  • --start-offset skips /tf_static: most static frames are published only once, at start-up (one is re-sent every 2 s). static_tf_from_bag.py re-publishes the bag's statics; without it TF can't join world to odom.
  • robot.launch.py runs the viewer on wall-clock time for the live robot; for a bag, start it yourself with --use-sim-time true. Make /tmp/resolved.json with .venv/bin/python -m nereus.packs resolve content/packs/scenarios/talos_uwrt -o /tmp/resolved.json. The full recipe is viewer_replay.sh.

Into a node, with new parameters

The strongest debugging tool there is: replay a run's inputs into a node, change one thing, and compare its output with what the robot did. The EKF lag (symptom above) was worked out this way, without a pool test:

  1. Play only the EKF's inputs: vectornav/imu, gyro/twist, dvl_twist, depth/pose. Not its old output, or two EKFs publish odometry/filtered.
  2. Run robot_localization's ekf_node with talos_ekf.yaml, use_sim_time:=true, under the robot's name (-r __ns:=/talos -r __node:=ekf_localization_node) and with the change under test.
  3. Publish the sensor mounts: the bag's static TF, plus dvl_link, which is on /tf (it hangs off a revolute joint), not /tf_static.
  4. Record the new odometry/filtered and compare. First run it unchanged: the replay must match the live EKF, or nothing after means anything. It did, exactly.

Stamps and clocks

Every message in a bag carries two times:

  • header.stamp: set by the publisher, meant to say when the data was measured, on the publisher's clock.
  • Receive time: when the recorder got it, on the recorder's clock.

The difference is a message's age when recorded. On a bag recorded on the Orin, both clocks are the same, so the age is real latency plus any deliberate back-dating:

  • The DVL is 125 ms old by design. The driver back-dates each stamp by the DVL's own dt2, the time from the echo to the output (dvl_driver.cpp). The stamp says when the water moved, which is what a filter needs.
  • The MPC's reference is ~32 ms old because it is stamped at the start of the tick and published after the solve (median 30 ms).
  • The bench bag's ages are all about −37 ms. Messages can't arrive before they were sent: the recorder's clock was behind the Orin's. Every cross-machine comparison from that bag is off by that much. Its dvl_twist isn't back-dated: the bench launch file runs fake_dvl.py, not the DVL driver.

What this means when debugging:

  • Compare stamps only from one clock. Anything that checks freshness against its own clock breaks across machines with different clocks: the MPC stops the thrusters when the newest odometry's stamp is 0.5 s old (odom_timeout), and its estimator drops sensor messages stamped more than 1 s ago.
  • Keep the clocks together. The opbox runs a chrony time server for the robot and the laptops (Computers and networks); chronyc tracking says how far off a machine is. The older colcon timesync orin2 sets the Orin's date over SSH as text to the second, so it is only good to about a second (timesync.py).
  • Don't step a running robot's clock. A backwards step of more than about 10 s makes the Nereus viewer drop TF.
  • In sim, everything runs on /clock. A node that reads the clock before /clock arrives gets zero; that is the cause of the sim-only mapping offset bug.
